# The Gemini job

The Gemini job is the one way in which Google's model takes part in the Dodam project. A script of the project runs Google's Antigravity CLI once, in its headless mode (`agy -p`), for one pull request or issue of the project, when the project's own account has put a mark on that item. The answer has a public part, which is posted as one comment on the item, and a private part, which stays on the owner's computer. The project's rules ask for a review by a model of another company than the author's, and for an attack by such a model before the judge counts for measurements and before the desk opens to the outside; this job is how that second pair of eyes looks.

Two programs make it up. The job (`job.py`) runs agy once for one item and one kind of look. The watcher (`watch.py`) looks at the repository at a steady pace and starts jobs, one at a time.

## What Google's pages say, and what is not known

Google's frequently asked questions for Antigravity say, as read on 19 November 2026: "Antigravity CLI headless mode (agy -p) is intended for direct scripting and CI workflows. Wrapping agy inside third-party coding agents or applications, or automating account rotation, is not supported under consumer plans." Under the question "Why can't I use third-party software (such as Claude Code, OpenClaw, or OpenCode) with my Antigravity login?", they say: "Using third-party software, tools, or services to access Antigravity is a violation of our Terms of Service". The terms say: "Using third party software, tools, or services to access the Service (e.g. using OpenClaw with Antigravity OAuth) is a breach of this Agreement. Such actions may be grounds for suspension or termination of your Antigravity and/or Gemini CLI accounts." The account is the owner's.

The job is a script of the project that events in the repository start, and it runs where the owner watches the project's sessions: in a terminal of Orca of its own (the owner's instruction of 23 November 2026, that every session of the project runs where the owner can watch it). Inside a coding agent's own shell it starts nothing: the owner's rule is that nothing runs hidden inside another session. Three properties are the job's own, each pinned by a check below: the process of the model cannot be typed into, it gets only the environment the job builds, and what it writes becomes public only through the job's check, as one comment on the item.

What the job relies on from Google's page on headless mode, as read the same day:

- `agy -p "<prompt>"` runs one prompt and exits. The response goes to standard output and diagnostics to standard error.
- `--output-format json` prints one JSON object when the run ends, with a `status` (`SUCCESS`, `ERROR`, `CANCELED`, `INTERRUPTED`, `INVALID`, `WAITING` or `RUNNING`), the `response`, and an `error` that is there only on failure. A run that fails exits with a code other than 0.
- `--print-timeout` bounds the wait for a response; by default there is no limit.
- `--sandbox` runs "with terminal sandbox restrictions enabled".
- `--model` names a model; with an unknown name the run exits with an error status and a code other than 0, rather than running another model. The name in the settings, `gemini-4-carbon-medium`, is the one the page lists beside "Gemini 4 Carbon (Medium)"; the CLI took it in the second run, on 20 November 2026, and that run reported that this model answered.
- Headless mode uses cached credentials: one signs in once in an interactive session. A run with no terminal that is not signed in exits with an "authentication required" error.
- By default the CLI follows the execution and permission modes in its own settings. A tool action that needs an approval it cannot get in headless mode is denied, the run goes on and exits with 0, and a notice naming the tool goes to standard error. Tools can be allowed ahead of time in the CLI's own settings file, which the job does not touch. `--dangerously-skip-permissions` approves every tool call of a run; the job never passes it.

What is not known:

- Google has not confirmed in writing that a job started this way counts as the "direct scripting" its page allows: a watcher that the project's coordinating session starts in a terminal of Orca, and that starts a run of agy for a mark on the repository.
- How long Google's quota window is, and how a used-up quota shows in the answer: the pages that were read say neither. When a run fails, the job reads its error and the end of its diagnostics. It takes the run as a used-up quota when they hold one of these: "quota", "rate limit" (also written together or with one character between), "resource exhausted" (likewise), "too many requests", "429", "usage limit", "limit reached", "out of credits". It takes it as signed out when they hold one of these: "authenticat" (the start of "authentication" and its kin), "not signed in", "sign in", "login required" or "log in required", "unauthorized" or "unauthorised". Those words are a guess. Diagnostics that use such words for another reason make a broken run read as a used-up quota (put back for the wait, at most three times for one mark) or as signed out (the watcher stops). The wait of five hours in the settings is a guess as well.
- What `--sandbox` restricts, beyond what the first run showed. In that run, on 19 November 2026, the verification look reported that its shell commands could read and write only in the checkout, in agy's own folder and in the temporary folders, with no network and no Docker or colima socket, so it could not start containers; the job has no check of its own on this. agy also has, as the first run reported, tools beside the terminal (searching the web, writing files, subagents, swarms, workflows, and timers and recurring jobs), and, as the second run reported, an option on a terminal command to leave the sandbox, denied in headless mode unless the CLI's own settings allow it; what the sandbox does to the other tools is not known.
- How agy tells its own version: the pages that were read do not say. The charter records, from Google's page "CLI troubleshooting" (read on 19 November 2026), that the Antigravity CLI updates itself in the background, checking at most once every 15 minutes, and that the variable `AGY_CLI_DISABLE_AUTO_UPDATE=true` is the official switch that turns this off; runs that produce numbers keep it on. The job produces no numbers and does not set it: it runs the CLI as installed, although the working rules ask for each CLI at a pinned version; holding agy at one version is work that remains, as the charter says. For every run it records the program file's resolved path, its size and its SHA-256 digest. That record shows which program file was started; it does not show a program that this file starts in turn, nor an update that happens while the run goes on.
- Where agy keeps its cached sign-in: the page says that headless mode uses it, not where it is. The job passes the real home folder on so that agy can find it, and in the runs of 19 and 20 November 2026 it did; where in the home folder it is kept is not known.
- Whether a prompt can be given on standard input together with `-p`: the page's list of flags says that `--input-format` (text or streaming JSON) reads prompts on standard input, but shows it only in the streaming mode. The job passes the prompt after `-p`, as the page's examples do.

The page also documents a streaming output, as read on 23 November 2026: `--output-format stream-json` prints one JSON event per line while the run goes on (one at the start, one for each step, with the steps' text and the tools' calls and output, and one at the end in the same shape as the JSON output). The job does not use it: it reads the one JSON object at the end, and the terminal shows nothing of the run's text before the run has ended.

## How it is started

The project's coordinating session starts the watcher in a terminal of Orca of its own that holds no coding agent, where the owner sees it run (the owner's instruction of 23 November 2026, that every session of the project runs where the owner watches). It opens the terminal with Orca's own command and types the start line into the terminal's shell, in the repository's root folder. It does not start the job by hand and does not call agy from its own shell. The line replaces the terminal's shell with the watcher, so that no shell is left in that terminal to read what is typed into it while the watcher runs or after it has ended; when the watcher ends, the terminal's process ends with it:

```
exec python3 tools/gemini/watch.py
```

The same line starts it in a terminal window of the operating system. The watcher refuses to run inside a coding agent's own shell. A session that types the line into a terminal of its own is one the refusal does not notice: the refusal guards against a start by accident inside an agent's shell, not against this decided one.

`--tell` names the coordinator's run in Orca. On 19 November 2026 that line did not arrive: called outside one of Orca's own terminals, Orca's command-line tool answered `no_active_sender_terminal`. The option stays; what the coordinator reads is `finished.log` in the private folder. The watcher keeps running until its terminal is closed or Ctrl-C is pressed. The job alone can be started by hand the same way, with a line that replaces the shell as well; it then asks GitHub which account is signed in and starts nothing when that is not the project's account, as the watcher does:

```
exec python3 tools/gemini/job.py --kind verify --number 12
```

Another session of the project can see that a run is on without opening the private folder. The command line that the job starts is agy's program, `-p` and the prompt, and every prompt begins with its template's first words, `You are the Dodam project's Gemini job`, the same in all three templates; a list of processes with their whole command lines (`ps -A -ww -o args=`) shows those words while a run is on, and not after it. Check: `test_a_run_can_be_seen_from_outside_by_the_first_words_of_its_command_line`.

With `--settings` and `--private` a person can name another settings file and another private folder. Started by hand that way, the job can be pointed at another repository, another account, a local address to fetch from, the sandbox switched off or another model, and it keeps its day's count, its quota's wait and its list of names in that other folder. That is the person's own act, outside the watcher's rules. The refusal inside a coding agent, the check that the item is the account's own, the environment agy gets and the scan hold all the same.

Before the first run, the owner writes the names that must never be posted (their own names in every spelling, and the computer's names) into a file named `names.txt` in the private folder, one per line. Without that file nothing is posted; a link in its place, an empty file or one with only comments counts as no file.

The private folder is named `dodam-gemini-` followed by the account's number and lies in the computer's folder for all accounts (the folder `Shared` beside the home folders), or in `/var/tmp` where there is no such folder; `--private` names another one. It must lie outside the repository and outside the folders `.dodam` and `.dodam-desk` of the home folder, and be a real folder that only the owner's account can open. It holds `names.txt`; `finished.log`, one line for every job that got as far as an answer folder; the job's state and the watcher's; the watcher's notes; and one folder for each job that got as far as its prompt: the prompt, the way agy was started, everything agy printed, the result, for an attack look the record of its containers, and, when there was a response, the response and the comment as it was or would have been posted. A job that stops before agy starts leaves less: when a coding agent is found right before agy, the prompt, the way agy would have been started and the result; when agy is not found, the prompt and the result. A response without a public part leaves the response and the job's fixed comment. One watcher runs for one private folder: a second one ends at once, with the exit code 5 and a note that another watcher is using the folder. A damaged state file of the job or of the watcher, also one whose inner values are damaged (a count that is not a whole number, a day that is not a date, a wait that is not a number, a version that is a truth value or not a whole number), is left as it is and stops them, without a trace of an error, until it is mended by hand.

Checks: `test_a_private_folder_that_is_not_apart_and_closed_starts_nothing` (in the repository, in `.dodam` or `.dodam-desk`, a link, open to others), `test_the_watcher_checks_its_private_folder`, `test_a_second_watcher_on_the_same_private_folder_ends_at_once`, `test_a_damaged_state_file_of_the_job_is_left_as_it_is_and_stops_it`, `test_a_damaged_state_file_of_the_watcher_is_left_as_it_is_and_stops_it`, `test_the_default_private_folder_is_named_after_the_account_in_the_folder_for_all_accounts`.

Three labels are the marks: `gemini-verify` for a verification look, `gemini-attack` for an attack look, and `gemini-discuss` for a discussion. For a discussion, the question is the newest comment of the project's account whose first line is `Question for the Gemini job:`.

## The rules, each with the check that pins it

"Checks" are the automatic tests in `bench/tests/test_gemini.py`. They run on every push, in the required job `variants` of the automatic check, beside the pilot's checks; they use no network, though the network is not switched off. They start the job and the watcher as programs, the way the coordinating session does, against stand-ins: a program named `agy` that records what it was given and answers what the check tells it to; a program named `gh` that serves made-up items and records every request; a program named `docker` that holds made-up containers; and a local git repository in place of the project's. Every check first makes sure that the names `agy`, `gh`, `orca` and `docker` lead to the stand-ins and that the repository is a local one, so no check calls the real model, the real repository or a real container tool. The programs are started through a small runner that leaves its own parent first, so that the processes above them are those of a plain terminal and not whatever started the checks. Some checks start them inside a terminal like one of Orca's instead: a program named as Orca's terminal host holds a terminal, starts a shell in it with Orca's names in its environment, types the line into it and types more while the program runs and after it has ended.

### Inside a coding agent's own shell, nothing starts

The job and the watcher look at their own environment and at all their parent processes before they do anything else, and the job looks again right before it starts agy. They refuse when the environment carries a mark of Claude Code or of two other coding agents, or when a parent process is a coding agent. The refusal names the mark or the parent and never its value. When the parent processes cannot be read, they refuse as well. Orca's own marks and Orca's terminal host are no reason to refuse: in a terminal of Orca that holds no coding agent the watcher and the job run, and a coding agent between Orca's terminal host and them still makes them refuse.

The marks of Claude Code are the ones it set in the shells of the session that wrote the job (Claude Code 2.1.327): `CLAUDECODE`, `AI_AGENT`, and every name that begins with `CLAUDE_`, among them `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_PID`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_CHILD_NOTES_DIR`, `CLAUDE_CODE_PLUGIN_DIRS`, `CLAUDE_CODE_FORCE_TERMINAL_IMAGES` and `CLAUDE_EFFORT`. The other agents' marks are names beginning with `CODEX_` and the name `OPENCODE`. The parent processes are recognised by the name of their program (among them `claude`, `codex`, `opencode`, `cursor-agent`, `aider` and `goose`) or by the package of a coding agent in their command line. Only Claude Code's marks and the program name `claude` were seen at work; the others are a guess, and a wrong one only makes the job refuse where it could have run. Orca's own marks, which no longer count, were seen in its terminals as names that begin with `ORCA_` and `TERM_PROGRAM` set to `Orca`, and its terminal host as a program named `Orca Agents` (Orca 1.4.266) and before that `orca-terminal-host`.

Checks: `test_inside_claude_code_or_another_coding_agent_the_job_starts_nothing` (each mark alone), `test_a_coding_agent_among_the_parent_processes_stops_the_job` (a real parent process named `claude`, `codex`, `opencode`, `cursor-agent`, `aider` or `goose`), `test_a_coding_agent_named_only_in_its_command_line_stops_the_job` (each package the job looks for), `test_under_a_plain_shell_the_job_runs_agy_once`, `test_the_watcher_inside_claude_code_asks_github_for_nothing`, `test_the_watcher_under_a_coding_agent_or_without_the_process_list_asks_github_for_nothing`, `test_the_job_looks_again_for_a_coding_agent_right_before_agy` (the parent turns into a program named `claude` while the job reads the item), `test_when_the_process_list_cannot_be_read_the_job_refuses`, `test_in_a_terminal_of_orca_the_job_runs_unless_an_agent_holds_it_and_agy_gets_no_input_and_no_terminal` (Orca's names in the environment, Orca's folder first in PATH, the terminal host by each of its two names; with a program named `claude` between the host and the job, it refuses).

### In a terminal, what is typed reaches neither the model nor a shell

In a terminal of Orca, sessions of the project can type with Orca's own command, as a person can at the keyboard. What is typed there while the watcher or the job runs, or after it has ended, reaches neither agy nor a shell:

- agy is started with its input closed (it reads from an empty device), in a session of its own, without a terminal: none of its descriptors is a terminal, it has no controlling terminal, and its output goes to files in the private answer folder.
- The watcher closes its own input as it starts, so that what is typed while it runs is read by nobody, and nothing it starts can read it either.
- The start lines above replace the terminal's shell with the program, so that no shell is left to read what was typed while the program ran or after it ended.

Control characters typed into the terminal still send their signals to the program that holds it: Ctrl-C stops it as the part on closing the terminal says; a signal it does not handle, such as the one Ctrl-\ sends, ends it outright, like a job killed outright.

Checks: `test_in_a_terminal_of_orca_the_job_runs_unless_an_agent_holds_it_and_agy_gets_no_input_and_no_terminal` (a line typed while the job reads the item does not reach agy), `test_the_start_line_leaves_no_shell_to_read_what_is_typed_and_the_watcher_closes_its_input` (the document's lines for the watcher and for the job, each typed into a terminal like one of Orca's; a command typed while the program runs and one typed after it ended are not run).

### Only a mark of the project's account on one of its own items starts a job

The watcher starts a job only for the newest event that put one of the three labels on an open item, when the account that put it has the project's numeric id (`project_account_id` in the settings), the item was opened by that account, and, for a pull request, its head lies in the project's own repository and not in a fork. A mark that does not qualify is remembered and starts nothing later; the label stays. In one round the watcher sees at most 100 open items for each label; more are not seen until fewer carry it. It remembers at most 5,000 handled and 5,000 ignored marks; past that the oldest are forgotten, so a mark whose label could not be taken off could start a job again after 5,000 later ones. Comments never start a job, so the job's own comments cannot; the job only ever takes labels off. An event that was handled is never handled twice, even when its label could not be taken off; when a job is done the label is taken off, so that putting it again (a new event) starts a new job. A job that could not read GitHub, or fetch the commit, before agy started is not handled: its mark stays, nothing is counted, and the next round tries again. A job that fails after agy started (its time was up, an error, an answer too long or without JSON, or a fault while posting) is handled: its mark is taken off without a comment, and its run counts in the day. A job whose prompt cannot be brought under its bound even with every comment and earlier answer left out (the template, the title, the description, the done criteria and the question stay) is handled as well: its mark is taken off, without agy being started and without counting in the day. So is a discussion mark on an item where the project's account has not written its question yet: the mark is taken off without a comment, without agy being started and without counting in the day, and a question written afterwards needs the mark again. A job started by hand on a marked item leaves the mark and the watcher's state as they are, so the watcher may start a second job for that mark. A missing sign-in, of GitHub's tool or of agy, gives the status `signed_out`; the watcher then stops and the mark stays. An item whose events or comments go past the bound of pages is left out for that round, with a note in the private folder (`watch-notes.log`), and keeps no other item from being looked at; its mark stays. So an outside account can keep one item from being looked at, by writing enough on it; the project then opens a new item. The job, started by hand, refuses an item that is not the project's own in the same way.

The signed-in account of the GitHub command-line tool is confirmed in every round, before anything is read for marks: when it is another account than the project's, the watcher stops at once. When GitHub answers that question with a fault, a sign-in it refuses among them (an expired token given in the environment, which version 2.101.0 of the tool reports as HTTP 401 and not as signed out), that round reads and starts nothing and the next round asks again; a fault while the marks are read leaves the round empty in the same way. At its start the watcher is strict: when it cannot confirm the account, for whatever reason, it does not start, and says so. The job confirms the account once more right before it posts a comment: when another account is signed in then, nothing is posted, the status is `settings` with the reason `account`, the run counts in the day, the watcher stops at once and the mark stays. A job started by hand also asks at its start, and starts nothing for another account.

`test_a_job_started_by_hand_refuses_an_item_that_is_not_the_projects_own` (also a closed item), `test_a_handled_mark_never_starts_a_second_job_and_a_new_mark_does`, `test_the_watcher_remembers_at_most_five_thousand_marks_of_each_kind`, `test_a_job_whose_commit_could_not_be_fetched_is_tried_again_by_the_watcher`, ### The prompt is made of three things only

The prompt is the template fixed in the repository for the kind of look, then the done criteria of the item, then text written by the project's account on the item: its title and description and its comments, oldest first. Comments of every other account are left out whole, also when they copy the job's first line or the question's first line. Quoted text inside the project's own text is left out too: every line that begins with `>`, also after the marks of a list item (`- >`, `1. >`); the lines that continue such a quote, up to the next blank line, which GitHub shows inside the quotation; every HTML block quote and every inline `<q>` quote, whole, also when quotes are nested; the tags are followed by name. When they do not balance (a closing tag that does not match the innermost open one, a closing tag with nothing open, a tag left open, or a tag that cannot be read to its end with certainty, such as one with a quote mark or `>` inside it), everything from the first quote tag of the text to its end is left out. A quote in a form the job does not recognise (for example inside a table cell, written with character references, or with a full-width `＞`) gets in, and so does a plain copy of someone's words. Leaving quotes out does not look at code: a line of code that begins with `>`, and the lines after it up to a blank line, are left out, and an HTML quote tag written in code as an example leaves out the rest of that entry. The third run reported that two earlier answers of the job were cut short this way. The job's own earlier answers go in a section of their own, marked as its own. For a discussion the newest question of the project's account goes last, under its own heading. Past the prompt's bound in bytes, the oldest entry is left out first, a comment or an earlier answer of the job, and the prompt says how many were left out; the template, the done criteria and the question never are. A discussion without a question of the project's account does not start agy. Reviews and review comments of a pull request are never read.

Checks: `test_no_text_of_another_account_reaches_the_prompt` (made-up comments of the project's account, of two other accounts and of a bot, with each form of quote and with copied first lines), `test_the_discussion_question_is_the_newest_marked_comment_of_the_project_account`, `test_a_discussion_without_a_question_of_the_project_account_does_not_start_agy` (started by hand, and by the watcher, which takes the mark off), `test_a_prompt_past_its_bound_leaves_out_the_oldest_comments_and_never_the_question`.

### A clean checkout of its own, with no remote

For each run the job makes a new folder in the computer's folder for temporary files, and checks that it lies outside the repository and outside the private folder; otherwise nothing starts. In it, it starts an empty git repository and fetches the pull request's head and its base branch (for an issue, the tip of `main`) from the public address in the settings, which needs no sign-in. It checks that the fetched head is the commit GitHub named, and stops when the head has moved. The head is the one GitHub names when the job reads the item, not the one there was when the mark was put: a push after the mark is what agy sees. The checkout is a clone of its own, not a worktree of any repository, and has no remote at all, so there is nowhere a push could go without naming an address. The branch `base` holds the base for comparing. The folder is removed when the run ends.

Checks: `test_a_folder_for_the_checkout_inside_the_repository_or_the_private_folder_starts_nothing`, `test_the_checkout_is_a_clone_of_its_own_at_the_head_commit_with_no_remote`, `test_an_issue_is_checked_out_at_the_tip_of_main`, `test_a_head_that_moved_since_github_was_read_stops_the_job`.

### agy gets no token and no key, and signed-out settings for gh and git

agy runs with an environment built from a fixed list of names, not by removing names from the job's own: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM`, `TMPDIR` and `TZ` as they are, and the following, set by the job. `GH_CONFIG_DIR` points at a new empty folder and `GH_PROMPT_DISABLED` is `1`, so a `gh` that the model starts finds no sign-in (on version 2.101.0 it ends with "To get started with GitHub CLI, please run: gh auth login"). `GIT_CONFIG_GLOBAL` points at a new empty file, `GIT_CONFIG_NOSYSTEM` is `1` and `GIT_TERMINAL_PROMPT` is `0`, so git has no credential helper and asks nobody; `GIT_SSH_COMMAND` is `false`, so a push over SSH does not reach the account's keys. No variable of Antigravity's own is set. Nothing of GitHub, Claude, Google's cloud or any other cloud gets through, nor an SSH agent. The job's own reading and posting happen outside agy's run, with the sign-in the job was started with.

Nothing in that environment marks Orca or a coding agent, whatever the environment of the watcher or the job carries. A value marks when it holds Orca's name or the name of a coding agent's program, standing alone and not inside a longer word. PATH loses its entries that mark (a terminal of Orca puts Orca's own folder first in it), and any other value that marks is left out: a home folder whose path marked would leave agy without its sign-in. When the folder for temporary files marks, the folders the job makes for the run would carry it: the watcher and the job then start nothing, with the reason `temporary_folder`.

This stops a mistake, not a program: a command that sets the variables back, calls the GitHub tool with its own settings, or reads the keychain is not stopped by it.

Checks: `test_agy_gets_an_environment_without_tokens_or_keys_and_signed_out_settings` (a dozen made-up secrets in the job's environment; none reaches agy; inside agy's run git has no credential helper and the SSH command fails), `test_agy_gets_the_environment_the_job_builds_and_nothing_that_marks_orca_or_an_agent` (the watcher under Orca's terminal host with Orca's names, marked entries in PATH and a mark in every other value passed on: agy gets PATH without those entries and none of the other values; a temporary folder that marks starts nothing).

### How agy is started

agy runs once, in the checkout, with the prompt after `-p`, `--output-format json`, `--model` with the model the settings name (settings without a model start nothing), `--print-timeout` set a little later than the job's own time bound, and `--sandbox` for the kinds that only read and reason (a verification look and a discussion). It never gets `--dangerously-skip-permissions`, a way to continue an earlier conversation, or prompts on standard input; its input is closed. It runs in a session and process group of its own, without a terminal, and the job ends that group: agy and every process that stayed in it, when agy ends, when the job's own time bound is up (the job's bound decides, and the status is `timeout`; agy's own limit is only a second line) and when the job is stopped. A process that left the group (started in a session or group of its own) and a container started through Docker's daemon are not stopped this way; the containers of an attack run that carry its label are removed when the run is over, as the next part says. agy also holds the job's lock: a job that is killed outright leaves the lock held until agy ends, so no second run starts beside it; a process that left agy's group with the lock keeps later jobs waiting until it ends. Before it starts, the job records in the private answer folder the program's resolved path, size and SHA-256 digest, the model it asks for, its arguments (without the prompt, which is kept beside them) and the names in its environment.

Checks: `test_agy_is_started_once_with_json_output_a_time_limit_and_the_sandbox_for_reading_kinds`, `test_what_agy_left_in_its_group_stops_when_agy_ends`, `test_a_job_killed_outright_leaves_the_lock_with_agy_until_agy_ends`, `test_settings_without_a_model_start_nothing`.

### The containers of an attack run are removed by its own label

An attack look runs without the sandbox and may start containers. Its template gives the run a label of its own, `dodam-gemini-run=` followed by 16 random hexadecimal digits, and requires it on every container the run starts. When an attack run is over, however it ended (with an answer, past its time, with an error or stopped by a signal), the job asks the container tool for the containers that carry this run's label (`docker ps --all --quiet --no-trunc --filter label=...`) and removes those and no other (`docker rm --force` with their ids): two calls at most, each bounded by `container_seconds` in the settings, 60 seconds. A listing that holds anything but containers' ids removes nothing. It records in the answer folder what it found and removed. When the computer has no container tool, or the tool fails or does not answer in time, that is recorded, and nothing else about the run changes: neither its status nor what is posted; nor does a record that cannot be written. After a verification look or a discussion, whose sandbox cannot start containers, the job calls no container tool. Containers started without the label, such as those the project's own tests start, are not removed by the job; the template asks the model to stop and remove every container it started before it answers, and that is an instruction, not a limit.

Checks: `test_the_containers_of_an_attack_run_are_removed_by_its_own_label_only` (an attack look with an answer, past its time and stopped by a signal; a fault of the container tool; a container tool that does not answer, with a bound of one second; a listing that is not of ids; no container tool; a record that cannot be written; a verification look; a discussion; containers without a label, with another run's label and with another label stay), `test_each_attack_run_has_a_label_of_its_own` (two attack runs, each removing its own).

### The whole answer stays private, and one comment carries the public part

Everything agy prints is written to the answer folder in the private folder and stays there. From a successful response the job takes the part between a line `=== PUBLIC ===` and a line `=== PRIVATE ===`: exactly one line of each, the public one first. Anything else (a mark missing, doubled, out of order, or written in another form), and an empty public part, gives the status `no_public_part`: nothing of the response is used, and the job posts one fixed comment of its own words under its first line, saying that the run gave nothing that can be posted, that nothing of it is used, and that putting the mark on the item again starts another run. That comment carries nothing of the response, in any form; it goes through the scan and the confirmation of the account like any other comment, and when the scan holds it, it is not posted and the reasons say why. The mark is taken off and the run counts in the day. The verdict is read from the public part only, and is one of two fixed words: `approve` when the public part holds a line that is "Verdict: approve" from its start and no other verdict line, otherwise `changes-needed`; a quoted, listed or emphasised verdict line is not read. A run that gave no public part to read, for whatever reason, has the verdict `none`. The comment's first line is written by the script and says that the project's Gemini job wrote it automatically; the model cannot write it or remove it. A public part longer than its bound is not posted.

Checks: `test_the_whole_answer_stays_private_and_only_the_public_part_is_posted_under_the_scripts_first_line`, `test_the_verdict_is_one_of_two_fixed_words_and_unclear_means_changes_needed`, `test_an_answer_without_a_public_part_or_too_long_is_not_posted`, `test_an_answer_not_cut_by_exactly_one_line_of_each_mark_in_order_is_not_posted`, `test_an_answer_without_a_public_part_gets_a_status_of_its_own_and_a_fixed_comment` (two answers that hold a made-up token and text of another account give the same comment, with nothing of either; a listed word in the comment keeps it back).

### The scan: nothing that must not be public is posted

Before posting, the comment is put into one normal form (invisible characters removed, full-width letters made plain) and scanned three times: as it is, and on two copies in which character references are resolved and tags written on one line and the marks `*` and `~` are taken out, one with code spans and blocks taken out and one with them kept, so that nothing passes because the scan took it for code. It is not posted, and the result says which kinds it found, when it holds: a personal name (from `names.txt`; the account's own name and full name, each from three characters on; a Korean name with an honorific; or an @-mention, also inside code. A listed name counts also when it is joined to digits, hyphens or underscores, or when its words, in ASCII or not, are joined by other characters); an e-mail address; a local path, in any case of letters (a home folder, the system's temporary folders including `/tmp` and `/var/tmp`, `~/` and `$HOME`, the private folder's own path also when `--private` names one elsewhere, in the spelling with its parent folders resolved (named through a linked folder, its other spelling is held only when it matches one of the shapes here), or a Windows user folder written with either kind of slash; a path is held also inside a code span); an address inside a private network (private and shared IPv4 ranges, private and link-local IPv6 addresses, names ending in `.local`, `.lan`, `.internal`, `.home.arpa` or `.ts.net`); a computer's name (this computer's name, from four characters on, or a name such as one ending in `-Mac-mini`); a work item number (the prefixes in the settings, or a Linear address); or the shape of a token (GitHub, Anthropic, AWS, Google, Slack, GitLab, DigitalOcean and npm tokens, a run of 40 letters, digits, slashes and plus signs that holds a slash or a plus, whatever its mix and also right after or right before an equals sign, unless it goes on from a word, a path or a host name (without that exception the rule held 14 stretches of the repository's 43 documents on 20 November 2026, all of them paths of web addresses, and with it none), private keys including PGP ones, signed web tokens, and any run of 32 or more letters, digits, dashes and underscores that mixes capitals, small letters and digits). A commit's hexadecimal name passes. When `names.txt` is missing, nothing is posted. The scan also holds some answers that could have been posted, such as an @ that is not a mention, also inside code, a path of a build machine, or a long identifier that mixes capitals, small letters and digits; holding is the safe side. No scan stops deliberate hiding: a name split by a code span, by a link, or by a tag written over several lines, for example, passes it.

Checks: `test_a_public_part_that_fails_the_scan_is_not_posted` (one case or more for each kind), `test_the_accounts_names_and_the_computers_name_count_from_their_cut_offs`, `test_the_comment_is_put_into_one_normal_form_before_the_scan`, `test_without_the_private_list_of_names_nothing_is_posted`.

### The coordinator hears one fixed line

When a job that got as far as an answer folder ends, it appends one line to `finished.log` in the private folder:

```
gemini-job kind=verify number=12 status=posted verdict=approve private=<the answer folder>
```

The status is one fixed word (`posted`, `held`, `no_public_part`, `quota`, `timeout`, `signed_out`, `refused`, `settings` when another account was signed in right before posting, `stopped` or `error`), and so is the verdict (`approve`, `changes-needed` or `none`). With `--tell`, the job also sends that line to the coordinator's run with Orca's command-line tool (`orca orchestration send --to run:<run> --type status`). On 19 November 2026 such a send, made outside one of Orca's own terminals, did not arrive (the tool answered `no_active_sender_terminal`); what the coordinator reads is `finished.log`. The line carries no text of the model.

Checks: `test_the_coordinator_hears_a_fixed_line_that_carries_no_text_of_the_model`, `test_without_a_run_to_tell_the_line_goes_only_to_the_private_file`.

### The terminal shows each run

What the watcher or the job prints in its terminal, on standard error: when a run of agy starts, its kind, the item's number and the item's title; while it runs, a line a minute with the kind, the number and the minutes it has run; when it ends, the status, the verdict and the reasons, which are fixed words, and, when the comment was posted, the public part as it was posted. When the answer is held, the terminal shows the reasons and nothing of its text; the private part is never shown. The title and the public part are shown without control characters, so that neither can drive the terminal. The public part is shown only once it is on the item: a session that can read the terminal (Orca lets sessions read its terminals) learns nothing of the model's answer that it could not read on GitHub. Standard output carries only the result line in JSON, as before.

Checks: `test_the_terminal_shows_each_run_its_title_a_line_a_minute_and_how_it_ended` (a run of a minute and a little that is posted, with a control character in the title and in the public part; a run whose answer the scan holds), `test_the_whole_answer_stays_private_and_only_the_public_part_is_posted_under_the_scripts_first_line` (nothing of the private part is printed).

### Bounds

Every bound is in `settings.toml`, and a check pins each at its value, with the model and the prefixes of work item numbers: a look every 60 seconds, at most 8 runs of agy in a day (by the day in UTC), at most 1,800 seconds for one run (the templates tell the model that the run is ended after 30 minutes and that its answer is to be written by 20), a wait of 18,000 seconds when Google's quota is used up (a guess at the quota's window), a prompt of at most 100,000 bytes, a public part of at most 30,000 characters, an answer of at most 2,000,000 bytes, at most 10 pages of 100 comments or events for one item (an item with exactly 1,000 is read), a mark put back at most 3 times for a used-up quota, and at most 60 seconds for each call of the container tool after an attack run. Settings without a bound, or with one out of its range, start nothing. The job itself keeps the day's count and the quota's wait, in its own state in the private folder and under its lock, however it was started: by the watcher or by hand. One job runs at a time: the lock keeps a job started by hand and a job of the watcher apart, and the watcher starts the jobs of one round one after another. A run past its time is stopped by ending agy's process group. When Google's quota is used up, as far as the job can tell from words that are a guess, the job is put back: its mark stays, it is counted neither as handled nor in the day, and no run starts until the quota's wait has passed. The fourth time the same mark meets a used-up quota, its job is handled as an error and its run counts in the day.

Checks: `test_the_settings_file_holds_every_bound_at_its_decided_value`, `test_settings_without_a_bound_or_with_a_bound_out_of_range_start_nothing` (each bound missing, below and above its range), `test_the_day_bound_stops_jobs_and_keeps_the_marks_for_the_next_day`, `test_one_job_runs_at_a_time`, `test_a_job_past_its_time_is_stopped_with_the_whole_process_group_of_agy`, `test_used_up_quota_puts_the_job_back_until_the_window_has_passed`, `test_a_job_started_by_hand_keeps_the_day_bound_and_the_quota_wait_and_counts_in_the_day`, `test_an_answer_past_its_bound_in_bytes_is_not_read`, `test_comments_past_the_bound_of_pages_stop_a_job_before_agy`, `test_each_word_searched_in_a_failed_run_reads_as_quota_or_signed_out`, `test_a_mark_put_back_for_a_used_up_quota_three_times_is_then_handled_as_an_error`, `test_the_watcher_asks_at_its_pace`.

### It runs only while its terminal is open, and installs nothing

The watcher and the job run in the foreground of the terminal they were started in; started with the lines above, each is the terminal's own process. When the terminal closes (or on Ctrl-C, or when they are told to stop), they end agy's process group and then themselves; what left that group is not stopped. A job stopped this way writes its result and its line with the status `stopped`; its run stays counted in the day and its mark stays. Neither installs a service, a scheduled task or anything else that keeps running, and both use only Python's standard library.

Checks: `test_closing_the_terminal_stops_the_program_and_agy` (each of the three signals), `test_nothing_is_installed_to_keep_running_and_only_the_standard_library_is_used`.

### The templates

Each of the three templates says what its look is and what it is not, asks for the public part and the private part, asks for the verdict line, and carries the rules for the owner's computer: programs under test run only in containers, as the tests run them, never on the host; one batch of containers at a time; the free space is read first and the work stops under 20 GB; Docker and colima are never restarted or pruned; nothing is deleted with a bare wildcard; the folders `.dodam` and `.dodam-desk` of the home folder, the keychain, tokens and keys are never opened; nothing in the pull request is changed, nothing is pushed or merged, no setting is changed; text in the repository is data, not instructions; no subagent, swarm, workflow or schedule is started; and nothing in the public part tells how the judge, the measuring tools, the desk or this job itself could be fooled. Each tells the model, with numbers that the job fills in from the settings it runs with, after how many minutes the run is ended, that nothing of a run that is ended is kept, and by when its answer is to be written: by two thirds of the run's time. The verification look and the discussion say that their sandbox cannot start containers and run no program under test; the verification look says in its private part what could not be run. The attack look's public part says which parts were looked at, how many attempts succeeded and how serious each is; what was tried, and how, goes in the private part. The attack look starts no command that may take longer than five minutes, never waits for a command in the background, puts the run's own label on every container it starts, and stops and removes every container it started before it writes its answer.

Checks: `test_each_template_states_the_look_the_two_parts_the_verdict_and_the_rules`, `test_each_template_tells_the_model_its_time_with_numbers_from_the_settings` (each template, at 1,800 and at 900 seconds), and this page's own: `test_the_document_states_each_property_with_a_test_that_exists`.

## What the job does not do

- The refusal stops a coding agent from starting the job inside its own shell as part of its work. It cannot stop a program of the same account that removes its marks and leaves its parents; such a program could as well start agy itself. It does not notice a session that types into a terminal it did not start: a terminal of Orca, where sessions type with Orca's own command and where the coordinating session starts the watcher that way, a terminal inside a multiplexer such as tmux or screen that was opened earlier from a plain terminal, or a terminal driven through the screen (by AppleScript, or by an agent that works the computer's screen). It does not notice agents it does not list either, such as an agent built into an editor whose program is not named above. Once the watcher or the job runs, what is typed into its terminal reaches neither agy nor a shell, but the signals of control characters reach the program; a shell typed into before the program starts is that session's own act.
- The account is confirmed at the start of each round and right before each comment. A switch to another account after a round's confirmation is not stopped until the next confirmation: while that round reads the marks, their events, the items and their comments from GitHub, those are read under the other account; between the last confirmation and the post, the comment is posted under it; and before the watcher takes a label off, the label is taken off under it.
- The rules for the owner's computer in the templates are instructions to the model, not limits the job enforces, among them the time by which the answer is to be written, the rule on long commands and the rules on containers; only the removal of an attack run's labelled containers is done by the job, and containers without that label stay. The rule against subagents, swarms, workflows and schedules is such an instruction too: the job cannot stop them, and one of those inside a run counts as one run in the day. What may limit the model is the terminal sandbox for the reading kinds (what it restricts is partly known, from the first run), agy's own rule that an action needing approval is denied in headless mode (unless the CLI's own settings allow it), and the reduced environment above. The model runs as the owner's account with the real home folder; in an attack look, without the sandbox, it can read and change what that account can.
- agy keeps, as the first run reported, its own transcripts of each run (the prompt, its thinking, its tool calls and the whole answer, the private part included) in its folder under the home folder, outside the private folder. The job neither moves nor removes them.
- agy loads, as the first run reported, the checkout's `AGENTS.md` and the customisations of the checkout and of the home folder as rules placed above the prompt. The template is not the only instruction it gets, and a pull request that changes those files changes the rules for its own look. Antigravity's customisations also include skills, plugins, hooks and MCP servers; the third run reported that it loaded agy's own built-in skills from its folder under the home folder and offered a tool for asking questions. Whether `agy -p` loads or runs other customisations from the checkout or the home folder is not known, and the job does not stop it.
- A job killed outright leaves its folder for the checkout in the temporary folder, and a folder the model made that cannot be removed may be left there too: the job removes the folder without stopping at what it cannot remove.
- The scan finds shapes and listed values. It cannot know every name, and it cannot tell whether a public part explains how to fool the judge, the measuring tools, the desk or this job itself; that rule is in the templates only.
- Text of another account that the project's account copied without quoting it reaches the prompt; the job cannot tell it apart. agy also reads the files and the commit messages of the checkout, which hold text written outside the project once an outside pull request has been merged or fetched onto a branch of the project. Two rules the coordinating session works by cover what the job cannot: an item whose checkout holds files or commit messages written outside the project is not marked, and text written outside the project is never quoted, in any form, inside the project's own text on a marked item.
- The private answer folder can be opened by any program of the owner's account. The job hands no text of the model to anyone, but it cannot stop a session of that account from opening the folder.
- It does not post anything when it holds an answer, and it does not tell anyone on GitHub why.
