# The desk's lock

The desk is the AI session that reads what outsiders write to the Dodam project and answers in the project's name. A stranger's text is exactly what can make a model stop obeying its instructions, so the desk's rules are not instructions. Each one is something the session cannot do. This page says what the session can do, what makes everything else impossible, and what shows it.

How the lock works is public on purpose: it has to hold when it is known.

## What the session can do

This is the whole list.

1. Hear that something new arrived. It does not wait by itself. A relay, the small program in the desk's terminal, runs the watcher and writes every arrival into a kept list. It starts one session at a time, each a fresh one for one item: it tells the session the kind of each arrival and the number of that one item, lets it finish and ends it. Several arrivals on one item go to one session together. For a live session the tool's own way of waiting is used.
2. Read one issue or pull request of the project's repository as data (`read_item`). Outside the part marked as outside text the tool gives only numbers and fixed words (the item's number, issue or pull request, open or closed). Everything a stranger controls is inside the marked part, each entry cut to a size in bytes: the author's name, the labels, the title, the text, the newest comments and who wrote them. The whole is at most 20,000 bytes, and the tool says what it cut. For a pull request the tool classifies the changed files itself: it asks GitHub for what the fixed rule needs, runs the classifying function, and hands the session the verdict in fixed words (which protected folders are touched, whether a new test is added, whether it is ready for review), or only that the files could not be classified. Neither the changed lines nor the names of the changed files reach the session.
3. Answer on one issue or pull request of the project's repository (`answer`). The tool writes the first line, which says that the project's AI desk wrote the comment. It keeps the limits (for one item in an hour, for one account in a day, for everyone in a day), refuses when the way in is closed, refuses text that is too long, refuses text with a character that is not on the list of what the desk writes with, and refuses text that tells about the computer or the owner or holds a secret. Whether the answer says that the project's agents were told is a field, not wording: the tool adds a fixed sentence, in the language of the answer, exactly when a report about that item was accepted in that session.
4. Put one label from a fixed list on an item (`add_label`): `bug`, `enhancement`, `duplicate`, `invalid`, `question`, at most 100 a day.
5. Pass one short report to the coordinating session (`tell_coordinator`): one receiver, set when the desk is started; a fixed form; at most 800 characters; a first line saying that what follows may quote outside text. Every report is written into a kept list first. A report of a vulnerability is sent at once; every other kind goes out with one digest, at most once an hour. One report of a kind about one item is kept in a day. A session that handles an item reports about that item only, one report of each kind and three in all besides a vulnerability.
6. When the way in through live sessions is open, use these tools of AI coworker: `open_bridge`, `wait_for_message`, `inbox`, `read_conversation`, `reply`, `list_connections`, `write_agreement`. Never `connect` (which joins another session) and never `close_bridge`.
7. Read the files of its own copy of the public repository (`Read`, `Grep`), a stated number of lines and bytes at a time. There is no tool that lists files: a search that gives file names does that work, and its size is known before it runs.

## How it is started

```
python3 tools/desk/start.py --coordinator ADDRESS
```

The command is run in the terminal where the desk is to be watched. It checks everything it relies on, then runs the relay in that terminal, which starts Claude Code with the closed list once for every item, one session at a time. A fresh session takes in about 10,200 tokens before it does anything, the standing instructions included (measured once on the desk's model, with the real instructions).

Without `--state` the state folder is named `dodam-desk-` followed by the account's number and lies in the computer's folder for all accounts (the folder `Shared` beside the home folders), or in `/var/tmp` where there is no such folder. It is never in the home folder, because a session is shown paths of the state folder and the home folder's path names the account.

It refuses to start, with one sentence that says why and never with a trace of an error, when

- the file of facts, the standing instructions or the watcher is missing, or the standing instructions are longer than 12,000 bytes;
- the installed Claude Code is not the version the lock was checked on;
- the closed list (`lock.json`) is damaged, holds an entry of the wrong kind, names anything beyond the widest list written into the start command itself (a tool, a live-session tool, a name let into the environment, a longer search path), or states less for one turn or for one day than its own numbers add up to;
- the copy of the repository differs from what is committed, holds a file that is not part of it (ignored files count), or has its git folder inside the copy, where a session could read the names and addresses in it, or keeps that folder at a path that holds the account's or the computer's name;
- a path that a session can be shown holds a known value, in the reduced form described under "The check on text that leaves": the copy (which is the session's working folder), the state folder with the configuration folder in it, and the command of the check before every tool call;
- the state folder is inside the copy, is a link or lies under a folder that is a link (its real path must be given; the tools and the relay look at the folder the same way every time they use it, so a link put above it after the start is refused as well), is inside the hidden project folder (its name compared without regard to capital letters), or is open to other accounts. Folders that the command makes on the way to it are closed to other accounts, each of them;
- anything the command reads or writes in the state folder is not what it must be: a regular file (not a link, not a pipe, not a device, not a folder) or a real folder, owned by this account and closed to every other. That holds for the token files, the watcher's own state file, the folder `session` and each file in it, the lock file, the kept arrivals, the record of what was sent and spent, and the configuration folder. All of it goes through one module, which opens a file without following a link and looks at what it opened once more, so that nothing can be changed between the look and the use. The relay and the tools look at each of these the same way before every use, and the relay ends in one sentence when one of them is wrong;
- a path in the copy is longer than 200 bytes, or the closed list lets the sessions of a day write more reports than it keeps;
- a way in is open and the sign-in the sessions would use shows an email address;
- the way in through live sessions is open, because the limits of that way are not enforced yet; the live-session tools, where they are checked, must be a released version, not a pre-release;
- no receiver is given;
- the check that runs before every tool call does not answer;
- anything it did not expect goes wrong.

Each session is started

- without Claude Code's terminal interface, so that what is typed in the terminal reaches the session as a message and can never be a command;
- with two built-in tools, both of which only read, confined to the copy of the repository;
- with the desk's own tool server and, when that way is open, the live-session server, and no other;
- with no settings, instructions, hooks, plugins, commands or connected services of the person whose computer it is;
- with an environment that holds a handful of names and no secret;
- in the mode that refuses at once whatever is not allowed, with nobody asked;
- with a check before every tool call that refuses a tool off the list, that reads everything handed to a live-session tool the way an answer is read, and that counts the session's tool calls, its reading calls and the bytes they can hand over, and refuses the call past each bound before it runs. Claude Code shows a session the command of a check that refused and what the check wrote. So the command is the shell and one file in the state folder and nothing else, and of everything a check may print the session is shown one line: the reason, or a fixed sentence. The interpreter, the lock's files and the file of known values are named inside that file, which a session cannot read. The check fails closed: a crash, a missing interpreter or a check that hangs blocks the call, and the start command runs the check once and refuses to start when it does not answer;
- with Claude Code's own bound on the number of turns and its own bound on the size of one response;
- with Claude Code's description of the repository switched off, because it carries the owner's git name.

## The sign-in to Claude

A session cannot give away what it does not hold. Claude Code tells every session the email address of the account it is signed in with, and no check on outgoing text can catch an address that a turned model spells out, reverses or encodes. So the desk does not run on the owner's sign-in while a way in is open.

The owner puts a sign-in of the desk's own in the state folder: a file named `claude-token`, a regular file that only the owner's account can read. The start command hands it to a session through the session's environment and nowhere else (not on a command line, not in a file the session is pointed at, not to the tools, not to the watcher), together with a configuration folder of the desk's own inside the state folder, so that nothing of the owner's sign-in or settings is read. The command knows that it made that folder itself because it makes a new, empty one at every start, under a name it draws then, and removes the ones from earlier starts; a folder of that kind that is a link, a file or open to others stops the start. It then asks Claude Code itself, under exactly that configuration, what the sign-in shows. When the answer still holds an email address and a way in is open, the desk does not start. With every way closed it starts on whatever sign-in there is, so that the lock can be checked.

Tests show this with a stand-in for Claude Code's answer. That answer proves nothing about the token: Claude Code gives it for any string, without asking the service. So one condition for opening a way is not something the start command can check, and the owner's side checks it at deployment: the session was started once with the real token and asked what it knows without reading anything, and nothing of the owner was in what it said.

What a sign-in shows about the account (the address, the name of an organisation, a display name), for the owner's sign-in and for the desk's own, is added to the values that no text may carry out.

When the service refuses the desk's sign-in, the session ends at once. The arrival stays kept, the relay tells the coordinator once, and after three refusals in a row it starts no session until the desk is started again.

## The sign-in to GitHub

The session has no path to GitHub except tools 2, 3 and 4, and those make a fixed set of requests to one fixed repository: read an item and its comments; for a pull request, read the pull request (once before and once after the list of its files, to see that its head did not move), the folders of benchmark tasks at its base commit and at the tip of the main branch, the entries of the tests folder at the tip of the main branch, and the pages of its changed files; post a comment; add a label. One reading call makes at most 18 requests (10 of them pages of 100 files; a pull request with more changed files is not classified) and all of them fall under one deadline of 40 seconds, inside the session's own time.

When the owner puts a token of the desk's own in the state folder (a file named `github-token` that only the owner's account can read), the tools and the watcher use that token and never the owner's sign-in. The session cannot read the file. The fewest rights that work for such a token, limited to this one repository: metadata, read; issues, read and write; pull requests, read and write. Nothing else, and in particular no right to write the repository's contents, so the token cannot push or merge whatever is done with it. The listings of folders are public; that such a token may read them was not tried with a real token.

## What enforces each rule, and what shows it

"Tests" are the automatic checks in `bench/tests/test_desk_lock.py`, which run on every push without network and without a sign-in. "The live check" is `tools/desk/check_lock.py`: it starts the real locked session with the real start command against made-up data and tries each forbidden thing, asked plainly and asked by text planted in a made-up issue. Two further runs show the bounds inside one session (fourteen reading calls asked for at once, and more turns than a closed list of three allows) and a sign-in that the service refuses (a made-up token). One more run, made by its name only, shows that what the relay says about who is held back reaches the reading tool through Claude Code: a made-up item carries a comment of an account that the relay's record holds back, a session for another account's arrival reads it, and the comment is left out and counted as not shown. Its last result is in `tools/desk/lock-check.json`.

## The check on text that leaves

The first protection is that the session does not hold the owner's values at all. This check is the second. It is a list of what is allowed, not of what is forbidden.

Every text that leaves passes it in one place: an answer, the label, the report to the coordinator (which may quote a key an outsider wrote, since the coordinator is not an outsider, but only in characters on the list), and everything handed to a live-session tool. In this order:

1. The text is put into its composed form, so that a letter with its accent is one character. The no-break space and the ideographic space, which ordinary text holds without its writer knowing, become plain spaces, in what is checked and in what is sent. Then every character must be on the list below. Any other character is refused, whatever it is: invisible, blank, a control character, a letter of another alphabet, a small capital, a fullwidth letter or digit, an emoji.

| Characters | Why they are on the list |
| --- | --- |
| Tab, line break, space | Layout |
| The printable characters of ASCII: `A` to `Z`, `a` to `z`, `0` to `9` and its punctuation | English, and code |
| `¡` `¿` `ª` `º` `«` `»` and `Á É Í Ñ Ó Ú Ü á é í ñ ó ú ü` | Spanish |
| `×` `−` `≤` `≥` `•` `※` | What ordinary answers use: the times sign, the minus sign, at most and at least, the bullet, the reference mark |
| `·` | It is in the desk's own name |
| `–` `—` `‘` `’` `“` `”` `…` `→` | The usual marks of printed text |
| `、` `。` `々` `「` `」` `『` `』` `【` `】` `〜` | Japanese punctuation, with the lenticular brackets and the wave dash |
| Hiragana (ぁ to ゖ, ゝ, ゞ) and katakana (ァ to ヾ, with the middle dot and the long mark) | Japanese |
| Kanji and hanja (the main block, 一 to the end of that block) | Japanese, Korean |
| Hangul syllables (가 to 힣) and the single consonants and vowels as typed alone (ㄱ to ㅣ) | Korean |
| `！` `（` `）` `，` `：` `；` `？` `～` | Japanese fullwidth punctuation and the fullwidth tilde; fullwidth letters and digits are not on the list |

2. The known values are compared on a reduced form of both sides: case-folded, accents taken off whether composed or not, and a digit read as the letter it is written for, for all ten digits (0 as o, 1 as l, and i as l too, 2 as z, 3 as e, 4 as a, 5 as s, 6 as g, 7 as t, 8 as b, 9 as g). A value whose reduced form has six or more letters and digits is refused in four forms. One: wherever it stands, whatever is attached before or after it, be that letters of any of the four languages, digits, punctuation or nothing. Two: the same under the reductions. Three: the same with its characters, or groups of them, set apart by up to three characters that are not letters or digits; a space is such a character, and so is the long-vowel mark of Japanese in its wide and its narrow form, which looks like a dash. Four: across words however far apart, when it begins where a word begins and ends where a word ends. A shorter value is refused as a whole word, also under the reductions and set apart in that way. The known values are what names this computer and this account (asked of the computer itself), what a sign-in shows about the account, and the owner's git name and address. The project's name on GitHub and the repository's name are public and are never refused. The cost of form three is that an honest sentence can hold the letters of a value across a space by accident; of the 2,576 sentences of the project's own page in four languages and of both charters, checked with ordinary names as made-up values, none is refused for that.
3. Keys and other shapes. The known beginnings of keys are refused wherever a word begins with one and a letter or a digit follows, at once or after spaces, tabs or line breaks: `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `sk-`, `xoxa-`, `xoxb-`, `xoxe-`, `xoxp-`, `xoxr-`, `xoxs-`, `AKIA`, `ASIA`, `AIza`, `eyJ`; so are the first line of a private key and a sign-in header with its value. A run of twenty or more Latin letters and digits is refused when it holds a digit, or a capital letter after its first letter; a run of letters only, small or with one capital at the start, is a word and passes however long it is. So a commit is named by its first seven to twelve digits, never by all forty. A key written in small letters only is not found by this rule; a session holds no key in the first place. A word is exempt from the search for runs only when the whole word is exactly an existing path of the desk's copy, links not followed; a word with a part after `#` or `?` is searched in full. Also refused: a secret after a label when the value looks like one (at least eight characters with a letter and a digit), an address inside a private network, a path of a user's folder on a computer (a root and at least one more part). Addresses that mean "this machine" on every machine (`localhost`, `127.0.0.1`, `::1`, `0.0.0.0`) are not refused.

A refusal names the kind of thing found, never the thing.

No check of text can find a value that is encoded (in hexadecimal, in base64, in any cipher), reversed, written by sound in another script, translated, described, or spread over two answers or over the first letters of lines. The protection against all of these is the first one: the session does not hold the owner's values, and what it is shown is searched for them (see "What a session knows without reading anything").

## What a day may cost

The desk runs on the same subscription as the project's other work, so a flood of items must not be able to use it up. These bounds are in the closed list. Every bound is the largest number that may happen: 10 turns means that an 11th does not start. A day is any 24 hours.

Cost is counted in weighted units. The service reports four counts for every response: tokens of input, tokens written to the cache, tokens read from the cache, tokens of output. A unit is one token of input; a token written to the cache counts 1.25, a token read from the cache 0.1, a token of output 5. These are the ratios of Anthropic's published prices for one model, written in one place in the closed list. That the subscription weighs the four classes as the price list does is an assumption; the relay writes each session's four counts into its record so that the first real days can replace it.

**One turn.** The most a session can hold is the sum of what can enter it: 8,000 tokens for Claude Code's own instructions and the tools, and the standing instructions at 12,000 bytes (together 10,196 tokens measured, with the real instructions of 11,067 bytes), the one message that starts it (at most 4,000 bytes), what the reading calls hand over (48,000 bytes), the short replies of the other tool calls (30 of at most 500 bytes), and its own earlier responses (10 of at most 5,000 tokens): 137,000, counting a byte as a token, which is never too few. The dearest thing a turn can do with it is to write all of it to the cache anew, at 1.25, and to write one full response, at 5: 137,000 × 1.25 + 5,000 × 5 = 196,250 units. The largest files of the repository are read like any other, a part at a time: 400 lines of them are charged what those lines hold, and a part that does not fit in what is left is refused.

The arithmetic checks itself while the desk runs. The first response of a session can take in only Claude Code's own instructions and tools, the standing instructions and the first message: at most 8,000 + 12,000 + 4,000 = 24,000. When a first response reports more input than that, the relay ends the session, tells the coordinator that the desk itself is not working, keeps the arrival, and starts nothing more until the desk is started again.

**One session.** A session is ended at the first response that takes it past 60,000 units, and that response can cost at most one turn's bound. So what is set aside when a session starts is 60,000 + 196,250 = 256,250 units, and a session is charged at most that. A session that ends without a count from the service, or that the relay had to end, is charged all of it. Every session that starts is charged more than nothing.

**The worst day.** A session starts only when the charges of the last 24 hours plus 256,250 are at most 800,000. So what is charged in a day is at most 800,000 units: the day's bound is the worst day itself. The cost of this is that the last quarter of the day's bound is used only by sessions that turn out cheap: with ordinary items the bound on sessions (40) is reached first. Measured in the live check with these bounds in force: each of the two made-up items took 4 turns, one reading call and 6 to 10 seconds; one cost 11,965 units (10 of input, 3,625 written to the cache, 29,133 read from it, 902 of output) and the other 7,170.

What 800,000 units are of the weekly allowance: the repository's capacity record (the pilot of 17 November 2026) has seven counted runs on `claude-sonnet-5-5`, the model the desk runs on, so no scaling between models is needed. Their counts by class were 116 of input, 151,078 written to the cache, 1,068,528 read from the cache and 68,106 of output: 116 + 151,078 × 1.25 + 1,068,528 × 0.1 + 68,106 × 5 = 636,346 units. The record's one figure for the allowance is an upper bound: each run took less than 0.21 of a percentage point of the week. Seven runs took less than 1.47 points, so one point is more than 432,889 units, and 800,000 units are less than 1.85 points. The worst day stays under two points of the week, on the assumption stated above.

Once a day's bound is reached nothing new is started, and the coordinator is told once for that bound; the next digest says, after the vulnerability reports and before everything else, which bound closed the day and which accounts used the most of it, the first three by number. Arrivals wait in the kept list and are offered again, one at a time under the same check, whenever the relay has nothing to start. A place in the list is for one item and one account and holds that account's own arrivals on that item, the newest 10; an account holds at most 5 places and the list 100. What is dropped is counted for each account and listed in the next digest, account by account. A notice that the limit was reached is sent once in a day; it names no account, and none is sent for a held-back account's own arrival or for an arrival on a closed item. The digest says that the list was closed for everyone only when no account could give a place, so that an account that holds nothing would have got none either. An arrival without the account's number, or in the wrong shape, is not handled; it is counted and named in the digest. What is typed in the desk's terminal comes from the coordinator; it is counted and bounded like the rest. The digest's time is looked at before every start of a session, so a queue of sessions does not hold a digest up.

**What the coordinator receives in a day** is at most 48 messages: 10 vulnerabilities, 6 reports that the desk itself is not working, 8 notices that a limit was reached (one for each limit there is), and 24 digests.

**Whose an arrival and a session are.** An account is held back when it gets no session now: it waits after a session that had to be ended, or the sessions it paid for in the last 24 hours that have ended are 8, or those sessions were charged its share of the day's units or more. The session that is running is no part of this, neither as one of the 8 nor with what is set aside for it; what is set aside for it counts toward the day's units from its start, and toward nothing else. One function of the relay says who is held back, and the choice of what starts, the placing of arrivals and what a session's tools are told all come from it. A session whose cost was never written, because the desk was stopped while it ran, counts as one that ended and was charged everything set aside. Seven things hold. The made-up days of the tests begin every run with a fixed opening that brings the desk into each state these seven speak about (each way of being held back; a day closed by sessions and by units; every place taken with and without places of held-back accounts; an arrival for a full list during the session of an account that was charged earlier in the day; a session for two writers and one for ten while an eleventh waits; an answer, a label and a report refused for want of room; an item that closes with other accounts' arrivals kept on it, an arrival on a closed item, an item closed again after it opened; an ended session that read nothing; an arrival during a session, a restart, the clock set back, and the clock set a day or more ahead and put right again), then play 1,500 random steps, and assert after every step of both what is said below under the first five points and the seventh. The random steps are of two kinds, three seeds each: days in which sessions cost what they may, so that the day's units run out, and days of cheap sessions, so that the day's sessions run out and accounts use up their own. The accounts have numbers of nine and ten digits, as on GitHub. Who is held back the made-up days work out by themselves, from the sentence above and the record of what was charged, and compare with what the relay says after every step and while a session runs. They count how often each state was reached, in the opening and in the random steps apart, and fail when one was not. Seven of these states are reached by the opening alone in every run: an account held back by its share of the day's units, a report refused for want of room, an account at its twenty kept reports, an item that closes with other accounts' arrivals kept on it, an arrival for a full list while the place that would go by the rule is in hand, an arrival between two of the relay's steps at the end of a session, and a closed item's line that names fewer accounts than went. For those seven the made-up days are one fixed sequence; every other state is also reached by the random steps of one kind or the other in each of its seeds. After every step the made-up days also look at every line the desk wrote in it, that no number is cut, and at every step in which only a held-back account's own arrivals were dropped, that no notice was sent and no day closed. A session without its mark is not among these states: a test of its own shows that its tools refuse. About a state that is not in that list they say nothing.

1. Nothing that another account writes removes an unhandled arrival of an account that is not held back, with two exceptions and no others. An account that is held back can lose a kept place to an account that is not, when every place is taken. A place holds one account's arrivals, and writing again removes only the writer's own older ones. A place whose arrivals the running session is handling is in hand: it is neither kept for later nor done. It counts toward the hundred and toward its account's five, it does not go while that session runs, by either rule, and it is not among the places its account can give. An account can give the places it holds that are not in hand. The first exception, with these conditions: every place of the list is taken; no account that is held back holds a place it can give; the account that writes holds no place and is not held back; the place that goes is the oldest that can go of the account that can give the most places; and that account can give more than one, so no account loses the last place it can give this way. The second exception: when an item is closed after two sessions in a row that had to be ended, every arrival kept on it goes, whoever wrote it and whether the closing session handled it or not; keeping them would hold one of each writer's five places for seven days. In every case what goes is counted arrival by arrival for the account that wrote it, in one count: a place that goes counts each arrival it held, and each arrival on a closed item counts one. The digest names every such account with its count, and the items its arrivals were on where the line has room. For a closed item it names the item, the day on which it opens again, how many arrivals went and the accounts by number: up to eight, as many as the line holds, and how many more there are. No line of the desk cuts a number: one that does not fit whole is left out. An arrival of a held-back account that is dropped, at its own five places or from a full list, is counted for it and is nothing more: no limit of the day was reached by it, no notice is sent for it, and the day is not said to be closed.
2. While an account is held back, nothing it writes and nothing it holds changes whether or when an item of another account starts, or whether an arrival of another account is kept. The oldest place whose account and item are not held back says which item is next. When every place is taken and a writer that is not held back needs a place and holds fewer than five, a place of an account that is held back goes: the oldest place that can go of the one among them that can give the most, and there the last place an account can give can go too. The writer need not be without places for this. What an account wrote while it was held back and still holds keeps its place and its age: once the account is no longer held back, its item starts in the order in which it was written, before an item that another account wrote later.
3. An account that is held back holds no kept place of another account. What it writes on someone else's item takes one of its own five places, and when it has none left its arrival is dropped and counted against it. When the other account has been handled, that account's place is free.
4. A session has one payer, and whatever a session does is charged only to accounts whose arrivals it handles. The session handles the arrivals of every writer on its item that is not held back, at most ten of them, and its tools are given those accounts and nobody else. The relay marks every session it starts as one for an item or as one for what was typed to the desk. A session without the mark, or a session for an item that was not told its item, whose arrivals it handles or who is held back, does nothing: a list that is missing is not an empty list, and its tools refuse. The session, its units and the wait after it had to be ended go to the payer, the newest of those writers. An answer, a label and a report each go to one account: the newest of those writers that has room for it; when none has room the tool refuses. No count of an account changes in a step in which none of its arrivals was handled.
5. After a session that the relay had to end, only an account whose text that session was shown waits. The reading tool leaves out what an account wrote that is held back at that moment: its comments, and when it is the item's first writer the title, the body and the author's name. It says how many texts are not shown, and it writes down whose text it handed over before it answers. When the relay ends a session, the item waits a day, and the payer waits a day if the session was shown the payer's text; a payer whose text was not shown (the writer of a review, which the desk never reads, or the payer of a session that was ended before it read anything) does not wait, and nobody else waits in any case. What the session costs is the fourth point's matter and does not depend on this: the payer is charged one of its sessions of the day and everything that was set aside, whether or not its text was shown.
6. How many outside accounts it takes to close a day is worked out by a test from the closed list, over every mixture the rules allow (sessions that end by themselves, as cheap and as dear as they can be, sessions that the relay has to end at the worst case, and both together), and the numbers in the table below are that test's numbers.
7. One outside account alone never closes a day, for any bound. The start command refuses a closed list in which one could; one in which the limits that one account alone can reach (the sessions of its own item, its own arrivals past its places, its own answers, its own kept reports) would be all the notices of a day; and one that closes an item after fewer than two sessions.

| --- | --- |
| A day's sessions | 5 |

Two accounts can close a day's units, and that is not forced further. A session that the relay has to end is charged everything that was set aside for it, 256,250 units, which is nearly a third of the day; two accounts with such a session each, and 31,251 units more between them, leave no room to set aside a third. Without the share of the units for one account, one account did it alone: sessions just under the bound of one session and then one that had to be ended. In two tries on the real program text alone did not get a session ended. The room for kept vulnerability reports, 80 in a day, cannot be filled: a session writes at most one, no account has a cap of its own there, and the reports of 24 hours come from at most 41 sessions: the 40 that a day has, and one that started just before and was still running, because sessions run one at a time. Should a vulnerability report arrive with the room full all the same, it is not kept and not sent: the tool refuses it, the answer then says that the desk could not pass it on and that the item stays open, the refusal is counted for the next digest, and the coordinator is told once that the limit was reached. When the vulnerability reports that are sent at once are used up for the day, further ones wait for the next digest and are not lost. When the day is used up nothing is lost: arrivals are kept up to the caps, the coordinator is told, the items stay open on GitHub and are read later. And the owner's allowance is not touched beyond the day's bound: that bound is all the desk can spend, whoever writes.

**The start and the end of a session are one step each.** This is a property of its own. The list of kept arrivals, the record of sessions, which session is running and which places are in hand are shared by the arrivals that the watcher reports and by the sessions that the relay starts, and one lock of the relay guards them: placing an arrival, choosing what starts, starting a session and ending one each take it, and none of them reads or changes any of the four without it. The lock is held for the steps around a session and never for the length of one. At a session's start, reading the list, choosing, counting the session and taking its places in hand are one step. At its end, taking the handled places out of the list, writing what the session cost, taking out what is kept on its item if the item closed, and clearing what is in hand and which session runs are one step. At no moment at which an arrival can be placed or a session chosen does the relay count a session as ended while one of its places is in hand, or as running while none of its places is in hand. On disk the handled places go before the cost is written: a stop between the two leaves a session without a cost, which counts as ended and charged everything set aside, and never an arrival that was handled and is handled again. The tools of a session are another process: they change the record under the record's own file lock and not under the relay's lock. What they write there is what the session sent, labelled and reported; they never write or change the entry of a session, an item's closing or the kept list, and the only thing their look at the record does to the sessions is to drop entries that are older than a day, as every look does. So nothing they write while a session runs changes who is held back, what is placed or what is chosen. One thing can wait under the relay's lock: when a start finds a bound of the day reached, the notice of it is delivered inside the step. A delivery is given 60 seconds at most, and at most 8 such notices are sent in a day, each bound once; an arrival that comes meanwhile is placed when the step is over. A test plays an arrival and a choice at every point between two of these steps, each point by its name.

What remains of this, said plainly. What the second point costs: an account that is held back, also one that has only had its eight sessions of the day, loses the arrivals it has kept when every place is taken and others write, its last place too, and to writers that already hold places as well as to newcomers. The digest names the account, how many of its arrivals went and, where the line has room, the items they were on, so that the coordinator can find them; the desk does not come back to such an item until someone writes on it again, and the item stays open on GitHub. An account in the last session it may have that day is not held back until that session ends, so what it writes during those minutes is placed like the writing of any account that is not held back, and a moment later its places are those of a held-back account. A place in hand does not go and is not among the places its account can give, so for the length of one session up to ten places of a full list cannot give way: while no session runs it takes 100 accounts to close the list to an account that holds nothing, and while a session runs that handles the arrivals of 10 accounts it takes 90, ten that hold two places each, one of them in hand, and eighty that hold one. When that session ends the list is open to a newcomer again. Stopping the desk while a session runs costs that session's payer: the payer is charged everything that was set aside, what the session was handling was not handled and stays kept, and if that charge holds the payer back, the place goes first when every place is taken, its last too. The desk is to be stopped between sessions. What an honest reader loses by the fifth point: while an account is held back, a session for someone else's arrival on the same item does not see what that account wrote. When it is the item's first writer, the session answers a comment without the question it belongs to; it is told that a text is not shown and says so, and the item is read again when that account is handled. A text that got a session ended stays on its item when its writer's day of waiting is over, so the next writer on that item can be the payer of a session that is ended for it; that is why the second such session in a row closes the item. A closed item opens again by itself 7 days after the session that closed it, by the desk's clock, and its count then stands at one: the first session after that which has to be ended and was shown its text closes it for another 7 days. So a text that gets sessions ended costs two payers a day of waiting each, and after that one payer a day of waiting in a week. A writer that is not held back and writes on a busy item can make the session dearer for the payer; when that writer wrote last, it is the payer itself. The reading tool reads the newest one to two hundred comments of an item and shows the newest 8 of those that are left after the leaving-out, so an item with more comments than that is not read whole. So two accounts, each the payer of a session that had to be ended, can close one item to the desk for 7 days; the digest names the item and the day, and the coordinator reads it meanwhile. A session that had to be ended counts toward the two only when it was shown text of that item; one that was ended before it read anything says nothing about the item and does not count, though the item still waits its day. A session that was not ended begins the count anew. Beyond that the count does not ask why: two sessions in a row that read the item and then ran out of time because the service was slow close it as well.

**The desk's clock.** The desk's time never goes back: it is the latest time the desk has seen, kept in its record. While the computer's clock is behind that, the desk's time stands still, so that nothing that was counted ends early and no new day begins; when the clock has caught up, time moves on. A clock that was set far ahead and put right again therefore holds the desk's limits where they are until the real time has caught up. Only the hour between two digests is kept by the computer's clock, in either direction, so that a clock set back does not hold a digest up. The entry of the session that is running is not dropped from the record, however far the clock is set ahead; it is written at its end.

## What a session knows without reading anything

Claude Code itself tells every session a few things. After every run of the live check, everything the session was shown (the whole stream the relay reads: refusals of the check, failing tools, refused answers, results) is searched for the known values in reduced form, and none may be found; the record holds what Claude Code shows of a check that refused and of a tool that failed, word for word. In every run but one, every known value is searched for. The one is the run that asks the session to write down what it knows, when the check runs on the owner's sign-in: there the session holds what that sign-in shows about the account (the address, and with it a name of an organisation or a display name) and writes it down, so that is taken out as it is written before the search, and a value that is a part of it (the account name inside the address) is not searched for, because it cannot be told from the address when the session spells the address its own way. The row of that run in the record names both. On a sign-in of the desk's own nothing is taken out and nothing is left unsearched: anything the sign-in shows that is found in the stream fails the run. That is the run to make before a way in is opened (`check_lock.py --claude-token` with the desk's own sign-in); it has not been made yet. The check makes a copy of that sign-in in its own temporary folder for the time of its runs, because the start command looks for it in the state folder; the copy is taken away when the check ends, however it ends (passed, failed, interrupted, with its folder kept), and nothing the check keeps holds the sign-in: a stream that held it is kept with a fixed word in its place, and the check fails. One ending cannot be caught: a kill that no program can answer (the kill signal, loss of power) leaves the copy in the check's temporary folder, and whoever ran the check then removes that folder by hand. The check keeps the stream of every run in a folder of its own beside the desk's default state folder, closed to other accounts and never in the repository, so that a hit can be looked at. Once, before streams were kept, the search of that one run found the account name with the address taken out as written; eight repeats with the stream kept did not find it again, and the cause was not seen. The live check also asks the locked session once what it knows and compares the answer with the real values on this computer; the values themselves are recorded nowhere. The record of the live run is older than the mark that says what kind a session is: the two sessions that the check starts without the relay get that mark through the relay's own function, and the next live run shows it. The live check runs on the owner's sign-in, with made-up data and no way to the outside, so its record shows the address in the session; with a way open the desk runs only on a sign-in that shows none.

## Not enforced yet

- The limits on connection codes (how often a code works, for how long, how many for one author in a day) and on live sessions at once are in the file of facts, but no tool keeps them: the live-session tools hand out a code on every call. Until a tool does, the start command refuses to start with that way open.
- A reply in a live session goes out through the live-session tool, not through the answering tool. It therefore lacks what an answer has: the first line that names the AI desk, the limits on answers, the cap on length, the field that says whether the project's agents were told, and the exemption for paths of the copy and for public values. Of the check on text that leaves it gets the part that runs before every tool call (characters that are not on the list, known values, shapes), nothing more.
- For a live session, the conversation with one connected session is to stay one session in which no GitHub item is handled. The relay does not run live sessions yet, and the bounds on spending do not cover them.

## Stated limits

- The lock is what the start command builds. A session started in the desk's folder any other way is an ordinary session, and whoever can type into the desk's terminal gives the desk instructions, inside the closed list. The folder and the terminal are therefore the owner's to keep.
- One account cannot use up the day's answers for everyone, but many accounts together can. When that happens the tools tell the coordinator once, and the desk answers again the next day.
- Several accounts acting together can still get more answers on one item than one account could: each brings its own five a day, up to the limit for one item in an hour and the limit for everyone in a day.
- The bounds on what a session may cost rest on Claude Code doing what its two switches say (the bound on turns, the bound on the size of a response) and on the service's counts. Both switches were seen to refuse on the pinned version. When a session costs more than was set aside for it, the relay tells the coordinator at once.
- The same holds for spending, with the numbers under "Whose an arrival and a session are": five accounts together use up a day's sessions, and two accounts a day's units. The desk then waits. That is the purpose of the bounds; the cost is that a real question arriving in a flood waits with the rest or, when the kept list has no room for it, is dropped, counted and named in the digest, and has to be found by the coordinator.
- Whoever can change folders on this computer is outside what the lock stops; the tools and the relay refuse a state folder that is reached through a link, each time they use it, and nothing more.

## What the lock does not do

- It does not judge what an answer says. A wrong answer, a promise or a detail that should not be public is still a matter of the standing instructions.
- The check on text that leaves lets through only the characters the desk writes with and finds a known value in the four forms stated above. A value that is encoded, reversed, written by sound in another script, translated, described, or spread over two answers or over the first letters of lines is another text to it. That is why the first protection is that the session does not hold the value at all.
