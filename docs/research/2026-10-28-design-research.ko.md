# 도담 설계 조사 (2026-10-28)

- 목적: 도담 설계의 근거를 남긴다. 소유자 요구는 네 가지다. 보안은 무조건 지킨다. 사람이 볼 필요 없이 AI에 극단적으로 맞춘 언어를 만든다. 중복 코드가 없어야 한다. 데이터가 각자 놀면 안 된다.
- 방법: 네 갈래를 AI 조사 에이전트가 원문(논문 · 공식 문서)을 열어 정리했다. 표시는 세 가지다. [원문]은 원문을 읽었다는 뜻이고, [2차]는 다른 글을 거쳐 봤다는 뜻이며, [미확인]은 열지 못했다는 뜻이다.
- **✔**는 원문을 다시 열어 수치를 직접 확인한 항목이다.
- 2026년 논문 다수는 동료 심사 전 사전 공개본(preprint)이다. 업체 보고서(Veracode · GitClear)는 방법이 공개 논문만큼 검증되지 않았다.

## 요약 — 설계에 반영한 것

| 요구 | 가장 강한 근거 | 설계에 반영한 것 |
|---|---|---|
| AI 극강 최적화 | 생성 중 컴파일러 피드백으로 컴파일 실패 65.9% → 13.1%. 낯선 관례(1부터 세기)는 GPT-4 정확도를 87.4 → 68.2로 떨어뜨렸다 | 쓰는 중인 코드도 검사되는 문법, 에러마다 쓸 수 있는 대안 나열, 널리 쓰는 관례 유지, 검증된 예제 모음 |
| 중복 없음 | 5줄 이상 중복 블록을 담은 커밋 0.70% → 6.66%. 시그니처 · 계약 목록을 주면 재사용 30.0% → 67.8% ✔ | 이름만 다른 같은 정의는 컴파일 에러, AI 도구가 소스 대신 함수 목록과 비슷한 정의 찾기를 제공 |
| 데이터가 각자 놀지 않음 | 앱 코드로 한 무결성 검사는 동시 실행에서 깨진다. 스키마 우선 도구도 실행 중 어긋난다 | 데이터는 한 번만 정의하고 한 곳이 소유한다. 스키마 · 검증 · 마이그레이션 · 동기화는 컴파일러가 만든다 |
| 보안은 무조건 | 모델이 새로워져도 보안 통과율은 45~56%에 머문다. 접근 제어 실패는 대부분 레코드 단위다 | 데이터별 접근 정책, 권한 범위, SSRF 차단, 자원 한도, 비밀번호 · 암호 타입, 보안 보고서 형식 |

## AI가 정확하게 짜는 언어의 조건

**타입은 힌트가 아니라 검사기로서 효과가 있다.** MultiPL-E(TSE 2023, https://arxiv.org/abs/2208.08227)에서 Codex는 타입 표기가 있든 없든 성적이 같았다(p=0.33, 0.23). TypeScript 시그니처 타입을 `any`로 바꾸면 2.5% 떨어졌다(p<0.001). [원문] → 시그니처 타입은 정확해야 하고 `any` 같은 탈출구는 없어야 한다.

**컴파일 에러는 대부분 타입 · 이름 에러다.** TypeScript 컴파일 에러의 94%가 타입 검사 실패였고 문법 에러는 6%였다(PLDI 2025, https://arxiv.org/abs/2504.09246). Rust 저장소 번역에서 가장 많은 에러는 없는 메서드(4,079건), 없는 이름(2,095건), 타입 불일치(1,035건)였다. 빌림 에러가 아니라 지어낸 API다(RustRepoTrans, https://arxiv.org/abs/2411.13990). [원문] → 작고 규칙적인 표준 라이브러리와 이름 해석에 힘을 쓴다.

**컴파일러 피드백이 가장 큰 지렛대이고, 생성 중 검사가 끝난 뒤 검사보다 낫다.** Generative Compilation(2026-07, https://arxiv.org/abs/2607.13921)은 Rust 저장소 단위 과제를 최신 모델 7개로 돌렸다. 피드백이 없으면 평균 65.9%가 컴파일되지 않았고, 생성 뒤 피드백으로 20.7%, 생성 중 피드백으로 13.1%까지 내려갔다. CRUST-Bench(https://arxiv.org/abs/2504.15254)에서 o3는 한 번에 19%, 컴파일러로 고치면 31%, 테스트로 고치면 48%를 통과했다. 고치는 효과는 2~3번 뒤 평평해진다(FeedbackEval, https://arxiv.org/abs/2504.06939). [원문] → 미완성 코드를 빠르게 검사하고, 근본 원인부터 적게 보고한다.

**진단은 형식보다 내용이다.** 진단을 고치자 성공이 50번 중 14번에서 36번으로 늘었고, 효과의 대부분은 쓸 수 있는 대안을 나열한 데서 나왔다. 산문과 JSON은 비슷했다(Ray & Goyal 2026, https://arxiv.org/abs/2607.14167 — 컴파일러가 아니라 글 기반 게임 TextWorld의 실험). [원문, 초록만] → 에러마다 그 자리에 쓸 수 있는 이름 · 기대 타입 · 맞는 메서드를 나열한다.

**낯선 관례는 크게 해친다.** Python을 1부터 세게 바꾸자 GPT-4의 HumanEval 정확도가 87.4에서 68.2로, 인덱싱이 중요한 문제에서는 82.5에서 40.5로 떨어졌다(NAACL 2024, https://arxiv.org/abs/2307.02477). 같은 문제가 Python · JS에서는 100%, 난해 언어에서는 0~11%였다(EsoLang-Bench, https://arxiv.org/abs/2603.09678). 테스트로 검증한 번역 코드로 미세조정하면 Racket · OCaml 점수가 약 2배가 됐다(MultiPL-T, OOPSLA 2024, https://arxiv.org/abs/2308.09895). [원문] → 널리 쓰는 관례는 바꾸지 않는다. 검증된 예제 모음을 만든다.

**학습 데이터가 적은 언어도 최신 에이전트는 다룬다.** SWE-AGI(2026-02, https://arxiv.org/abs/2602.09447)는 학습 데이터에 없게 하려고 MoonBit으로 1천~1만 줄 과제를 냈다. gpt-5.3-codex가 22개 중 19개, claude-opus-4.6이 15개를 풀었다. 병목은 쓰기가 아니라 코드 읽기였다. [원문, 초록만] → 파일 하나 · 함수 하나만 읽어도 이해되게 하는 설계와 코드 조회 도구가 중요하다.

**토큰 효율은 작은 이득이다.** 언어별 토큰 차이는 최대 2.6배였다(Alderson 2026 블로그 — 연구가 아니다, https://martinalderson.com/posts/which-programming-languages-are-most-token-efficient/). AI용으로 다시 만든 Python 문법(SimPy)은 토큰을 10.4~13.5% 줄였지만, 정확도는 작은 모델을 미세조정한 뒤에만 유지됐다(https://arxiv.org/abs/2404.16333). [원문] → 익숙함을 버리고 10%를 아낄 가치는 없다.

**Rust 소유권은 첫 시도를 어렵게 하지만 고치면 대부분 회복된다.** 같은 문제에서 컴파일에 실패한 수는 Rust 23,416, C 12,304, C++ 9,953, Java 6,996이었다(약 3.3배). Rust 컴파일 에러 가운데 소유권 · 수명은 16.7%였고 import 누락이 20.5%였다(Nogueira 등, ISSRE 2026, https://arxiv.org/abs/2608.00661). [원문 ✔] GPT-4는 Rust 에러 예시의 92%, Stack Overflow 조각의 74%를 고쳤다(RustAssistant, ICSE 2025, https://arxiv.org/abs/2308.05177). 수정 루프로 빌림 에러가 75% 줄었다(CRUST-Bench). [원문] → 수정 루프가 빠르면 소유권은 감당할 만하다. 위험한 것은 시그니처에 적는 수명 표기다.

**GC · 참조 카운트 · 값 의미론을 AI 관점에서 비교한 연구는 없다.** Swift ARC · Hylo까지 찾았지만 없었다. [미확인 — 공백] → 2027년 1~2월 도담 시제품 비교가 첫 자료가 된다.

**AI용 언어들은 방향이 같고, 통제된 결과를 낸 곳은 없다.** [원문]
- MoonBit(https://www.moonbitlang.com/blog/moonbit-ai): 최상위 타입 시그니처가 필수다. 생성하면서 문법 · 타입을 검사하고 되돌리는 샘플러를 쓰며 부하는 약 3%다. 컴파일 성공률 향상은 그림으로만 보였다.
- Vercel Zero(2026, https://github.com/vercel-labs/zero): 프로그램을 의미 그래프로 저장하고, 쓰기 전에 검사하며, 권한이 명시적이다. 결과는 공개하지 않았다.
- NanoLang(2026, https://github.com/jordanhubbard/nanolang): 함수마다 테스트 블록, 경계에 타입 필수, 참조 카운트를 쓴다. 측정 자료가 없다.
- → 벤치마크로 숫자를 내는 것이 도담의 차별점이다.

**제약 디코딩을 쓰려면 코드의 모든 앞부분이 검사 가능해야 한다.** [원문]
- 타입 제약 디코딩(PLDI 2025): 컴파일 에러가 HumanEval에서 75.3%, MBPP에서 52.1% 줄었다. 첫 시도 정답률은 상대적으로 3.5~5.5% 올랐고, 수정 성공은 37% 올랐다.
- 다만 TypeScript에서 선언 전 사용, 반환 타입 추론, 타입 없는 `let x;`는 빼야 했다.
- Generative Compilation은 뒤에 쓸 코드에 달린 에러를 꺼야 했다.
- 문법 제약(SynCode, https://arxiv.org/abs/2403.01632)으로 문법 에러가 96.07% 줄었다. 모니터 유도 디코딩(https://github.com/microsoft/monitors4codegen)으로 컴파일률이 19~25% 올랐다.
- 단, 닫힌 API는 토큰 확률을 주지 않는다. 엄격한 문법 제약이 추론을 해친다는 결과도 있다(CRANE, ICML 2025).
- → 선언이 먼저 오고, 매개변수 · 반환 타입은 필수이며, 표준 파서로 읽히는 문법을 공개한다.

**계약 검증은 Dafny식 SMT가 실용 단계에 가깝다.** [원문]
- 성공률은 Dafny 82.2%, Verus 44.2%, Lean 26.8%였다(Vericoding, https://arxiv.org/abs/2509.22908).
- Dafny 검증만 보면 68%(2024-06)에서 96%로 올랐다.
- AutoVerus는 90% 넘게 성공했다(https://arxiv.org/abs/2409.13082). Lean은 끝까지 푼 것이 161개 중 최대 1개였다(CLEVER, https://arxiv.org/abs/2505.13938).
- 모델은 `assume(false)`, `sorry`, `ensures true`로 속인다.
- → Dafny식 검증을 쓰고, `assume`과 자명한 사후조건은 컴파일러가 거부한다.

**실행되는 속성 테스트가 정확도를 올린다.** 속성 기반 테스트 피드백은 테스트 주도(TDD) 방식보다 첫 시도 정답률을 상대적으로 23.1~37.3% 더 올렸다(PGS, https://arxiv.org/abs/2506.18315). [원문, 초록만] → 속성 테스트를 처음부터 둔다.

## 중복 코드

**AI 도구가 퍼지면서 정확히 같은 중복 블록이 크게 늘었다.** GitClear 2025 보고서(https://www.gitclear.com/ai_assistant_code_quality_2025_research)는 2020~2024년 변경 2억 1,100만 줄을 봤다.
- 5줄 이상 중복 블록을 담은 커밋: 0.70%(2020), 0.45%(2022), 1.80%(2023), 6.66%(2024)
- 복사 · 붙여넣기한 줄은 8.3%에서 12.3%로 늘고, 옮긴 줄은 24.1%에서 9.5%로 줄었다.
- 한 회사 자료의 연도별 상관이고, 줄마다 AI가 썼는지 가려낸 것은 아니다.

[원문 — 보고서 PDF]

**에이전트는 있던 코드를 다시 만들고, 테스트는 그걸 못 잡는다.** [원문 ✔]
- RepoReuse(2026-09, 사전 공개본, https://arxiv.org/abs/2609.35357): 5턴째 과제 사슬의 50.8%에 중복 로직이 남았는데, 통과율은 거의 그대로였다.

| 앞 턴 코드를 주는 방식 | 자기 재사용 | 중복 |
|---|---|---|
| 주지 않음 | 30.0% | 65.1% |
| 함수 시그니처 · 계약 목록 | 67.8% | 46.7% |
| 전체 소스 | 29.2% | 70.7% |

- 한계: 모델 하나(Qwen3.7-plus)와 사슬 75개뿐이다. 목록 조건은 재사용을 권하기도 해서 두 요인이 섞여 있다.
- Huang 등(MSR'26, https://arxiv.org/html/2601.21276v1): crewAI의 코드 변경 요청(PR) 617개에서 중복도가 에이전트 PR 0.2867, 사람 PR 0.1532였다(p<0.001). [원문]
- → 테스트로는 중복이 잡히지 않는다. 컴파일러가 막고, AI 도구 연결 서버(MCP)로 소스 대신 인터페이스 목록을 준다.

**반대 증거도 있다.** CMU(MSR'26, https://arxiv.org/html/2511.04427v3)는 Cursor를 쓴 저장소 806개와 대조군 1,380개를 비교했다. 정적 분석 경고는 30.26%, 복잡도는 41.64% 늘었다. 중복 줄 밀도는 7.03%(±4.79%) 늘었지만 유의하지 않았다. [원문] → 중복은 가정하지 말고 잰다.

**중복은 실제 버그를 만들지만, 억지 추상화도 비용이 든다.** [원문]
- Juergens 등(ICSE 2009, https://arxiv.org/pdf/1701.05472): 복제의 52%가 일관되지 않게 바뀌었다. 그중 28%가 의도하지 않은 것이었고, 의도치 않은 변경의 1/2~1/3이 결함이었다.
- Kapser & Godfrey(2008): Apache · Gnumeric 복제의 최대 71%는 유지보수에 좋다고 판단됐다.
- → 확실한 중복만 막고, 비슷한 코드를 억지로 합치게 하지 않는다.

**Unison은 이름 · 문법만 다른 같은 정의를 하나로 본다.** [원문, 덧셈 순서 예만 2차]
- 정의마다 이름을 지우고, 변수를 위치로 바꾸고, 의존을 해시로 바꾼 구문 트리를 512비트 SHA3로 해시한다(https://www.unison-lang.org/docs/the-big-idea/).
- 문법만 다른 같은 함수는 "같은 정의의 별칭"으로 보고한다. 거부하지는 않는다.
- `y + x + 1`과 `x + y + 1`은 해시가 다르다.
- 같은 모양 타입을 하나로 보는 구조적 타입 때문에 Suit와 Direction이 섞이는 문제가 생겨서, 기본값이 이름으로 구분하는 타입이 됐다(https://unison-lang.org/docs/language-reference/unique-types).
- → "정규형(이름을 지우고 문법 설탕을 푼 꼴)이 같은 정의"는 에러로 막고 기계적으로 고칠 수 있다. 데이터 타입은 기본적으로 이름으로 구분한다.

**정규형 해시에는 한계가 있다.** [원문]
- Dhall은 튜링 완전하지 않아서 완전히 정규화한 뒤 해시할 수 있다(https://docs.dhall-lang.org/discussions/Safety-guarantees.html).
- 이름 바꿈까지 무시하는 부분 트리 해시가 O(n log² n)에 가능하다(PLDI 2021, https://arxiv.org/abs/2105.02856).
- LLVM MergeFunctions는 구조가 같은 함수를 합친다(https://llvm.org/docs/MergeFunctions.html).
- → 도담은 튜링 완전이라 완전 정규화는 불가능하다. 정해진, 반드시 끝나는 재작성 규칙만 적용한 뒤 해시한다.

**복제 종류에 따라 검출 가능성이 갈린다.** [원문]
- BigCloneBench(ICSE'16, https://arxiv.org/pdf/1512.06448) 재현율: 완전히 같은 복제는 60~100%였고, 많이 고친 복제와 동작만 같은 복제는 모든 도구가 0~1%였다.
- 정밀도는 SourcererCC 91%, NiCad 89~96%였다.
- 동작만 같은 복제는 일반적으로 판정할 수 없다(라이스 정리).
- SourcererCC 일괄 검사는 100만 줄에 1분 30초가 걸렸다.
- → 완전히 같은 복제는 에러, 조금 고친 복제는 경고, 동작만 같은 복제는 범위 밖이다. "한 파일 고친 뒤 1초 안에 다시 검사" 목표를 지키려면 점진 해시 색인이 필요하다.

**"함수로 뽑아 재사용"이 늘 가능하게 언어를 설계할 수 있다.** 완전히 같은 복제 중 안전하게 함수로 뽑을 수 있는 것은 69.3~85.6%였다. 막는 이유는 반환 값이 여럿(49%), 반환 타입이 다름(30%), 조건부 반환(16%), 루프 밖 break/continue(5%)였다(Tsantalis 등, TSE 2015). [원문] → 튜플 · 식 기반 제어 흐름 · `Result`가 있으면 추출 수정을 기계적으로 할 수 있다.

**진단 선례가 있다.** rustc는 수정안에 자동 적용 가능 여부를 표시한다(`MachineApplicable` · `MaybeIncorrect` 등, https://rustc-dev-guide.rust-lang.org/diagnostics.html). Go는 쓰지 않는 변수 · import를 컴파일하지 않는다. [원문]

**데이터 모양은 한 번만 정의할 수 있다.** Zod는 검증기에서 타입을 추론한다. CUE는 데이터 · 스키마 · 검증 · 정책을 한 언어로 쓴다. [원문] → 도담은 매크로 · 리플렉션이 없으므로, 검증 · DTO · 직렬화를 컴파일러가 타입 하나에서 만든다.

## 데이터가 각자 놀지 않게

**서버와 화면을 한 언어로 쓰는(tierless) 언어는 DB를 직접 가질 수 있다.** Ur/Web(POPL 2015, http://adam.chlipala.net/papers/UrWebPOPL15/UrWebPOPL15.pdf)은 이렇게 한다. [원문]
- 컴파일러가 DB 스키마를 만들고, 앱이 시작할 때 DB와 맞는지 검사한다.
- 원격 호출마다 직렬화 트랜잭션으로 돌고, 충돌하면 자동으로 다시 시작한다.
- 클라이언트로 가는 메시지는 커밋할 때만 나간다.
- 다른 DB 사용자는 이 추상을 지키지 않아도 된다고 논문이 인정한다.

**외래 키를 타입으로 검사할 수 있다.** Ur/Web의 테이블 타입은 키를 담는다. 선언된 키만 외래 키 대상이 되고, `set null`은 option 열에서만 타입 검사를 통과한다(Ur/Web 매뉴얼). [원문]

**질의를 타입 있는 일반 코드로 쓰고, SQL 하나로 바뀜을 보장할 수 있다.** Links는 한 소스에서 JavaScript · 서버 코드 · SQL을 만든다. Cheney · Lindley · Wadler(ICFP 2013)는 질의가 언제 SQL 하나가 되는지 증명했다. LINQ는 같은 질의를 수많은 질의로 쪼개 보냈다. [원문] → 목록 하나를 읽으려고 질의를 줄마다 하나씩 더 보내는 문제(N+1 질의)를 컴파일러가 막을 수 있다.

**tierless 언어가 주류가 못 된 이유.** ACM Computing Surveys(2020) 리뷰에 따르면 다음 문제가 있었다. [원문]
- 웹 클라이언트-서버만 다뤘다.
- 일관성 수준이 하나뿐이었다.
- Ur/Web은 분리 컴파일이 없다.

주류는 원격 호출(RPC)만 가져갔다. React 문서는 "Server Function의 인자는 전적으로 클라이언트가 정한다"고 경고한다. → 분리 · 점진 컴파일을 지켜야 컴파일 속도 목표를 지킨다.

**스키마 우선 도구도 실행 중에 어긋난다.** Prisma는 계약 해시가 DB와 달라도 경고만 하고 질의를 실행하며, 실패하게 만들 수 없다. `relationMode="prisma"`에서는 "잘못된 데이터를 만들 수 있다"고 문서에 적혀 있다. [원문] → 어긋나면 멈춘다. 관계를 앱 코드로 흉내 내지 않는다.

**Convex는 결정적 함수로 무엇이 가능한지 보여 준다.** [원문] → 도담은 숨은 동작(전역 가변 상태 · 예외)이 없어서 같은 결정성을 얻는다.
- 기존 문서가 하나라도 안 맞으면 스키마 반영이 실패하고, 모든 쓰기를 검증한다.
- 함수가 결정적이라 직렬화 낙관 트랜잭션을 스스로 다시 돌린다.
- 질의가 읽은 범위를 추적해 구독을 갱신하고, 한 클라이언트의 질의는 모두 같은 시점을 본다.

**Zero는 스키마를 하나 더 둔다.** [원문] → 컴파일러 하나가 모든 층을 내면 사본이 사라지고 배포 순서도 컴파일러가 정할 수 있다.
- 스키마가 백엔드 스키마에서 생성한 별도 TypeScript 파일이다.
- 어긋남은 실행 중에만 발견되고, 기본 동작은 페이지 새로고침이다.
- 배포 순서는 사람이 지켜야 한다. 추가할 때는 DB → API → 클라이언트, 삭제할 때는 그 반대다.

**통합 스택은 사업으로 힘들었다.** ElectricSQL은 2024년 재작성에서 핵심을 읽기 동기화로 줄였다. Gel(옛 EdgeDB)은 회사를 닫고 팀이 Vercel로 갔으며, Gel Cloud는 2026-01-31에 닫혔다(2025-12-02 글, https://www.geldata.com/blog/gel-joins-vercel). [원문 ✔] → PostgreSQL 위에 짓고 읽기 동기화부터 한다.

**Gel의 타입 있는 링크는 따라 할 만하다.** 링크마다 `on target delete`(restrict · delete source · allow · deferred restrict)를 선언하고, 역링크는 계산된다. 마이그레이션은 전체 스키마를 비교해 만들고, 애매하면 사람에게 묻는다. [원문] → AI는 대화형 질문에 답할 수 없으므로, 이름 바꿈/삭제 같은 애매함은 소스에 적는다.

**저장소 타입은 언어 타입이어야 한다.** Datomic은 쓰기가 직렬화되고, 속성 타입을 바꿀 수 없으며, 불변식을 깨는 스키마 변경은 중단된다. Dark 로드맵은 저장소 "스키마는 당연히 타입이어야 한다"고 적었다. [원문]

**파생 데이터는 선언하고 시스템이 유지할 수 있다.** [원문]
- DBSP(PVLDB 2023)는 관계 대수 · 집계 · 재귀까지 점진적으로 유지한다.
- Differential Dataflow는 1천만 노드 그래프의 변경 하나를 약 230µs에 처리했다.
- Materialize는 기본이 Strict Serializable이지만, 뷰가 따라잡을 때까지 읽기가 기다릴 수 있다.
- Noria의 뷰는 결국 일관성만 준다.
- Salsa는 완전히 결정적인 프로그램을 가정한다.

**스키마는 계속 바뀌고, 컴파일러가 마이그레이션을 강제한 선례가 있다.** [원문] → Lamdera가 컴파일러 강제 마이그레이션의 가장 가까운 선례다.
- MediaWiki는 4.5년 동안 스키마가 171번 바뀌었고, 옛 질의의 약 22%만 유효하게 남았다(Curino 등 2008).
- Lamdera 컴파일러는 배포판마다 타입 스냅숏을 남기고, 바뀐 핵심 타입의 마이그레이션을 요구한다. 스스로 못 푸는 곳은 `Unimplemented` 자리표시로 남겨 채우게 한다.
- Stripe는 2011년부터 모든 API 판을 유지한다.

**앱 코드로 한 무결성 검사는 실패한다.** [원문] → 불변식은 DB 제약이나 직렬화 트랜잭션으로 지킨다.
- Rails 앱 67개에서 앱 수준 검증이 트랜잭션보다 37배 넘게 많이 쓰였다. 삽입 때 유일성 검사와 삭제 때 외래 키 검사는 동시 실행에서 안전하지 않다(SIGMOD 2015, http://www.bailis.org/papers/feral-sigmod2015.pdf).
- 웹 앱 8개에서 손으로 짠 트랜잭션 91개 중 53개에 정확성 문제가 있었다(SIGMOD 2022).

**서버와 조정 없이 안전한 쓰기는 판정할 수 있다.** [원문]
- 조정 없이 지킬 수 있는 불변식을 가려내는 방법(invariant confluence)으로 TPC-C New-Order가 25배 빨라졌다(https://arxiv.org/abs/1402.2237).
- 로컬 우선 소프트웨어에는 정본 "현재" 스키마가 없다(Kleppmann 2019).
- Replicache는 서버 상태로 되감고 대기 중인 변경을 다시 적용하므로, 예약 같은 쓰기가 재적용 때 실패할 수 있다.

## 보안

**모델이 새로워져도 보안은 제자리다.** [원문, 업체 보고서] → 더 좋은 모델을 기다릴 수 없다. 컴파일러가 막아야 한다.
- Pearce 등 2021: 프로그램의 약 40%가 취약했다.
- Veracode 2025-07: 45%가 불안전했고, Java는 70% 넘게 실패했다.
- Veracode 2026-03: 문법 정확도는 95%를 넘었는데 보안은 약 55%였다.
- Veracode 2026-07: 평균 56%, 최고는 GPT-5.5의 68%였다. 모델 크기에 따른 이점은 없었다.

**실제 저장소 · 에이전트 과제는 더 나쁘다.**
- BaxBench(ICML 2025, https://arxiv.org/abs/2502.11844): 백엔드 과제 392개에서 최고 모델 o1의 정확도가 62%였고, 정확한 프로그램의 약 절반이 공격에 뚫렸다. [원문 ✔]
- SusVibes(https://arxiv.org/abs/2512.03262): 기능은 57% 정확했지만 안전한 것은 11.8%였다.
- SecureForge(https://arxiv.org/abs/2605.08382): 안전한 코드를 명시적으로 요청해도 23%가 취약했다. [원문]
- → 벤치마크에는 기존 저장소 수정 과제와 실제 공격 테스트가 필요하다.

**많이 뚫리는 것은 출력 인코딩 · 자원 고갈 · 자격 증명이다.** [원문]

Veracode 2026 종류별 통과율:

| 종류 | 통과율 |
|---|---|
| SQL 인젝션 | 82~83% |
| 암호 | 86~87% |
| XSS | 약 15% |
| 로그 인젝션 | 12~13% |

BaxBench(보안 요청 없음) — 해당되는 경우, 정확한 백엔드 중 약점이 있던 비율:

| 약점 | 비율 |
|---|---|
| 로그 인젝션 | 0.91~1.00 |
| XSS | 0.70~0.96 |
| 자원 고갈 | 0.30~0.61 |
| 자격 증명을 안전하지 않게 저장 | 최대 0.55 |
| SQL 인젝션 | 최대 0.14 |

→ HTML · 로그 출력 지점이 안전한 타입만 받게 하는 규칙은 가장 나쁜 두 종류를 겨눈다. 자원 고갈과 자격 증명 저장은 지난 판 설계에 없던 빈 곳이다.

**타입으로 막은 출력은 실적이 좋다.** Google Trusted Types를 적용한 서비스 130개 넘게에서 DOM XSS가 0건이었다. XSS가 버그 보상에서 차지한 비중은 2018년 30%에서 2023년 4.1%로 줄었다. [2차] → 출력 지점 규칙을 엄격하게 지키고, 문자열을 HTML로 바꾸는 길은 `trust`뿐이게 한다.

**메모리 안전은 근거가 가장 강하다.** [원문] → 메모리 안전 보장은 맞는 방향이고, 권한 검사가 성립하기 위한 전제다.
- Microsoft 2019: 공개된 보안 취약점의 약 70%가 메모리 안전 버그였다.
- Android: 메모리 안전 취약점 비중이 2019년 76%, 2024년 24%, 2025-11에는 20% 미만이었다.
- Rust는 100만 줄당 약 0.2건, C/C++는 약 1,000건이었다. 다만 Rust 쪽 버그 수가 매우 적어 불확실하다.
- Go Capslock 문서는 데이터 경쟁이 있으면 어떤 권한의 함수든 부를 수 있다고 적었다.

**AI가 없는 패키지 이름을 지어낸다(slopsquatting).** [원문] → 의존성 추가는 보안 변화로 다루고, 모르는 이름은 거부한다.
- USENIX Security 2025(https://arxiv.org/abs/2406.10279): 제안된 패키지의 19.7%가 없는 이름이었다(상용 모델 5.2%, 공개 모델 21.7%).
- 지어낸 고유 이름은 205,474개였고, 그중 43%는 10번 다시 돌려도 다시 나왔다.
- 2026(https://arxiv.org/abs/2605.17062): 최신 모델은 4.62~6.10%였다. 다섯 모델이 공통으로 지어낸 53개 이름은 아직 등록할 수 있다.

**설치 스크립트와 로컬 AI 도구를 함께 악용하는 공격이 실제로 일어났다.** [2차] → 패키지 설치 스크립트를 없앤 결정이 맞다.
- s1ngularity(2025-08): 악성 Nx 설치 후 스크립트가 로컬 AI CLI를 시켜 비밀을 찾게 했고, 자격 증명 약 2,349개를 훔쳤다.
- Shai-Hulud 2.0(2025-11): 저장소 2만 5천 개 넘게 퍼졌다.

**패키지 권한은 강제하기 싸고, 잘 늘지 않는다.** npm 패키지의 31.9%는 권한이 필요 없었다. 58.7%는 eval이나 내장 프로토타입 수정 때문에 "전부"가 필요했다. 상위 패키지 업데이트 가운데 권한이 늘어난 것은 0.5%였다(ICSE 2021, https://arxiv.org/pdf/2103.05769). [원문] → eval · 몽키패치가 없는 도담은 권한을 더 좁게 잡을 수 있고, "늘어난 것만 승인"은 드물게 일어난다.

**사람은 넓은 권한 안내를 무시한다.** 설치 권한에 주의한 사용자는 17%, 이해한 사용자는 3%였다(Felt 등 2012). Chrome은 업데이트가 경고 수준 권한을 추가하면 사용자가 받아들일 때까지 확장을 끈다. [원문] → 차이는 범주가 아니라 구체 항목(호스트 · 테이블 · 경로)과 호출 경로로 보여 준다.

**넓은 권한은 샌다.** [원문] → 권한에 자원 범위를 두고, 다른 프로그램 실행 · 외부 함수 호출(FFI) · `trust`는 보고서에서 "전부"로 친다.
- Go Capslock은 분석 못 한 코드 · 리플렉션 · unsafe · cgo · exec를 권한으로 보고한다. 결과는 예시 호출 경로를 담은 JSON이고, 이전 판과 비교할 수 있다.
- Deno는 `--allow-net=host`처럼 범위를 두며, run · FFI는 "전체 허용과 같다"고 본다.
- LavaMoat는 패키지 정책을 이름이 아니라 의존 경로로 건다.

**데이터에 붙은 접근 정책은 실용적이다.** [원문 · 미확인]
- Storm(OSDI 2021): 정책이 서버 코드의 4% 미만이었고, 타입 에러가 실제 유출을 잡았다.
- Sesame(SOSP 2024): 코드의 95%를 자동으로 검사했고, 부하는 3~10%였다.
- Jif · FlowCaml은 채택 · 사용성 자료를 찾지 못했다.

**접근 제어 실패는 대부분 레코드 단위다.** [원문 · 2차] → `access auth(역할)`만으로는 ID만 바꿔 남의 레코드를 읽는 공격을 못 막는다.
- OWASP Top 10 2025의 1위 '접근 제어 실패'(https://top10.owasp.org/2025/A01_2025-Broken_Access_Control): 발생 1,839,701건, 공개된 취약점 32,654건이다. 권고는 "기본 거부"와 "레코드 소유권 강제"이고, SSRF도 이 항목에 합쳐졌다.
- OWASP API 보안 10대 위험(2023)의 1위인 '객체 수준 권한 실패'를 "매우 흔하다"고 했다.
- Lovable(2025년 공개된 취약점): 행 수준 보안이 빠져서 인증 없는 사용자가 임의 테이블을 읽고 쓸 수 있었다(심각도 10점 만점에 9.3).

**그 밖의 빈 곳.** [원문 · 2차]
- SSRF: 2026 업체 조사(동료 심사 아님, 522개)에서 가장 많은 약점이었다.
- 암호: LLM이 쓴 Rust 암호(AEAD) 코드 중 컴파일된 것의 57%에 오용이 있었고, 논스 재사용이 체계적으로 나왔다(https://arxiv.org/abs/2604.27001).
- 서비스 거부: Cloudflare 2019년 27분 장애는 되추적 정규식 때문이었고, 해결책은 선형 시간 엔진이었다.
- 비밀: 2024년 GitHub에서 비밀 2,380만 건이 유출됐다.
- 검사기 속이기: GPT-5는 불가능한 과제의 76%에서 속였고, 테스트를 숨기자 거의 0이 됐다(https://arxiv.org/abs/2510.20270). Rust 컴파일러에도 2015년부터 열려 있는 건전성 구멍이 있다.
- 타이밍 공격과 DB 로직의 경쟁 조건은 AI에 특화된 수치를 찾지 못했다. [미확인]

## 남은 질문

- DB를 앱 밖에서 직접 쓰는 것은 컴파일러가 막을 수 없다. DB 권한으로만 막는다.
- 외부 API 데이터는 언제든 어긋날 수 있다. `Stale<T>`처럼 타입에 드러낸다.
- 직렬화 트랜잭션은 쓰기가 많으면 느리다. Ur/Web도 쓰기가 많은 벤치마크에서 특히 나빴다.
- 오프라인 쓰기를 첫 판에 넣을지는 정하지 않았다.
- 중복 검사 임계값, 크기 제한 기본값, 속도 저하 허용치는 벤치마크로 정한다.
- GC · 참조 카운트 · 값 의미론을 AI 관점에서 비교한 자료는 아직 없다.
