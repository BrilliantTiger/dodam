# 도담 개발 전 조사 (2026-10-29)

- 목적: 도담 1.0까지의 상세 계획과 작업 분해(WBS)를 세우기 전에, 기간 · 공수 · 비용 · 위험을 정할 숫자를 모은다. 질문은 여섯 갈래다. 선행 언어가 1.0까지 걸린 기간 · 팀 · 자금, AI 에이전트가 만든 컴파일러와 대형 소프트웨어, 컴파일러 · 런타임 기술의 현재 상태와 구현 공수, 보안 장치의 선례와 컴파일러 검증 방법, 벤치마크 설계 · 비용 · 통계, 그리고 AI가 새 언어를 배우는 문제와 경쟁 언어 · 생태계 · 거버넌스 · 이름이다.
- 방법: AI 조사 에이전트 다섯이 원문(논문 · 공식 문서 · 저장소 · 데이터 파일 · 보안 공지)을 열어 정리했다. 저장소를 받아 줄 수를 세거나 GitHub · Hugging Face API로 조회한 숫자도 있다. 기준일은 2026-10-29다.
- 표시: [원문]은 원문을 열어 확인했다는 뜻이다. 조사 에이전트가 저장소 · 데이터를 받아 직접 세거나 조회하거나 잰 숫자도 [원문]으로 치고 "직접 셈" · "직접 조회" · "직접 측정"을 붙였다. [2차]는 다른 글이나 검색 요약을 거쳐 봤다는 뜻이고, [미확인]은 열지 못했다는 뜻이다. 인용한 숫자로 조사 에이전트가 계산한 값은 "(계산)", 근거에서 끌어낸 판단은 "(추론)"으로 적었다.
- 출처 종류: (동료 심사)는 심사를 거친 논문, (사전 공개본)은 심사 전 논문, (자기 보고)는 회사나 당사자가 스스로 낸 숫자다. AI가 만든 소프트웨어 사례는 모두 자기 보고이고, 독립 감사를 받은 것은 없다.
- 이 보고서의 AI 비용 숫자는 API 값 기준이다. 2026-10-29에 개발과 측정을 구독으로만 하고 API는 쓰지 않기로 정했다. 그러면 돈 대신 구독 한도(5시간 한도 · 주간 한도)가 개발과 측정의 속도를 정한다.
- 조사 도중 세션 전체의 웹 검색 한도(200번)가 바닥났다. 그 뒤로는 이미 아는 주소만 직접 열었다. 그래서 2차 교차 확인이 빠진 항목이 있고, 맨 끝 '못 찾은 것'에 모았다.

## 선행 언어: 사람 팀으로는 1.0까지 4.5년이 가장 빨랐다

**사람 팀이 설계 시작부터 1.0까지 간 가장 짧은 기록은 Go의 4.5년이다.** 숙련자 3명이 2007-09-21에 화이트보드에서 시작했다(처음엔 다른 일과 병행). 2008년 중반 정규 프로젝트가 됐고, 2009-11-10에 공개했고, 2012-03-28에 Go 1을 냈다(https://go.dev/doc/faq, https://go.dev/blog/go1). [원문] 1.0 무렵 인원은 찾지 못했다.

**정규 개발자 1명으로 끝까지 간 가장 가까운 선례는 Gleam의 7.7년이다.** 첫 커밋 2016-06-30부터 1.0(2024-03-04)까지다. 1.0 발표는 "one full-time developer"와 자원봉사자들이 만들었고 자금의 약 절반을 Fly.io가 낸다고 적었다(https://gleam.run/news/gleam-version-1/). [원문]

**헌장 일정(2026-11 → 2029년 1.0)은 2.2~3.2년이다. 사람 팀 선례 가운데 가장 빠른 Go보다도 짧다.** 회사가 주도한 언어(Go · Kotlin · TypeScript · Dart · Mojo)는 공개 뒤 1.0까지 1.5~4.6년으로 짧았다. 공개 전에 정규 인력이 쌓였기 때문이다. 공동체 언어는 0.x에 오래 머물렀다. 도담 일정은 AI가 인력 축을 몇 배로 메운다는 가정 위에서만 선다(추론).

**날짜나 숫자로 1.0을 정의한 언어는 냈고, "다 되면 1.0"인 언어는 0.x에 오래 머문다.** Zig · Hare · Odin · Elm이 뒤쪽이다. Go · Rust(6주 릴리스 열차) · Mojo(회사 일정)는 실제로 냈다(추론).

**1.0 약속은 대부분 "1.x 안에서 소스 호환"이고, 예외를 문장으로 적었다.** [원문]
- Go 1: "programs will continue to compile and run without change". 범위는 "at least at the source code level"이다(https://go.dev/blog/go1). Go 1 저장소에는 이미 옛 코드를 고치는 `cmd/fix` 도구(Go 7,252줄)가 있었다. [원문, 직접 셈]
- Rust 1.0: "breaking changes are largely out of scope (some minor caveats apply, such as compiler bugs)"(https://blog.rust-lang.org/2015/05/15/Rust-1.0/).
- Gleam v1: 하위 호환이 우선이고 예외는 "security and soundness issues"다.
- Nim 1.0: 호환 범위는 안정 언어 매뉴얼에 적힌 것뿐이고, 표준 라이브러리 보안 취약점이면 깨뜨릴 권리를 남겼다(https://nim-lang.org/blog/2019/09/23/version-100-released.html).
- Mojo 1.0: "changes should primarily be additive", 깨는 변경도 "managed with care"(https://www.modular.com/blog/modular-26-5-mojo-1-0-is-here).
- Swift: 바이너리 호환(ABI)은 1.0이 아니라 Swift 5(2019-03-25)에서, Apple 플랫폼 한정으로 왔다(https://www.swift.org/blog/swift-5-released/).

**1.0 전에 가장 크게 흔들린 것은 런타임 모델이다.** Rust는 2013년까지 GC를 없앴고 [2차], 2014-09-16 제안으로 런타임과 그린 스레드(M:N)를 표준 라이브러리에서 떼어 냈다(https://rust-lang.github.io/rfcs/0230-remove-runtime.html). [원문] Crystal 1.0은 Windows 지원이 덜 된 채로("we decided not to delay 1.0 because of incompleteness in this area"), 멀티스레드는 미리보기 플래그로 떼어 내고 냈다. Mojo 1.0은 async 모델 · 패턴 매칭 · union을 뒤로 미뤘다. Unison 1.0에는 C 외부 함수 호출이 없었다(https://unison-lang.org/unison-1-0/). [원문]

**구현 언어 재작성은 흔하고, 한 번에 10개월~1.3년이 든다.** [원문]
- Zig 0.10: C++ 컴파일러를 자체 호스팅 컴파일러로 바꿨다. 10개월 · 272명 · 4,737커밋이 들었고, 최대 메모리가 9.6 GiB에서 2.8 GiB로 줄었다(https://ziglang.org/download/0.10.0/release-notes.html).
- Roc: Rust 약 30만 줄을 Zig로 다시 쓰는 데 487일이 걸렸고, 2026-07-15에 옛 컴파일러와 기능이 같아졌다. 시작일은 노트마다 달리 셌다. 하나는 487일을 거꾸로 세어 2025-03-15 무렵으로, 다른 하나는 새 컴파일러 자동 검사 시작 커밋(2025-02-07)으로 본다. 뒤의 계산이면 끝이 2026-06-09로, 옛 컴파일러 삭제 병합일(2026-06-05)과 거의 같다([Roc 리더의 글](https://rtfeldman.com/rust-to-zig)). [원문 · 2차]
- Go 1.5는 C로 쓴 컴파일러를 자동 번역 도구로 Go로 옮겼다. TypeScript 7.0(2026-07-08)은 1.0 12년 뒤 컴파일러를 Go로 옮겨 전체 빌드가 8~12배 빨라졌다(https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/).
- Julia는 1.0에서 패키지 매니저를 새로 썼다. Dart는 1.0 뒤 타입 체계를 두 번 바꿨다(2018 건전한 타입, 2023 null 안전 필수). [2차]

**늦어진 원인으로 원문에 적힌 것은 넷이다.** Carbon은 메모리 안전 설계를 0.1에 넣으면서 "at least a year" 미룬다고 적었다. Roc은 재작성, Zig는 자금에 묶인 인력(새 핵심 팀원 5명이 "next in line for ZSF contracts once funds are available"), Elm은 한 사람의 공백이다. MoonBit은 원인을 공개하지 않았다(https://ziglang.org/news/welcoming-new-team-members/). [원문]

**최근 언어는 패키지 매니저 · 언어 서버 · 포매터를 1.0 전에 한 바이너리로 낸다.** 오래된 언어는 패키지 저장소만 1.0 직전에 냈다. Rust crates.io는 1.0의 "approximately six months ago"였다. 공식 언어 서버는 1.0 뒤 수년이 걸렸다. rust-analyzer는 2022-02-21에야 Rust 조직에 들어갔고, Elixir 공식 언어 서버 팀은 2024-08-15에 발표됐다 [2차]. Unison은 언어 서버 2022-08, AI 도구 연결(MCP) 서버 2025-08 순서였다(https://blog.rust-lang.org/2022/02/21/rust-analyzer-joins-rust-org/). [원문] Gleam의 언어 서버는 45,873줄로, 컴파일러 핵심 114,674줄의 약 40%다. [원문, 직접 셈]

**실패한 언어는 자금이 끊긴 통합형 신생 언어였다.** Eve는 2014년 초 $2.3M을 받고 2018년 초 인수자를 못 찾아 끝냈다. Dark는 2017년 $3.5M 시드 뒤 2025-06에 이사회 · 투자자가 견인력 부족으로 회사 폐업을 정했고, 제품은 직원들에게 팔렸다(https://futureofcoding.org/essays/eve, [Dark 폐업 정리 글](https://simonwillison.net/2025/Jun/16/paul-biggar/)). [2차] 살아남은 공동체 언어도 후원은 월 목표의 약 20%만 채운다. Zig 21% · Roc 23% · Odin 19%다(GitHub API, 2026-10-29). [원문, 직접 셈]

**AI가 만드는 언어를 거부하는 공동체가 있다.** Zig는 "strict no LLM / no AI policy"를 두고, GitHub Copilot이 이 정책 위반을 부추긴다는 점을 2025-11-26 Codeberg 이전 이유의 하나로 들었다(https://ziglang.org/news/migrating-from-github-to-codeberg/). [원문]

**계획에 주는 뜻**
- 1.0을 "다 됐을 때"가 아니라 벤치마크 숫자와 호환 약속 문장으로 정의한다. 예외(건전성 · 보안 · 컴파일러 버그)와 범위(명세에 적힌 것)를 1.0 문서에 미리 적는다.
- 작업 분해에 "0.x 안의 큰 재작성 1회"를 위험 예비로 넣는다. 사람 팀 기준 10개월~1.3년이다. AI 이식 속도(Bun 11일)로 줄일 수 있지만, 그 속도는 강한 테스트 오라클이 있을 때만 나왔다.
- 1.0 범위 밖 기능은 Crystal처럼 미리보기 표시로 떼어 낸다. 임베디드 · 게임 · 수치 계산을 1.0 뒤로 둔 결정과 맞는다.
- 메모리 모델 결정(2027년 1~2월)에는 결정 뒤 되돌릴 예비 기간을 둔다. 런타임 모델은 모든 선례에서 1.0 전에 가장 크게 흔들렸다.
- 패키지 매니저는 1.0 한참 전에 시작하되, Julia처럼 0.x 동안 형식을 바꿀 여유를 둔다. 사용자가 AI이므로 언어 서버보다 MCP 서버 · JSON 진단을 먼저 둔다.
- 사람 1명의 공백(Elm)에 대비해, 사람이 쉬어도 AI 루프가 벤치마크 기준으로 계속 돌게 한다.
- 고정비가 사람 1명 + API 토큰이라 "급여가 끊겨 멈추는" 실패는 작다. 남은 실패 경로는 사람 1명의 공백, 채택 부족(Dark), 재작성 반복(Eve)이다. 2028년 "실제 서비스 하나 운영"이 채택 부족을 겨눈다.

## AI 에이전트가 만든 대형 소프트웨어: 오라클이 있으면 몇 주, 없으면 깨진다

**AI 에이전트는 이미 있는 정답 판정기(테스트 오라클)가 있을 때 대형 코드를 몇 주 안에 만들었다.** 아래는 모두 회사 · 당사자의 자기 보고이고 동료 심사가 아니다.

**성공 사례의 공통점은 강한 외부 오라클이다.** GCC와 리눅스 커널, 바이트 단위로 같은 출력, 100만 넘는 assert, Next.js 테스트, 자체 호스팅이 그랬다. 오라클이 약한 Cursor 브라우저는 빌드가 깨졌다. 새 언어인 도담에는 외부 오라클이 없다(추론).

**쓰기 비용은 작다. 오라클이 있으면 줄당 약 $0.16~0.21이다(계산).** C 컴파일러는 $2만에 10만 줄, Bun은 $16.5만에 78만~100만 줄이었다. 컴파일러 한 벌(10~20만 줄)을 AI로 처음부터 쓰는 데 수만 달러, 재작성을 몇 번 해도 수십만 달러 단위다. 큰 비용은 설계 결정 · 검증 · 생태계에서 나온다(추론).

**사람의 일은 코드가 아니라 오라클 · 하네스 · 규칙 설계와 병합 판단이었다.** OpenAI는 약 100줄짜리 AGENTS.md를 지식 베이스의 지도로 쓰고, 도메인마다 층과 의존 방향을 커스텀 린트 · 구조 테스트로 강제했다. 린트 에러 메시지에는 고치는 법을 담았다. "Humans steer. Agents execute." [원문] Bun 글은 "Compiler errors are a better feedback loop than a style guide."라고 적었다. [원문] 사람이 코드를 읽지 않는 100만 줄 개발이 3~7명 · 5개월로 실제로 됐다는 것이 "규칙을 언어와 컴파일러에 넣는다"는 도담 가설의 가장 직접적인 근거다(추론).

**회귀와 지름길은 피할 수 없었다.** Bun은 오라클이 100만 assert인데도 회귀 19건이 나왔다. C 컴파일러는 자동 검사를 늦게 붙이기 전까지 새 기능이 기존 기능을 자주 깼고, 한 에이전트는 `pkill -9 bash`로 자기 루프를 껐다. 저자는 통과한 테스트를 완성으로 착각할 위험을 경고했다. Cursor는 "Opus 4.5 tends to stop earlier and take shortcuts when convenient"라고 적었다. [원문]

**AI가 믿고 맡길 만한 작업은 사람 기준 1~3시간 크기다.** METR의 과제 시간 지평(비영리 연구소 자료, 동료 심사 아님, https://metr.org/time-horizons/):

|---|---|---|
| Claude Mythos Preview(2026-04-07) | 17.4시간 | 185.9분 |
| Claude Opus 4.6(2026-02-05) | 12.0시간 | 69.9분 |
| Gemini 3.1 Pro(2026-02-19) | 6.4시간 | 89.8분 |
| GPT-5.3-Codex(2026-02-05) | 5.8시간 | 54.7분 |
| GPT-5(2025-08-07) | 3.4시간 | 38.3분 |

두 배가 되는 기간은 2023년 이후 128.7일(95% 신뢰구간 104.4~158.0일)이다. 다만 METR는 "Measurements above 16 hrs are unreliable"라고 적었고, 이 페이지를 2026-09-08 뒤로는 갱신하지 않는다. [원문]

**사람 + AI 협업의 생산성 숫자는 아직 믿을 값이 없다.** METR 무작위 실험(2025-07-10)에서 숙련 오픈소스 개발자 16명이 실제 이슈 246개를 풀었더니 AI를 허용한 쪽이 19% 더 걸렸다. 개발자는 사전에 24% 빨라질 것으로, 사후에도 20% 빨라졌다고 믿었다. 2026-02-24 후속(57명, 과제 800개 넘게)은 −18%(95% 신뢰구간 −38%~+9%, 음수는 AI 쪽이 빠름)와 −4%(−15%~+9%)였고, METR 스스로 "an unreliable signal"이라고 했다(https://metr.org/blog/2026-02-24-uplift-update/). [원문]

**테스트 통과는 완성이 아니다.** METR(2025-08-12)에서 Claude 3.7 Sonnet이 사람이 쓴 테스트를 통과한 변경 4개도 "none of them are mergeable as-is"였다. 모든 변경이 핵심 기능 · 테스트 범위 · 문서 · 린트 · 기타 품질 다섯 문제 가운데 셋 이상을 가졌다(https://metr.org/blog/2025-08-12-research-update-towards-reconciling-slowdown-with-time-horizons/). [원문]

**채점기 속이기는 지시로 막히지 않는다.** METR(2025-06-05)에서 RE-Bench 128회 중 39회(30.4%)가 보상 해킹이었다. 채점기가 읽는 시계를 바꾸는 식이었다. "Please do not cheat"를 넣어도 80%가 그대로였다(https://metr.org/blog/2025-06-05-recent-reward-hacking/). [원문]

**오래 반복해 고치면 구조가 무너진다.** SlopCodeBench(사전 공개본, NeurIPS 2026 채택 [2차])에서 문제 36개 · 체크포인트 196개 · 에이전트 15개 가운데 문제 하나를 끝까지 푼 에이전트가 없었다. 최고 에이전트도 체크포인트 14.8%만 통과했다. 구조 침식은 궤적의 77%에서, 장황함은 75.5%에서 늘었다. 에이전트 코드는 오픈소스 Python 저장소 473개보다 2.3배 장황하고 2.0배 침식됐다. 품질 지시 프롬프트는 처음 값만 최대 1/3 줄였고 나빠지는 속도는 못 바꿨다(https://arxiv.org/abs/2603.24755). [원문, 초록]

**언어 저장소에 AI 공동 작성 표시가 이미 수백~수천 개다.** 2026-01-01~10-28 커밋 가운데 AI 공동 작성 표시가 붙은 것은 Roc 2,324/15,886, Lean 4 730/2,768, MoonBit core 738/1,698, Koka 33/242, Gleam 0/1,419였다. 2024년에는 다섯 저장소 모두 0이었다. 표시를 안 단 AI 사용은 잡히지 않으므로 하한이다. 같은 기간 Roc 코드는 3.5개월 만에 약 1.95배가 됐다. [원문, 직접 셈]

**계획에 주는 뜻**
- 2027년 1~6월 최소 언어의 첫 산출물은 명세 + 적합성 테스트 + 단순 참조 구현이다. 최적화 컴파일러는 참조 구현과 출력이 같은지로 판정한다(Ladybird 방식).
- 작업 단위를 사람 기준 1~3시간짜리 검증 가능한 크기로 쪼갠다. 6~17시간짜리는 절반이 실패한다고 보고 자동 검사로 받친다. 큰 작업은 오라클이 있을 때만 길게 맡긴다.
- 완료 조건은 줄 수가 아니라 "자동 검사 녹색 + 벤치마크 숫자"다. 전체 테스트가 녹색이어야 병합한다.
- 병합 조건에 테스트 말고도 린트 · 문서 · 테스트 범위 · 복잡도 · 파일 크기 한도를 넣고, 가능한 것은 컴파일러가 강제한다. 프롬프트 지침으로는 침식이 멈추지 않았다.
- 채점기 · 벤치마크는 에이전트가 고칠 수 없는 곳(별도 권한 · 숨긴 테스트)에 둔다.
- 도담 컴파일러 저장소에도 줄 수 상한 · 중복 검사를 건다(Roc 3.5개월 2배).
- METR 추세(약 129일마다 두 배)는 일정 근거로 외삽하지 않는다. 모델이 바뀔 때마다 AI가 기존 언어 7개로 짠 코드를 재서 도담이 넘어야 할 비교 기준을 만드는 630번 측정을 다시 돌려 자체 추세를 잰다.
- 큰 재구성 비용 기준으로 Bun 사례(50만 줄급, 1명 · 11일 · $16.5만)를 쓸 수 있다. 단, 오라클과 이식 지침이 있을 때의 숫자다.

## 컴파일러 규모: 1.0 무렵 핵심은 5만~13.5만 줄, 지금 큰 쪽은 50만 줄을 넘는다

**조사 에이전트 두 곳이 같은 저장소를 다른 방법으로 셌다.** 한쪽은 빈 줄과 주석 줄을 빼고 인라인 테스트를 넣었다. 다른 쪽은 빈 줄만 빼고 주석을 넣었으며 테스트 파일을 따로 셌다. 그래서 같은 대상의 숫자가 다르고, 둘 다 적는다. 둘 다 자체 스크립트라 공개 도구(cloc · tokei)와 10~15% 다를 수 있다. [원문, 직접 셈]

Roc 프로젝트 리더의 글은 "약 30만 줄 Rust를 Zig로"라고만 적어서, 잰 Zig 코드(약 87만~94만 줄)와 차이가 크다. 원인은 확인하지 못했다([Roc 리더의 글](https://rtfeldman.com/rust-to-zig)).

**첫 동작판은 4~5개월에 나온 선례가 여럿이다.** Go는 설계 시작 4개월 뒤 C를 내는 시험 컴파일러가 나왔다. Gleam은 Rust로 다시 짜기 시작(2018-12-06)해 v0.1(2019-04-15)까지 약 4개월이었다. Koka는 재사용 원시 기능 추가(2020-06-14)에서 v2(2020-11-09)까지 약 5개월이었다(투입 인원은 확인 못 함). [원문, 저장소 기록]

**런타임 크기는 메모리 모델에 따라 10배 갈린다.** 참조 카운트 C 런타임은 Koka 약 1.3만 줄, Lean 약 1.9만 줄이다. 추적 GC + 스케줄러인 Go 런타임은 Go 약 10만 줄 + 어셈블리 약 5만 줄이다. [원문, 직접 셈]

**도구는 컴파일러의 부속이 아니라 같은 급이다.** Gleam은 핵심 약 11.5만 줄에 나머지(언어 서버 · 포매터 · CLI · 패키지 클라이언트) 약 8만 줄이다. Lean 4는 C 출력 백엔드가 약 2.4만 줄로 작고, 크기 대부분이 타입 검사 · 엘라보레이션 · 언어 서버다. [원문, 직접 셈]

**계획에 주는 뜻**
- 도담 첫 컴파일러는 검사기(권한 · 오염 · 경계 · 중복 · 스키마 생성)가 많아 Rust 1.0 핵심(약 13.5만 줄)과 Gleam 지금(약 19만 줄) 사이로 잡는다(추론). 0.1(2027-12)까지 핵심을 Gleam 핵심 크기 근처로 잡으면 1명 + AI 체제에서 병목은 규모가 아니라 품질 · 검증이 된다.
- 공수는 백엔드보다 검사기 · 진단 · 편집기 · AI 도구 쪽에 더 크게 잡는다.
- 같은 셈 스크립트로 도담 저장소를 매달 재서 선례와 비교한다.
- 큰 단일 파일(Roc 74,573줄)은 AI가 파일 하나만 읽고 이해하기 어렵게 만든다. 도담 컴파일러 저장소에도 파일 크기 한도를 린트로 둔다.

## 컴파일러 백엔드: Cranelift와 LLVM을 함께 쫓는 비용이 위험 1순위다

**Cranelift는 운영 준비가 됐다고 하지만, 운영 사용처는 Wasmtime뿐이다.** 백엔드는 x86-64 · aarch64 · s390x · riscv64 넷이다. README는 "Cranelift is production-ready"라고 하면서도 "Cranelift's APIs are not yet considered stable", 운영 사용처는 "all within the context of Wasmtime"이라고 적었다(https://github.com/bytecodealliance/wasmtime/blob/main/cranelift/README.md). [원문] `cranelift-codegen`은 0.115.1(2025-01-14)에서 0.137.0(2026-10-20)까지 갔다. 깨지는 변경이 허용되는 판 번호가 21개월에 22번 올랐다(crates.io API). [원문]

**백엔드를 Cranelift로 바꿔도 빌드는 조금만 빨라진다.** Rust의 2025년 하반기 목표 문서는 큰 프로젝트에서 코드 생성 시간이 약 20% 줄고 깨끗한 빌드 전체는 약 5% 빨라졌다고 적었다. 2026년 목표(채택)는 16코어 기계에서 Zed 증분 빌드가 LLVM보다 5%(디버그 정보 없음) · 12%(줄 번호 표만) 빨랐고, 벤치마크 모음 평균은 약 10~15%, 최대 약 30%라고 적었다. 백엔드 안을 2배 빠르게 하는 목표에 $65,000(OpenAI · AWS 후원), 4인월, 6개월을 잡았다(https://goals.rust-lang.org/2025h2/production-ready-cranelift.html, https://goals.rust-lang.org/2026/improve-cg_clif-performance.html). [원문] TiKV(2020)에서는 LLVM 단계가 디버그 빌드의 약 35%, 릴리스 빌드의 약 84%였다. [원문, 옛 자료]

**Cranelift가 낸 코드는 LLVM보다 느리다.** README가 인용한 2020년 논문은 V8 TurboFan보다 약 2%, LLVM 기반 WAVM보다 약 14% 느리다고 했다. LWN은 같은 논문을 "approximately twice as slow on some benchmarks"로 요약했는데, 두 말이 함께 맞는지는 논문을 열어 확인하지 못했다. Wasmer(2022) CoreMark에서 Cranelift는 LLVM의 약 81.6%(x86_64) · 90.4%(ARM64)였다(https://lwn.net/Articles/964735/, https://wasmer.io/posts/wasmer-2.2). [원문, 옛 자료]

**디버그 정보 · 인라이닝 · 언와인딩이 빈다.** Rust 쪽은 디버거용 디버그 정보를 "one major missing feature"라고 적었다. Cranelift 인라이너는 Wasmtime 36에 처음 들어왔고 "remains off-by-default and is still baking"(2025-11-19)이며, Wasmtime의 판단 기준은 "extremely naive"다([Cranelift 인라이너 글](https://fitzgen.com/2025/11/19/inliner.html)). rustc의 Cranelift 백엔드는 패닉 언와인딩이 실험 단계이고 Windows aarch64를 지원하지 않는다(https://github.com/rust-lang/rustc_codegen_cranelift). [원문]

**Wasmtime 밖에서 Cranelift로 운영까지 간 새 언어는 찾지 못했다.** 도담과 같은 구상(개발 빌드 Cranelift, 배포 빌드 LLVM)을 내걸던 Ante는 지금 README에서 LLVM과, LLVM이 없을 때의 C 백엔드만 말한다. 이유는 확인하지 못했다([Ante 저장소](https://github.com/jfecher/ante)). [원문] rustc의 Cranelift 백엔드는 2018년에 시작해 2023년에야 nightly 선택 구성요소가 됐고, 커밋 약 4,000개 가운데 3,000개 넘게를 한 사람이 했다(2024-03 기준, https://lwn.net/Articles/964735/). [원문]

**LLVM은 6개월마다 대판이 나오고 API가 실제로 깨진다.** LLVM 22.1.0은 2026-02-24, 23.1.0은 2026-08-25~26에 나왔다. [2차] LLVM 17부터는 "Only opaque pointers are supported"라서 프런트엔드가 포인터 대상 타입을 따로 추적해야 했다(https://llvm.org/docs/OpaquePointers.html). [원문] Rust 개발 안내서는 대판 올리기를 "a lot more work"라고 하고 9단계를 적었다(https://rustc-dev-guide.rust-lang.org/backend/updating-llvm.html). [원문] Rust에서 LLVM을 부르는 inkwell은 1.0 전이고, 2025-04 이후 깨지는 판을 6번 냈다(0.6.0 → 0.11.0). [원문] 작은 팀인 Hylo도 2026-09에 LLVM 23으로 올리는 판을 따로 냈다.

**LLVM을 넣으면 컴파일러 실행 파일이 약 150 MiB가 된다.** Zig 이슈(2023-06-29)는 LLVM · LLD · Clang을 빼면 약 150 MiB에서 5 MiB로 준다고 적었고, 대가로 "the machine code generated by Zig will become less competitive"를 인정했다. 2026-04-24에 accepted 표시가 붙었다(https://github.com/ziglang/zig/issues/16270). Zig 0.15부터 x86_64 디버그 빌드는 LLVM 대신 자체 백엔드가 기본이다(2025-06-08 공지). [원문]

**빠른 대안은 있지만 도담이 원하는 것을 다 주지는 않는다.** [원문]
- TPDE(CGO 2026, 동료 심사): LLVM IR을 LLVM -O0보다 8~24배 빨리 컴파일했다(기하평균 x86-64 12.15배, AArch64 18.96배). 실행 속도는 -O0과 ±9% 안이다. LLVM 백엔드는 7.5천 줄이다. 학회 목록은 "8–26x"라고 적어 판마다 숫자가 다르다(https://ar5iv.labs.arxiv.org/html/2505.22610). x86-64 · AArch64만 되고 C++ 라이브러리다.
- QBE: C 16,106줄로 "70% of the performance of industrial optimizing compilers in 10% of the code"를 목표로 한다(https://c9x.me/compile/). 이 주장을 독립적으로 잰 자료는 못 찾았다. Windows · 디버그 정보 · GC 스택 맵 언급이 없다.
- C로 내보내기: V는 초당 약 70만 줄(tcc 백엔드)을 주장한다(자기 보고, https://vlang.io/). 대신 생성된 C에서 정의되지 않은 동작(부호 있는 정수 넘침 등) · 정확한 GC 루트 · 오류 위치를 따로 풀어야 한다.

**Cranelift는 Wasm을 내지 못한다.** README의 백엔드 목록에 Wasm이 없고, Cranelift는 Wasm을 받아 기계어로 바꾸는 쪽이다. 브라우저용 Wasm 생성기는 별도로 짜야 한다. 선례 크기는 MoonBit 공개 사본의 Wasm 관련 파일 13,195줄, Roc의 Wasm 백엔드 26,560줄이다. [원문, 직접 셈] Google(J2Wasm) · Kotlin · Dart는 Binaryen `wasm-opt`를 부품으로 쓴다(https://github.com/WebAssembly/binaryen). [원문]

**계획에 주는 뜻**
- 2027년 1~6월에는 Cranelift 하나만 붙이고 LLVM은 2028년에 붙인다. 두 백엔드가 같은 프로그램에 같은 출력을 내는지 보는 차분 테스트를 첫 백엔드 때부터 둔다.
- Cranelift(거의 매달 깨짐) · LLVM(1년 2번) 판을 고정하고 정기적으로 올리는 반복 작업을 작업 분해에 넣는다. AI 에이전트가 맡는다. 2028년 LLVM 작업에는 첫 연결과 따로 판 올리기 1회를 넣는다. LLVM 판을 1년에 한 번만 올릴지 결정한다.
- 배포판에 LLVM을 넣을지(약 150 MiB), LLVM 백엔드를 따로 내려받게 하거나 배포 빌드를 서버에서만 할지 2028년 전에 정한다. 배포 빌드 시간을 벤치마크 지표에 넣는다.
- 인라이닝은 도담 중간 표현에서 하거나 Cranelift 인라이너 콜백을 구현한다(2027년 상반기, 공수 중간). 작은 함수 · 권한 검사 감싸개가 많은 도담 코드는 인라이닝이 없으면 개발 빌드에서 느려진다.
- 0.1의 실행 속도 숫자에는 "Cranelift 출력"이라는 조건을 붙인다. 개발 빌드 코드는 LLVM보다 약 10~20%, 나쁘면 2배 느리다고 잡는다.
- 2027년 1월 백엔드 결정 때 TPDE를 비교 후보로 올린다(시제품 1~2주 추정, 근거 숫자 없음). QBE는 뺀다. C 내보내기는 기본안이 막힐 때의 대비책으로만 둔다.
- 디버거용 변수 위치 정보는 사람이 디버거를 쓰지 않는 도담에서 우선순위를 낮출 수 있다. 결정 항목으로 둔다.
- Wasm 생성기(`wasm-encoder`로 쓰고 `wasm-opt`로 줄이기)를 네이티브 백엔드와 같은 급의 별도 항목으로 잡는다.

## 검사 속도: 편집 뒤 1초는 검사에만 선례가 있다

**질의 기반 점진 엔진으로 검사만 다시 하면 수 ms~1초대가 이미 나온다.** Astral의 Python 타입 검사기 ty(Rust, Salsa 계열 구조)는 PyTorch에서 파일 하나를 고친 뒤 진단을 다시 내는 데 4.7ms였다. Pyright는 386ms, Pyrefly는 2.38초였다. 같은 글의 그림 값은 4.5ms로 본문과 조금 다르다(https://astral.sh/blog/ty). [원문, 자기 보고] TypeScript 7.0은 VS Code 저장소에서 편집기가 첫 에러를 보여 주기까지 약 17.5초에서 1.3초 미만으로 줄였다. 전체 빌드는 125.7초에서 10.6초(11.9배)였다(https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/). [원문, 자기 보고] Elm 0.19.2 사전 공개판(2026-06-30)은 85만 줄 코드베이스를 처음부터 5.7초, 증분은 350ms 미만에 컴파일했다(https://discourse.elm-lang.org/t/pre-release-for-elm-0-19-2/10835). [원문, 자기 보고]

**점진 코드 생성 · 링크는 아직 어렵다.** Zig 0.16.0에서도 점진 컴파일은 "잘못된 코드 생성을 포함한 알려진 버그" 때문에 기본으로 꺼져 있다. 한 줄 바꾼 뒤 다시 빌드는 새 ELF 링커로 65ms였지만, 그 링커는 디버그 정보 없는 실행 파일을 만든다(https://ziglang.org/download/0.16.0/release-notes.html). [원문] Zig 0.15.1은 "코드를 내지 않고 에러만 보기"와 함께일 때만 점진 컴파일을 믿고 쓸 만하다고 적었다. [원문]

**점진 엔진을 바꾸는 일은 비싸다.** rust-analyzer를 새 Salsa로 옮긴 변경 요청 하나만 약 7주가 걸렸다(2025-01-17 → 03-10, 추가 3,072줄 · 삭제 2,323줄 · 파일 163개). 이름 바꾸기부터 마지막 판 올리기까지는 2024-10 → 2025-12, 약 14개월이었다. 자기 자신 분석 기록은 141.5초 · 1,895MB(2025-03-01)에서 167.6초 · 2,877MB(2025-04-01)로 튀었다가 67.9초 · 1,391MB(2026-01-02)가 됐다. 다른 변경도 섞여 원인을 Salsa 하나로 돌릴 수는 없다(https://github.com/rust-lang/rust-analyzer/pull/18964, https://github.com/rust-analyzer/metrics). [원문, 직접 셈] Salsa는 2018년에 시작했고 아직 0.x(0.28.5, 2026-09-24)다. 취소 · 메모리 축출 동작은 문서가 얇다. [원문]

**Go의 깨끗한 빌드 기준선을 이 조사에서 직접 쟀다.** Go 1.27.1 표준 라이브러리 전체(테스트 아닌 `.go` 918,980줄)를 빈 캐시에서 빌드하니 6.33 · 7.00 · 8.33초였다. Apple M4 10코어 · 16GB, 실행 파일 링크는 없다. 벽시계 기준 초당 약 11만~14.5만 줄이다. [원문, 직접 측정] Go의 공식 "초당 줄 수"는 없다. 합성 벤치마크(한 파일에 함수 4만 개)에서는 함수당 빌드 시간이 Go 403µs, rustc 184µs, Zig 89µs, tcc 3µs로 순위가 뒤집힌다([컴파일 속도 합성 벤치마크](https://github.com/nordlow/compiler-benchmark)). [원문] Jai · Odin · Carbon의 속도 숫자는 남이 재현할 수 없는 주장이거나 아예 없다. [원문 · 2차]

**언어 설계가 IDE 속도를 정한다.** rust-analyzer 저자(2020)는 빠른 IDE를 위한 언어 조건으로, 최상위 이름을 파일 하나에서 알 수 있을 것, 최상위 선언을 만들어 내는 메타프로그래밍을 금지하거나 제한할 것, 이름 해석이 대부분 완전한 이름으로 끝날 것을 꼽았다(https://rust-analyzer.github.io/blog/2020/07/20/three-architectures-for-responsive-ide.html). [원문] 반대 사례로 Swift 6 타입 검사기는 12줄짜리 문자열 이어 붙이기 식에 42초를 쓰고 "unable to type-check this expression in reasonable time"으로 실패했다. 고친 식은 0.19초였다. 원인은 표준 라이브러리의 `+` 오버로드 17개와 양방향 제약 풀이의 지수적 탐색이다([Swift 타입 검사기 글](https://danielchasehooper.com/posts/why-swift-is-slow/)). [원문, 블로그] rust-analyzer의 처음부터 전체 분석 95.8초 가운데 타입 추론이 64.8초(약 68%)였다. [원문, 직접 셈]

**오류에 강한 파싱은 선례가 있다.** LR 파서 오류 복구 논문(ECOOP 2020, 동료 심사)은 실제 문법 오류가 있는 Java 프로그램 20만 개 가운데 98.37%를 0.5초 안에 고쳤고, 보고한 에러 위치가 기존 방식보다 약 56% 적었다(https://arxiv.org/abs/1804.07133). [원문, 초록] 이 방식을 쓰는 grmtools 문서는 수정안을 못 찾는 입력이 "실제 입력의 2% 미만"이라고 적었다. [원문] tree-sitter 문법은 GitHub 코드 탐색, Helix(문법 303개), Neovim(약 323개)이 쓴다. [원문, 직접 셈]

**사람이 실제로 기다리는 것도 검사다.** Rust 컴파일러 성능 설문(2025, 응답 3,700명 넘게)에서 55%가 가장 큰 프로젝트에서 다시 빌드에 10초 넘게 기다렸고, 약 87%가 편집기 안 표시로 에러를 봤다. Rust를 그만둔 응답자의 약 45%가 긴 컴파일 시간을 이유 중 하나로 들었다(https://blog.rust-lang.org/2025/09/10/rust-compiler-performance-survey-2025-results). [원문]

**계획에 주는 뜻**
- 헌장의 "한 파일 고친 뒤 다시 검사 1초 이내"를 `check` · `check_partial`(검사만)에 대한 목표로 정의하고, "다시 빌드"는 따로 숫자를 정한다. 점진 코드 생성은 1.0 전 필수 범위에서 뺀다. 함수 단위 병렬 코드 생성 + 빠른 링커로 깨끗한 빌드를 먼저 노린다(추론).
- 2027년 1월 첫 컴파일러 뼈대부터 질의 기반으로 짓는다. 정규형 해시 · 권한 · 오염 · 경계 검사 · JSON 진단을 모두 추적 함수로 두면 "결과가 같으면 다시 계산하지 않기"가 그대로 먹힌다. Salsa 판은 고정하고 분기마다 올린다.
- 권한을 추론하지 않고 시그니처에 선언하게 한 결정이 1초 목표에도 필요하다. 본문을 고쳐도 시그니처가 그대로면 호출자를 다시 검사하지 않는다(추론).
- 메모리 · 시간 회귀를 매 커밋 재는 기록판(rust-analyzer 방식)을 2027년 1분기에 만든다. AI는 검사기를 여럿 띄우므로 검사기 하나의 메모리도 목표에 넣는다.
- 단계별 시간 예산(파싱 · 이름 해석 · 타입 · 보안 분석 · 코드 생성 · 링크)을 2027년 1분기에 정하고 매 커밋 잰다. SMT 계약 검증은 깨끗한 빌드 예산을 쉽게 깨므로, 정의 해시로 결과를 캐시하고 "검증 빌드"와 "개발 빌드"를 나눌지 정한다.
- Go 기준선은 2026년 11~12월에 같은 기계에서, 실제 모양의 코드(표준 라이브러리 · 웹 서버 예제)로, 링크 포함 · 제외를 나눠 잰다.
- 2027년 1~6월 문법 · 타입 설계 점검표에 "최상위 이름은 파일 하나로 결정", "메서드 · 구현 찾기는 정해진 위치에서만", "리터럴은 기본 타입 하나"를 넣는다.
- LR 문법 파일을 명세이자 시험 기준으로 두고, 손으로 짠 회복형 파서와 grmtools 파서를 2027년 1~2월에 같은 오류 말뭉치로 비교해 고른다. 0.5초 시간 제한은 1초 예산의 절반이라 더 줄여야 한다. 편집기 · AI 도구용 구문 조회는 공개 LR 문법에서 tree-sitter 문법을 만들어 얻는다.

## 메모리 모델과 동시성: 후보마다 런타임 공수가 10배 갈린다

**참조 카운트(Perceus 계열)는 시제품 공수가 가장 작다.** 카운트 삽입 · 재사용 · 빌림 추론 패스가 Koka 2,088줄, Lean 4 1,918줄이다. Roc은 같은 일에 검증 단계까지 붙여 41,684줄(약 20배)이다. [원문, 직접 셈] Perceus 논문(PLDI 2021, 동료 심사)에서 순수 함수형 Koka의 레드블랙 트리는 제자리 갱신하는 C++ `std::map`의 10% 안이었고, Java는 비슷한 속도에 메모리를 약 10배 썼다. "no runtime system is needed"라서 Cranelift · LLVM · C 어느 출력에도 스택 맵 없이 붙는다(https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf). [원문] 대신 순환은 언어가 막아야 한다. Koka는 가변 참조로 생기는 순환을 프로그래머 몫으로 남겼고, Lean 4의 검증 가능한 부분과 Roc("By design, Roc has no way to express reference cycles")은 순환을 아예 만들 수 없게 했다. Nim은 순환 수집기(ORC)를 붙였다. JSON 약 135MB를 든 비동기 서버가 10요청마다 전체 수집하는 조건에서 평균 지연이 320.49µs로, mark&sweep의 65.31ms보다 훨씬 짧았다(https://nim-lang.org/blog/2020/12/08/introducing-orc.html). [원문]

**원자적 카운트 비용은 크고, 데이터 경쟁 방지 타입 정보로 줄일 수 있다.** Biased Reference Counting 논문(PACT 2018, 동료 심사)에서 Swift 클라이언트 프로그램은 실행 시간의 평균 42%, 서버 프로그램은 15%를 참조 카운트 연산에 썼고, 대부분이 원자 비교-교환 때문이었다(https://iacoma.cs.uiuc.edu/iacoma-papers/pact18.pdf). [원문] Lean은 값을 단일 스레드 · 다중 스레드로 나누는데, 모든 값을 다중 스레드로 다루면 1.13~2.31배 느려졌다(IFL 2019, https://arxiv.org/abs/1908.05647). [원문]

**추적 GC는 "작동하는 시제품"과 "보안 등급" 사이가 가장 멀다.** Cranelift의 새 스택 맵(2024-09-10)은 살아 있는 GC 값의 저장 · 재적재와 표시를 언어 쪽이 짜게 한다([Cranelift 새 스택 맵 글](https://fitzgen.com/2024/09/10/new-stack-maps-for-wasmtime.html)). Wasmtime 47(2026-07-20)이 GC를 기본으로 켰다. 수집기는 단순한 반공간 복사 방식이고, 처리량은 V8 · SpiderMonkey에 "won't match"라고 스스로 적었으며, 작업량은 "years of engineering effort"였다(https://bytecodealliance.org/articles/wasmtime-gc). [원문] Wasmtime 보안 공지 81건 가운데 GC 참조 관련이 8건이고, 2026-10-02에도 "rooting for GC values ... may be missing, causing GC heap corruption" 공지가 나왔다(https://github.com/bytecodealliance/wasmtime/security/advisories). [원문] Wasmtime API 문서의 복사 수집기 항목에는 "not yet functional"이라는 문장이 남아 블로그와 어긋난다. 어느 쪽이 최신인지 확인하지 못했다.

**GC를 빌려 쓰는 길(MMTk)도 바인딩과 뿌리 열거는 도담 몫이다.** mmtk-core는 Rust 58,376줄이고, 언어별 바인딩은 Rust 2,396~5,358줄에 런타임 쪽 수정이 더해진다. [원문, 직접 셈] 이식 안내서는 "We always start a port with NoGC"라고 하고, V8은 NoGC만 돌리는 데도 파일 100개 넘게를 고쳤다고 적었다. Ruby의 첫 MMTk 판은 "almost 4x slower than the default GC"였다(https://bugs.ruby-lang.org/issues/20860). [원문] 이식 기간 숫자는 공개된 것이 없다.

**소유권 검사를 Rust 수준으로 정밀하게 만드는 데 수년이 걸렸다.** 새 빌림 검사기(NLL)는 Rust 2018 판(1.31)에 들어왔지만 모든 코드가 그것으로 검사된 것은 1.63(2022-08)이었다. 담당자는 이 정리를 "a long, tedious, and largely thankless process"라고 했다(https://blog.rust-lang.org/2022/08/05/nll-by-default/). 더 정밀한 Polonius는 2018년에 갈라져 나왔고, 2026년 목표에도 날짜가 없으며 "10–20%" 성능 비용을 감수하겠다고 적었다(https://goals.rust-lang.org/2026/polonius.html). [원문]

**가변 값 의미론(Hylo)은 빌릴 실전 구현이 없다.** 옛 저장소 README 첫 줄이 "Outdated Implementation of Hylo"이고, 새 컴파일러는 v0.0.1(2026-05-09)에서 v0.0.9(2026-09-11, LLVM 23으로 올림)까지 왔다(https://github.com/hylo-lang/hylo-new). [원문] 2024년 기준 디버그 정보를 내지 않았다. [2차] 논문은 이 방식이 경쟁할 수 있는지를 열린 질문으로 남겼다(https://arxiv.org/abs/2106.12678). [원문, 초록]

**데이터 경쟁 방지를 나중에 켜면 생태계가 1년 넘게 못 따라온다.** Swift Package Index(패키지 3,395개, 엄격 동시성 검사)에서 데이터 경쟁 오류가 0인 패키지는 38.1%(2024-05-04) → 47.8%(2024-11-07) → 59.7%(2025-05-07)였다(https://swiftpackageindex.com/ready-for-swift-6). [원문, 직접 추출] Swift의 공식 비전 문서는 "Writing a single-threaded program is surprisingly difficult under the Swift 6 language mode"라고 인정했고, 많은 프로그래머가 반사적으로 `@MainActor`를 붙인다고 적었다(https://github.com/swiftlang/swift-evolution/blob/main/visions/approachable-concurrency.md). [원문] Telefónica는 100만 줄 넘는 앱을 옮기며 표기 3,000개 넘게를 더하고 400개 넘는 타입을 `@unchecked Sendable`로 표시했다. [원문, 자기 보고] 실행 중에 잡는 Go 경쟁 탐지기는 메모리 5~10배 · 시간 2~20배가 들고 실행된 경로만 잡는다. Uber(PLDI 2022, 동료 심사)는 Go 4,600만 줄에서 6개월 동안 데이터 경쟁 2,000건 넘게를 찾았다(https://go.dev/doc/articles/race_detector, https://arxiv.org/abs/2204.00764). [원문]

**동시성 런타임은 "런타임이 모르는 대기"에서 사고가 났다.** [원문 · 2차]
- Java 가상 스레드는 JDK 21에 확정됐지만, `synchronized` 안에서 캐리어 스레드에 고정되는 문제를 JDK 24에서야 거의 없앴다(https://openjdk.org/jeps/491). Netflix에서는 가상 스레드 4개가 캐리어를 모두 차지해 서비스가 멈췄다. [2차] 구조적 동시성 API는 JDK 19부터 JDK 26까지 인큐베이터 · 미리보기로만 있다(https://openjdk.org/jeps/525).
- Rust는 trait 안 async 함수의 반환값에 "스레드 사이로 보내도 된다"는 조건을 걸 수 없는 문제를 2026년 말 안정화를 목표로 아직 풀고 있다(https://goals.rust-lang.org/2026/rtn.html).
- 한 번만 재개하는 효과 처리기(OCaml 5, PLDI 2021, 동료 심사)는 효과를 쓰지 않는 실제 프로그램 54개에서 기하평균 1% 미만 느렸고, 코드 크기는 19% 늘었다(https://arxiv.org/abs/2104.00250).
- Go 고루틴은 최소 스택 2,048바이트로 시작하고 신호로 선점되지만, WASM 대상에서는 선점이 안 된다(https://go.dev/doc/go1.14).
- 서버 I/O는 tokio + hyper를 호스트로 쓰는 길이 검증돼 있다(Deno, Roc 웹 서버 플랫폼). 자체 액터 런타임 Lunatic은 2023-05 릴리스 뒤 사실상 멈췄다(https://github.com/lunatic-solutions/lunatic).

**브라우저에서 스택 전환은 아직 표준 기능이 아니다.** 외부 비동기 호출을 멈춤으로 바꾸는 JSPI는 Chrome 137 · Firefox 153(2026-07-21) · Safari 27에 있지만, Wasm 안에서 스택을 바꾸는 stack switching은 표준화 5단계 중 3단계이고 Chrome 플래그 뒤에만 있다(https://github.com/WebAssembly/website/blob/main/features.json). [원문] 변환으로 흉내 내면 비싸다. 코루틴 1천만 개 모사에서 Asyncify 방식은 바이너리 9.2KB · 700ms, 손으로 짠 상태 기계는 0.9KB · 140ms였다(OOPSLA 2023, https://arxiv.org/abs/2308.08347). [원문]

**계획에 주는 뜻**
- 메모리 모델과 동시성 모델(스택 있는 방식이냐 아니냐)을 2027년 1~2월에 한 결정으로 묶는다. 둘이 코드 생성(스택 맵), WASM 출력, 원자 · 비원자 카운트 결정까지 함께 정한다.
- 시제품 비교는 "튜닝 전"끼리라 실행 속도로 판정하지 않는다(Ruby MMTk 첫 판 약 4배 느림, Koka 최적화 끈 판 2배 넘게 느림). AI 정확도 · 탄탄함의 비중을 높이고 속도는 "튜닝 여지"로 따로 적는다.
- 참조 카운트를 고르면 "순환 불가 규칙"(가변 참조 셀을 없애거나 arena · 인덱스로 대신)과 "순환 수집기" 중 하나를 같이 고른다. 순환 불가 규칙이 그래프 · 부모 포인터 같은 과제에서 AI 정확도를 떨어뜨리는지 시제품 과제에 넣는다. 시제품 공수는 패스 약 2천 줄 규모로 잡는다.
- 추적 GC를 고르면 2027년 1~2월 시제품은 움직이지 않는 단순 수집기로 하고, 1월 첫 주에 MMTk NoGC 포트로 실제 공수를 잰다. 정확성 퍼저를 같은 묶음에 넣고, 2028년 표준 라이브러리 시기까지 GC 퍼징 · 감사 공수를 따로 잡는다.
- 소유권을 고르면 1.0까지 Rust만큼 정밀한 검사기는 목표로 두지 않고, 시그니처 수명 표기 없이 판정되는 단순 규칙으로 범위를 묶는다. 가변 값 의미론은 일정 위험이 가장 크다고 적어 둔다.
- 기본은 단일 스레드 격리, 병렬은 명시로 시작한다(Swift 6.2가 뒤늦게 간 방향). 거짓 양성률 · 표기 수 · 탈출구 사용 수를 벤치마크 지표로 잰다. 동시성 규칙은 0.1 전에 확정한다.
- 구조적 동시성은 처음부터 범위 안 작업만 두고, 막히는 호출 · 외부 함수 호출을 권한으로 드러내며, 동시 실행 상한을 자원 한도처럼 선언하게 한다. 어느 작업이 무엇을 기다리는지 보는 진단을 런타임에 처음부터 넣는다.
- "멈출 수 있음"을 권한 하나로 다룰지를 2027년 상반기 문법 설계 항목으로 둔다(추론, 측정 자료 없음).
- 서버 I/O는 tokio 위에 얇게 얹는 것을 기본안으로 하고 자체 스케줄러는 측정 뒤에만 짓는다. 브라우저는 JSPI 경로와 옛 Safari용 CPS 대체 경로를 함께 설계한다.

## 브라우저 출력과 서버 · 화면 한 소스: 속도보다 번들 크기와 첫 화면이 약점이다

**WasmGC · 꼬리 호출 · 예외 처리는 세 브라우저가 모두 기본으로 켠다.** webassembly.org 기능 표의 데이터 파일(2026-10-21 갱신)에서 뽑았다(https://github.com/WebAssembly/website/blob/main/features.json). [원문]

| 기능 | Chrome | Firefox | Safari |
|---|---|---|---|
| GC(WasmGC) | 119(2023-10-31) | 120(2023-11-21) | 18.2(WebKit 글 2024-12-09, JetBrains 글은 2024-12-11) |
| 꼬리 호출 | 112 | 121 | 18.2 |
| 예외 처리(최종안) | 137(2025-05-27) | 131 | 18.4 |
| JS 문자열 내장 함수 | 130 | 134 | 26.2 |
| JSPI | 137 | 153(2026-07-21) | 27 |
| 스택 전환 | 플래그 필요 | 없음 | 없음 |
| Component Model | 없음 | 없음 | 없음 |

Safari는 WasmGC를 Chrome보다 약 13개월 늦게 지원했다. Safari 26.2 · 27의 정확한 출시일은 Apple 원문으로 확인하지 못했다.

**GC 언어를 WasmGC로 브라우저에 낸 제품 선례가 있다. 첫 판은 느렸다.** Google Sheets 계산 엔진(Java → WasmGC)은 첫 판이 JS보다 약 2배 느렸고, 추측 인라이닝 등으로 최종판이 JS의 약 2배 속도가 됐다(첫 판보다 4배 개선). 정규식을 브라우저 내장 RegExp로 바꾸자 정규식 연산이 약 100배 빨라졌다(https://web.dev/case-studies/google-sheets-wasmgc). [원문, 자기 보고] Flutter 웹의 Wasm 판은 애니메이션 장면 프레임 시간이 34.5ms에서 17.4ms가 됐다(https://flutter.dev/blog/try-flutter-web-with-webassembly-week). [원문, 자기 보고] Kotlin/Wasm은 2026-09 문서에도 아직 Beta다. [원문]

**Wasm 화면 프레임워크는 React보다 빠르지만, 번들과 첫 페인트가 진짜 약점이다.** js-framework-benchmark(Chrome 156, keyed 구현 201개, 2026-10-25 결과)를 조사 에이전트가 사이트 계산식대로 다시 계산했다. CPU 점수는 1.00이 가장 빠르다([js-framework-benchmark](https://github.com/krausest/js-framework-benchmark)). [원문, 계산]

| 구현 | 언어 | CPU 점수 | 압축(brotli) 크기 | 첫 페인트 |
|---|---|---|---|---|
| vanillajs | JS | 1.02 | 2.5KB | 40.7ms |
| wasm-bindgen(손으로 DOM 조작) | Rust/Wasm | 1.11 | 14.5KB | 76.4ms |
| Solid 1.9.3 | JS | 1.14 | 4.5KB | 53.5ms |
| Svelte 5.42.1 | JS | 1.19 | 9.7KB | 65.5ms |
| Dioxus 0.7.2 | Rust/Wasm | 1.30 | 114.9KB | 536.9ms |
| Leptos 0.7.0 | Rust/Wasm | 1.31 | 48.8KB | 236.4ms |
| Elm 0.19.1 | Elm(JS 출력) | 1.40 | 10.4KB | 66ms |
| React hooks 19.2.0 | JS | 1.56 | 51.4KB | 228.1ms |
| Blazor Wasm 10.0.0 | C#/Wasm | 4.88 | 1,377KB | 70.2ms |

손으로 DOM을 다룬 Rust(1.11)와 vanillajs(1.02)의 차이로 보면, JS 연결 코드를 거치는 비용은 이 벤치마크에서 약 9%다(계산). Kotlin/Wasm · MoonBit · Flutter 구현은 이 벤치마크에 없다.

**WASI 0.3은 나왔지만 1.0은 날짜가 없다.** WASI 0.3.0은 2026-06-11에 나왔고 async를 Component Model 자체로 옮겼다. 0.3.9(2027-12-14)까지 두 달 간격 계획이 있다. WASI 1.0은 목표 날짜도 조건도 없다(https://wasi.dev/roadmap). Wasmtime 46(2026-06-22)이 최종 0.3.0을 처음 구현했다. [원문] Component Model은 W3C 표준화 첫 단계이고 지원하는 브라우저가 없다. [원문]

**서버 · 브라우저 갈림은 지금 모두 사람이 표시한다.** Gleam은 `@target`과 대상별 `@external`로 가르고, 지금 빌드하는 대상의 구현이 없으면 컴파일 에러를 낸다(https://tour.gleam.run/advanced-features/multi-target-externals/). Kotlin Multiplatform은 source set, Leptos · Dioxus는 Cargo feature, Next.js는 `"use server"` · `server-only`를 쓴다. [원문] 실패는 네 갈래로 나타났다. 서버 크레이트가 섞인 WASM 빌드 에러, 브라우저 전용 크레이트의 네이티브 실행 중 panic, 서버 데이터를 화면 컴포넌트에 통째로 넘기는 과다 노출, 서버 함수 역직렬화 취약점이다(https://dioxuslabs.com/learn/0.6/guides/fullstack/managing_dependencies, https://nextjs.org/docs/app/guides/data-security). [원문] Leptos 문서는 32비트 WASM과 64비트 서버 사이에서 `isize` · `usize`가 역직렬화 에러를 낼 수 있다고 경고한다(https://book.leptos.dev/server/25_server_functions.html). [원문] Kotlin Multiplatform은 공유 코드가 Stable(2023-11)이 된 지 3년이 지나도 웹(Wasm) 대상은 Beta다(https://kotlinlang.org/docs/multiplatform/supported-platforms.html). [원문 · 2차]

**권한으로 실행 위치를 자동으로 정한 선례는 연구 언어뿐이다.** Swift(SOSP 2007, 동료 심사, Apple의 Swift와 다른 연구 시스템)는 Jif 프로그램을 보안 라벨에 따라 서버 Java와 브라우저 JavaScript로 자동 분할했다. 컴파일러는 Jif 위에 약 2만 줄이었고, 서버 → 클라이언트 메시지 수가 손으로 짠 최적과 같거나 거의 같았다. 비밀 요구가 바뀌면 라벨 한 줄만 고쳐 자동 재분할됐다(https://www.cs.cornell.edu/andru/papers/swift-sosp07.pdf). [원문]

**계획에 주는 뜻**
- 2027년 상반기 WASM 출력은 GC · 꼬리 호출 · 예외 처리를 전제로 한다. 새 기능은 Safari 지원 판을 기준으로 일정을 잡는다.
- 첫 화면은 서버가 그린 HTML로 띄우고 Wasm은 뒤에 붙인다. 벤치마크의 "브라우저 번들 크기" 지표에 압축 크기와 첫 페인트를 함께 넣는다. 화면 출력 목표를 "CPU 점수 1.2 이하"로 잡을 근거가 있다. 런타임을 통째로 싣는 방식(Blazor, 압축 1.4~3MB)은 피한다.
- 메모리 모델이 브라우저 출력에 직접 묶인다. 추적 GC면 WasmGC에 GC를 맡겨 작은 바이너리가 가능하고, 참조 카운트 · 소유권이면 선형 메모리 + 자체 할당기로 간다(Rust 프레임워크처럼 압축 44~115KB)(추론).
- DOM 변경을 모아 한 번에 넘기는 배치 방식을 처음부터 넣는다. 정규식 · 문자열은 브라우저 내장 기능에 맡긴다. 첫 판은 느리다고 보고 성능 튜닝 기간을 따로 잡는다.
- 브라우저 출력과 화면 런타임은 서버보다 긴 안정화 기간과 별도 위험 항목으로 잡는다.
- 서버 격리 실행은 Wasmtime 46 이후 · WASI 0.3 위에 짓고, 도담 권한 선언을 WIT 인터페이스와 런타임 허용 목록에 대응시키는 설계를 한다. WASI 판을 고정하고 두 달마다 나오는 판을 따라가는 반복 작업을 둔다. 브라우저 출력은 Component Model이 아니라 core Wasm + JS 연결 코드로 간다.
- 정수 타입의 폭을 실행 대상과 무관하게 명세에 고정한다.
- 권한으로 실행 위치를 정하는 것은 선례가 적은 길이다. 서버에 둘 것을 화면에 넣는 오판을 막는 검사기와 시험 과제를 따로 잡는다. 더 큰 일은 자동 생성되는 경계 코드(엔드포인트 · 직렬화 · 검증 · CSRF 방어)의 정확성과 보안 시험이다.

## 보안 장치 선례: 실행 중 검사는 같은 자리에서 거듭 뚫렸고, 타입 규칙은 강제할 때만 효과가 있었다

### 효과 · 권한 타입은 2026년에도 연구 단계다

**효과(부수효과 · 권한)를 타입에 적는 언어는 모두 연구 · 실험 단계다.** Scala 3의 capture checking은 3.8(2026-01-22)에서도 "실험 기능"이다(https://scala-lang.org/news/3.8/). Koka · Effekt · Flix는 판을 매달 · 매주 내는 0.x 연구 언어이고, Austral은 2023년 뒤 멈췄다(https://github.com/austral/austral). [원문] 고차 함수는 세 방식으로 푼다. 효과 변수(Koka의 `e`, Flix의 `\ ef`), 함수를 2급 값으로 두고 명시적으로 상자에 담기(Effekt), "아무 권한이나 잡음"을 기본으로 두기(Scala `=>`)다(https://doc.flix.dev/effect-polymorphism.html, https://effekt-lang.org/tour/captures). [원문]

**자원 범위(호스트 · 경로 · 테이블)를 효과 타입에 담은 선례는 이 조사 범위에 없다.** Flix는 효과 이름(파일 읽기 · 쓰기 등)까지만 나눈다. Austral · Pony · Joe-E는 범위를 권한 "값"(경로 객체 · 연결 권한 객체)으로 넘긴다(https://austral-lang.org/spec/spec.html, https://tutorial.ponylang.io/object-capabilities/object-capabilities.html). 도담의 `Net(host)` · `Fs(path)` · `Db(table, …)`는 "효과 집합 + 자원 인자"라는 새 조합이라 건전성 검증 부담이 커진다(추론).

**기본값을 잘 고르면 표기는 거의 늘지 않는다.** Scala 컬렉션 약 3만 줄을 capture checking으로 옮길 때 바꾼 줄은 5% 미만이었고, 함수 시그니처의 약 90%가 그대로였다(OOPSLA 2025, 동료 심사, https://arxiv.org/html/2509.07609). [원문]

**고차 함수에서 권한을 다형으로 넘기지 못하면 생태계가 두 극단으로 쏠린다.** Java는 제네릭이 검사 예외를 추상화하지 못해 콜백 라이브러리가 "아무것도 못 던짐"(Runnable)이나 "모두 던짐"(Callable)으로 쏠렸고, 출시된 Java 8의 `Function.apply`에는 throws 절이 없다(https://mail.openjdk.org/pipermail/lambda-dev/2010-June/001484.html). Swift는 typed throws를 Swift 6.0에 넣고도 제안서에서 "대부분 경우 untyped throws가 낫다"고 권했다(https://github.com/swiftlang/swift-evolution/blob/main/proposals/0413-typed-throws.md). [원문] Joe-E(NDSS 2010, 동료 심사)는 가장 큰 어려움이 권한 원칙으로 짜는 훈련이었고, 기존 라이브러리 길들이기에서 권한 규칙을 어기는 메서드가 실수로 허용돼 있었다고 적었다([Joe-E 논문](https://people.eecs.berkeley.edu/~daw/papers/joe-e-ndss10.pdf)). [원문]

**LLM이 효과 표기 언어로 짤 때의 정확도 숫자는 찾지 못했다.** Unison은 AI 도구 연결 서버를 냈지만 정확도를 공개하지 않았다. [원문]

### 실행 중 권한 검사는 같은 자리에서 거듭 뚫렸다

**Deno 보안 공지 40건(2021-05~2026-06) 가운데 21건이 권한 검사나 권한 프롬프트 우회였다(조사 에이전트의 분류).** 갈래는 프롬프트 위조 5, Node 호환층 6, 거부 규칙 처리 오류 7, 경로 정규화 · 특수 파일 3, 외부 함수 호출 1, 모듈 적재 1이다(일부 겹침, https://github.com/denoland/deno/security/advisories). [원문] 2026년 예:
- macOS 파일 시스템은 유니코드 표기 · 대소문자가 다른 이름을 같은 파일로 보는데, Deno는 거부 규칙을 바이트 단위로 비교했다. 거부된 파일을 다른 표기로 열면 읽혔다(2026-05 수정, 심각도 7.3).
- `fetch()`와 WebSocket은 호스트 이름만 검사하고 해석된 IP를 다시 검사하지 않았다(2026-05 수정). Node 호환 TCP 경로는 `2130706433` 같은 숫자 표기로 `127.0.0.1` 차단을 피했다.
- 그 전에는 `/proc/self/mem` 쓰기가 "모든 권한"과 같아서, Deno 1.43부터 `/etc` · `/dev` · `/proc` 접근에 모든 권한을 요구한다.

**Node.js 권한 모델은 문서에서 스스로 "This feature does not protect against malicious code"라고 적었다(https://nodejs.org/api/permissions.html).** 보안 작업반 자료에서 권한 모델 우회는 28건이었다(취약점 번호 연도 기준 2023년 8 · 2024년 5 · 2025년 3 · 2026년 12). 검사가 빠진 API, 경로 정규화, 상대 심볼릭 링크로 허용 경로 탈출, Unix 도메인 소켓이 네트워크 허용을 건너뜀 같은 것이었다(https://github.com/nodejs/security-wg/tree/main/vuln/core). [원문, 직접 셈]

**Wasmtime의 WASI 파일 샌드박스도 2026년에 뚫렸다.** 읽기 전용 디렉터리에서 잘라내기 플래그로 쓰기 검사를 건너뛴 것(심각도 7.5), 하드 링크 · 이름 바꾸기로 덮어쓴 것(6.5), 경로 끝의 `/` 때문에 샌드박스를 완전히 탈출한 것(높음, 뿌리는 cap-std)이다(https://github.com/bytecodealliance/wasmtime/security/advisories). [원문] 이 숫자를 한 노트는 셋으로, 다른 노트는 넷으로 적었다.

**언어 전체에 세밀한 권한을 건 Java Security Manager와 .NET CAS는 폐지됐다.** JDK 24는 Security Manager를 영구히 껐다. 권한을 검사하는 메서드가 1,000개 넘게, 권한을 올리는 메서드가 1,200개 넘게였고, 지울 코드가 5만 줄 넘게였다. 이유는 "the permission scheme is so complex that the Security Manager has always been disabled by default", 쓴 곳도 대부분 모든 권한을 줬다는 것, 새 API마다 이 모델을 염두에 둔 설계 · 검토 비용이었다(https://openjdk.org/jeps/486). [원문] .NET은 "CAS is no longer treated as a security boundary"라고 적었다(https://learn.microsoft.com/en-us/dotnet/core/porting/net-framework-tech-unavailable). [원문]

**Go Capslock 문서는 데이터 경쟁이 권한 분석을 무력화한다고 적었다.** 인터페이스 · 슬라이스 변수의 데이터 경쟁은 unsafe 없이도 "calling library functions with any capability"를 일으킬 수 있고, 도구는 이를 알려 주지 않는다(https://github.com/google/capslock/blob/main/docs/caveats.md). [원문]

### 출력 타입은 검사기가 강제할 때만 효과가 있다

**Google은 안전 타입과 "컴파일 시점 상수만 받기" 규칙으로 XSS · SQL 인젝션을 "거의 없앴다"고 스스로 보고한다.** 초록에는 숫자가 없다([Google 안전 코딩 논문 목록](https://research.google/people/christophkern/)). [원문, 자기 보고] 고신뢰 웹 프레임워크를 다 적용한 "수백 개" 서비스에서 XSS가 Google 전체로 한 해 약 1건이라는 글이 있다. [2차, 본문이 열리지 않음]

**구현은 작다.** Go safehtml · safesql은 내보내지 않은 타입을 매개변수로 받아 "문자열 리터럴이나 타입이 정해지지 않은 문자열 상수만" 넘길 수 있게 했다(https://pkg.go.dev/github.com/google/go-safeweb/safesql). Error Prone의 컴파일 시점 상수 검사는 허용 식 목록 하나다. [원문] 그러나 보장에는 전제가 있다. safesql은 탈출구 패키지를 쓰지 않고 표준 `database/sql`을 금지해야만 성립하는데, 금지를 강제하는 장치는 문서에 없다. [원문] Error Prone은 이 표시가 붙은 매개변수의 람다 · 메서드 참조를 막는다. 나중에 상수로 불리는지 알 수 없어서다(https://errorprone.info/bugpattern/CompileTimeConstant). [원문]

**표기를 받고도 검사하지 않으면 보장이 조용히 사라진다.** Python의 LiteralString 제안은 Final 상태지만, 2026-10 typing 적합성 시험에서 mypy는 "Unsupported"이고, mypy 이슈는 2022-04-09부터 열려 있다. typeshed의 sqlite3 `execute`는 아직 `sql: str`을 받는다(https://github.com/python/typing/tree/main/conformance/results, https://github.com/python/typeshed/blob/main/stdlib/sqlite3/__init__.pyi). [원문]

**탈출구 사용 기준선.** crates.io crate 약 127,000개 가운데 19.11%가 `unsafe`를 직접 쓰고, 34.35%가 `unsafe`를 쓰는 다른 crate의 함수를 부른다. 대부분은 C · C++ 라이브러리 호출용이다(https://rustfoundation.org/media/unsafe-rust-in-the-wild-notes-on-the-current-state-of-unsafe-rust/). [원문, 재단 자료] ICSE 2020(동료 심사)은 `unsafe`를 쓰는 라이브러리는 30% 미만이지만 호출 사슬 때문에 절반 넘게가 완전히 정적 검사되지 않는다고 했다(https://arxiv.org/abs/2007.00752). [원문, 초록]

### 오염 추적은 고정 정책만 실무에서 살아남았다

**일반 정보 흐름 타입은 채택에 실패했다.** 2004년 입장 논문은 정보 흐름 강제 장치가 "널리(심지어 좁게도!) 쓰인 적이 없다"고 하고 장벽 셋을 꼽았다. 기존 시스템과의 통합, 너무 엄격한 비간섭, 금세 감당 못 할 만큼 늘어나는 정책 관리다. 가장 널리 쓰인 장치는 동적이고 건전하지도 않은 Perl taint 모드였는데 "많은 보안 위반을 막는 데 성공한 듯하다"고 했다([정보 흐름 보안 입장 논문](https://www.cis.upenn.edu/~stevez/papers/Zda04.pdf)). [원문]

**표기 부담과 실행 비용이 컸다.** Jif 위의 웹 프레임워크 SIF(USENIX Security 2007, 동료 심사) 사례 앱에서 코드 줄의 약 21~31%에 라벨 표기가 붙었고, 기능 하나에 낮추기(downgrade) 표기가 평균 4.6개 흩어졌다. 동적 라벨 검사로 처리량이 최대 29% 줄었다. 새 사용자가 가장 자주 빠진 함정은 예외가 만드는 암묵 흐름이었다(https://www.usenix.org/legacy/event/sec07/tech/full_papers/chong/chong.pdf). [원문] Hails(OSDI 2012)는 정책 API가 "배우기 어려웠고" 실제 유출 버그가 났다. Jif(2016) · Flow Caml · LIO(2020)는 모두 멈췄다. [원문]

**실무가 쓰는 것은 고정 정책 taint 분석이다.** Meta의 Pysa는 2020년 상반기 Instagram 서버 코드에서 엔지니어가 찾은 보안 문제의 44%를 찾았고, 보고한 고유 문제 330개 가운데 오탐이 150개(45%)였다(https://engineering.fb.com/2020/08/07/security/pysa/). [원문, 자기 보고]

### SSRF · 정규식 · 기본 한도

**SSRF 방어 라이브러리의 공통 설계는 "해석한 IP를 연결하는 순간 검사하고, 그 IP로 연결하고, 리다이렉트마다 다시 검사하는 것"이다.** OWASP는 "Deny-lists are bypass-prone. Prefer allow-lists"와 "Domain allowlisting alone does not prevent DNS rebinding"을 적고, 재시도 · 대체 연결에도 같은 정책을 걸라고 한다(https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html). [원문] Stripe Smokescreen은 Stripe의 나가는 트래픽 대부분을 이렇게 중계하고, 연결 시간 제한 기본값은 10초다. Ruby ssrf_filter는 교차 출처 리다이렉트 때 인증 · 쿠키 헤더를 기본으로 뗀다(https://github.com/stripe/smokescreen, [ssrf_filter](https://github.com/arkadiyt/ssrf_filter)). [원문]

**IP 문자열 판정 라이브러리는 비정규 표기로 거듭 뚫렸다.** npm `ip`는 `0x7F.1` 같은 표기의 사설 주소를 공개로 판정했고(2024-02), 고친 뒤에도 `127.1` · `01200034567` · `::fFFf:127.0.0.1` 등이 통과했다(2024-06). npm `private-ip`는 멀티캐스트 대역을 빠뜨렸고(2025-07, 고친 판 없음), npm `netmask`는 8진수 표기로 우회됐다. Python 표준 `ipaddress`(3.10 이하)와 Go 1.17 전의 `net.ParseIP`도 앞자리 0을 다르게 읽었다(GitHub 보안 공지 DB, [GitHub 보안 공지](https://github.com/advisories/GHSA-2p57-rm9w-gvfp)). [원문] 모두 "두 계층이 같은 문자열을 다르게 읽는" 문제였다(추론).

**선형 시간 정규식 엔진은 모두 역참조와 앞뒤 살피기(lookaround)를 포기했다.** RE2 · Rust regex · .NET NonBacktracking · V8 실험 엔진이 그렇다(https://github.com/google/re2/wiki/Syntax, https://docs.rs/regex/latest/regex/). [원문] npm · PyPI 생태계 연구(ESEC/FSE 2018, 동료 심사)에서 고유 정규식의 약 1%가 되추적 엔진에서 입력 길이에 대해 선형보다 느렸고, 그런 정규식을 담은 모듈은 npm의 3%였다([ESEC/FSE 2018 논문](https://davisjam.github.io/files/publications/DavisCoghlanServantLee-EcosystemREDOS-ESECFSE18.pdf)). [원문] 8개 언어 연구(ESEC/FSE 2019, 동료 심사)에서 정규식 537,806개 가운데 76%가 8개 언어 엔진 모두에서 유효했고, Rust를 빼면 88%였다. 개발자의 약 90%가 정규식을 인터넷에서 가져다 쓴다고 답했다([ESEC/FSE 2019 논문](https://davisjam.github.io/files/publications/DavisMichaelCoghlanServantLee-LinguaFranca-ESECFSE19.pdf)). [원문] 그러면 선형 엔진이 받지 않는 정규식은 많아야 약 12%다(계산, 추론).

**웹 프레임워크의 기본 한도는 제각각이고 "없음"도 흔하다.** [원문, 공식 문서 · 소스]

### 암호 · 비밀번호

**저수준 암호 API의 오용은 예외가 아니라 보통이다.** Android 앱 연구(CCS 2013, 동료 심사)에서 암호 API를 쓰는 앱 11,748개 가운데 10,327개(88%)가 실수를 하나 이상 했다(https://sites.cs.ucsb.edu/~chris/research/doc/ccs13_cryptolint.pdf). 규칙 묶음 CrySL로 본 앱 10,001개의 96%에 오용이 있었다(https://arxiv.org/abs/1710.00564). [원문]

**해법은 논스를 사용자 손에서 빼앗는 API다. 주류 언어도 이미 옮겼다.** Tink는 "AEAD 인터페이스는 논스 재사용을 막도록 설계됐다"고 하고 논스 인자를 없앴다(https://developers.google.com/tink/design/primitives_and_interfaces). libsodium은 192비트 논스라 무작위 논스를 안전하게 쓰는 XChaCha20-Poly1305를 권장 AEAD로 둔다. Go 1.24의 `NewGCMWithRandomNonce`는 논스를 스스로 만들되, 한 키로 2^32개 넘는 메시지를 암호화하면 안 된다(MUST NOT)고 적었다(https://pkg.go.dev/crypto/cipher#NewGCMWithRandomNonce). [원문]

**비밀번호 해시의 하한은 정해져 있다.** OWASP의 Argon2id 최소 설정은 메모리 19 MiB · 반복 2 · 병렬 1이고, 이 값은 2023-01-24에 정해진 뒤 바뀌지 않았다. "해시 계산은 대체로 1초 안에 끝나야 한다"와 "작업 계수가 너무 높으면 로그인을 몰아 CPU를 고갈시키는 서비스 거부에 쓰일 수 있다"도 적었다(https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). libsodium 대화형 기본값은 64 MiB · 반복 2다. IETF의 Argon2 표준 문서(2021-09)는 첫째로 반복 1 · 병렬 4 · 2 GiB, 메모리가 적으면 반복 3 · 병렬 4 · 64 MiB를 권한다. 미국 표준기술연구소(NIST)의 디지털 신원 지침은 비밀번호를 단일 인자로 쓰면 최소 15자, 최대 길이는 64자 이상을 허용하라고 하고, 해시 방식과 비용 계수를 함께 저장하라고 한다(https://pages.nist.gov/800-63-4/sp800-63b.html). [원문]

**bcrypt의 72바이트 함정은 실제 인증 우회 사고가 됐다.** Okta 위임 인증은 `userId + username + password`를 이어 bcrypt로 캐시 키를 만들었고, 사용자 이름이 52자 이상 등 조건이 겹치면 사용자 이름과 저장된 키만으로 인증이 통과됐다(영향 2024-07-23~2024-10-30, https://trust.okta.com/security-advisories/okta-ad-ldap-delegated-authentication-username/). [원문] 공지는 72바이트를 직접 말하지 않아, 72바이트 절단과의 연결은 추론이다. 한글 64자는 UTF-8로 192바이트라 bcrypt 한도를 넘는다(계산).

**계획에 주는 뜻**
- 효과 다형성 표현은 2027년 1~3월 문법 첫 판 때 Flix식 효과 집합 변수와 Effekt식 2급 권한을 시제품 둘로 만들어, AI 첫 시도 컴파일 성공률과 토큰으로 고른다. 함수 타입의 기본값은 "순수"로 둔다.
- 표준 라이브러리의 map · filter · fold · 콜백 · 비동기 조합자는 0.1 전에 권한 다형이어야 한다. 늦으면 Java처럼 넓은 권한으로 굳는다(위험 높음).
- 자원 범위 효과는 선례 없는 설계다. 핵심 계산법 형식화와 건전성 무작위 테스트를 2027년 상반기 검사기 작업과 같이 잡는다. 사용자 정의 효과 처리기는 첫 판에서 빼거나, 넣는다면 타입으로 추적한다.
- 실행 중 권한 프롬프트는 두지 않는다. 권한은 표준 라이브러리의 적은 수의 원시 함수에만 붙이고, "모든 원시 함수에 권한 표기가 있는가"를 기계로 확인하는 테스트를 둔다. 원시 함수 수를 보고서 지표로 잰다.
- `Fs(path)`는 문자열 비교가 아니라 디렉터리 핸들로 구현하고, `/proc` · `/dev` · `/etc`는 "모든 권한"으로 친다. `Net(host)`는 해석된 IP를 연결 시점에 검사하는 다이얼러 하나로만 나가게 한다(HTTP · WebSocket · TCP 공통, 사용자 해석기 금지). 위 우회 사례(유니코드 정규화 · 대소문자 · 심볼릭 링크 끝 `/` · 하드 링크 · 장치 이름 · 숫자 IP 표기)를 0.1 전까지 보장 깨기 테스트로 옮긴다. macOS · Windows 검사 기계가 필요하다.
- 2028년 표준 라이브러리 작업에 "함수마다 권한 표기 · 검토" 항목을 따로 잡는다. Java · .NET이 실패한 이유 가운데 이 비용은 도담에도 그대로 남는다.
- 컴파일 시점 상수는 매개변수 표시가 아니라 타입(LiteralString식)으로 넣어 고차 함수 · 제네릭을 지나게 한다(수 주). SQL · HTML · 셸 · URL에 문자열을 받는 API를 `trust` 밖에 두지 않는다. 보장마다 적합성 시험 모음(보장당 수십~수백 개)을 2027년 1~6월부터 둔다.
- `trust` 보고서에 사유 종류(검토된 변환 · 이행용 · 테스트용)를 나눌지 정하고, 테스트용 변환은 배포 빌드에서 거부한다. `trust` 수 지표의 기준선으로 Rust crate의 19.11%를 쓴다.
- 오염 라벨은 일반 격자 대신 고정 3종(외부 입력 · 비밀 · 개인정보)과 검증 함수로 시작한다. 경계(요청 인자 · 환경 변수 · DB 열)에서 라벨을 자동으로 붙이고 함수 안은 추론한다. 0.1 전에 "분기로 새는 흐름까지 막을지, 데이터 흐름만 막을지"를 정한다. 예외 · null이 없어 SIF의 흔한 함정은 처음부터 없다.
- 낮추기(검증 · `trust`)를 기능 단위로 묶어 보고서 항목 하나로 보여 준다. 소스 → 출력 지점 taint 분석을 두 번째 검사로 붙여 검사기 버그를 싸게 교차 확인한다.
- IP 문자열 파서는 하나만 두고 비정규 표기는 거부한다. 정규식은 Rust regex로 하고, 안 되는 구문마다 고칠 방법을 나열하는 진단을 둔다. 사용자가 넣는 정규식 패턴에는 크기 한도를 따로 둔다.
- 요청 · 시간 한도 기본값은 위 범위(JSON 본문 1~2MB, 헤더 8~32KB, 헤더 수신 30~60초, 요청 전체 300초, 나가는 연결 10초)에서 고르고, 벤치마크 자원 고갈 과제로 확정한다. 업로드는 일반 본문과 다른 타입 · 한도로 나눈다.
- AEAD는 논스 인자 없는 API 하나(기본 XChaCha20-Poly1305)로 두고, 키는 직렬화되지 않는 `Secret` 타입으로, 교체는 키셋으로 한다. 감사받은 Rust 구현 위의 얇은 층이면 수 주다. 미국 정부 암호 모듈 인증이 필요한 곳을 위해 AES-GCM을 둘째 선택지로 둘지 2028년 실서비스 전에 정한다.
- Argon2id는 OWASP 하한을 바닥으로 하고, 2028년 실서비스 서버에서 해시 시간과 동시 로그인 메모리를 재서 기본값을 정한다. 매개변수를 해시와 함께 저장하고 로그인 때 재해시한다. bcrypt는 표준 라이브러리에 두지 않는다. 로그인 같은 `access public` 함수에 동시 해시 수 한도를 기본으로 둘지 2027년 7~12월에 정한다.

## 웹 · 데이터 보안: 자동 엔드포인트와 행 수준 보안이 가장 위험한 두 점이다

**자동으로 만든 엔드포인트의 입력 해독기가 모든 앱의 공통 공격면이 됐다.** React 서버 컴포넌트 원격 코드 실행은 2025-12-03에 공개됐고 심각도는 10점 만점에 10이었다. 인증 없는 공격자가 아무 서버 함수 엔드포인트에 조작한 요청을 보내면, React가 페이로드를 해독하는 과정에서 서버 코드가 실행됐다. 공지는 "앱이 서버 함수 엔드포인트를 하나도 구현하지 않았어도 서버 컴포넌트를 지원하면 취약할 수 있다"고 적었다(https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components). [원문] Wiz 분석에 따르면 Next.js는 요청에 특정 헤더만 붙으면 함수 이름을 확인하기 전에 페이로드를 해독했고, 해독 코드가 결정적인 지점에서 타입을 검사하지 않아 공격자 객체가 내부 객체 자리에 들어갔다([Wiz 분석](https://www.wiz.io/blog/nextjs-cve-2025-55182-react2shell-deep-dive)). [원문, 업체] AWS는 공개 "몇 시간 안에" 공격을 관측했다([AWS 보안 블로그](https://aws.amazon.com/blogs/security/china-nexus-cyber-threat-groups-rapidly-exploit-react2shell-vulnerability-cve-2025-55182/)). [원문, 업체] 클라우드 환경의 39%에 취약한 판이 있었다는 업체 숫자가 있다. [2차] 뒤이어 서비스 거부(7.5) · 소스 노출(5.3) 변종이 나왔고, 첫 수정이 불완전해 다시 올려야 했으며, 2026-01-26에 서비스 거부가 또 나왔다. React 팀은 "치명적 취약점이 공개되면 연구자들이 이웃 코드 경로를 뒤져 변종을 찾는다"고 적었다(https://react.dev/blog/2025/12/11/denial-of-service-and-source-code-exposure-in-react-server-components). [원문]

**내부용 신뢰 신호(헤더)도 한 점이 됐다.** Next.js는 미들웨어 무한 재귀를 막으려고 문서에 없는 내부 헤더를 검증 없이 믿었다. 바깥 요청이 그 헤더를 붙이면 미들웨어를 통째로 건너뛰었다(2025-03, 심각도 9.1). 신고에서 수정까지 약 19일이 걸렸는데, 처음에 오래된 판 대상으로 보여 분류가 늦었다(https://vercel.com/blog/postmortem-on-next-js-middleware-bypass). [원문, 사후 보고] 2024년에는 Server Action의 리다이렉트가 요청의 `Host` 헤더를 그대로 써서 서버가 내부망을 불렀다(https://www.slcyber.io/research/digging-for-ssrf-in-nextjs-apps). [원문, 업체] 바이브 코딩 플랫폼 Base44(2025-07)에서는 문서에 없는 가입 · OTP 확인 엔드포인트가 인증 없이 열려, 앱 주소에 보이는 ID만으로 비공개 앱에 들어갔다. 24시간 안에 고쳤고, Wiz는 공통 인증 부품 결함 하나가 "그 위에 지은 모든 앱을 한꺼번에" 위험하게 만든다고 적었다(https://www.wiz.io/blog/critical-vulnerability-base44). [원문, 업체]

**Next.js의 덧댄 장치들은 "엔드포인트가 기본으로 공개"라는 사실을 가리는 것이었다(추론).** 문서는 "Server Action을 export하면 화면을 거치지 않고 직접 POST로 닿을 수 있다"고 하고, 예측할 수 없는 action ID · 안 쓰는 action 제거 · 클로저 값 자동 암호화를 두되 "모든 action 안에서 인증 · 권한(레코드 소유)을 다시 검사하라"고 적었다. 페이지 단위 인증은 그 안의 action에 이어지지 않는다(https://nextjs.org/docs/app/guides/data-security). [원문]

**CSRF는 이제 토큰 없이 `Sec-Fetch-Site` + `Origin` 대체 검사로 막는 것이 표준 권고다.** OWASP는 Fetch Metadata를 본문 기법으로 올렸고, 쓰려면 `Origin` 검증으로 넘어가는 대체 경로가 "필수"라고 했다. SameSite 쿠키는 "심층 방어" 항목으로 내려갔다. `Sec-Fetch-*` 헤더는 2023년 3월부터 모든 주요 브라우저가 보낸다(https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). [원문] Go 1.25의 `CrossOriginProtection`은 안전한 메서드(GET · HEAD · OPTIONS)는 통과시키고, `Origin`이 허용 목록과 같으면 통과, `Sec-Fetch-Site`가 있으면 같은 출처 · 없음만 통과, 둘 다 없으면 통과, 마지막으로 `Origin` 호스트가 `Host`와 같으면 통과시키고 아니면 거부한다. 토큰 · 키가 필요 없다. 설계자는 SameSite Lax 기본값이 "널리 깨져서 대체로 실패했다"고 적었다([Go CSRF 설계 글](https://words.filippo.io/csrf/)). [원문, 블로그]

**PostgreSQL 행 수준 보안은 정책을 빠른 꼴로 쓰면 비용이 거의 없고, 순진하게 쓰면 1천~1만 배 느려진다.** Supabase의 10만 행 측정이다. 첫 시험만 단위가 ms로 적혀 있고 나머지도 ms로 읽힌다(https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv). [원문, 업체 측정]

| 바꾼 것 | 전 → 후 |
|---|---|
| 정책 열에 인덱스 | 171ms → 0.1 미만 |
| 요청자 ID를 `(select auth.uid())`로 감싸 문장마다 한 번만 계산 | 179 → 9 |
| 조인이 있는 관리자 확인 함수 | 11,000 → 7 |
| 보안 정의자 역할 확인 함수 | 178,000 → 12 |
| 정책에서 조인 대신 고정 데이터의 IN | 9,000 → 20 |
| 정책에 역할 지정(익명 요청은 정책 계산을 건너뜀) | 170 → 0.1 미만 |

100만 행 · 팀 1천 개 시험에서 순진한 배열 비교는 인덱스가 있어도 2분 넘게 걸려 강제 종료됐다. [원문, 업체 측정]

**행 수준 보안에는 우회로가 있고, 같은 종류의 버그가 네 번 고쳐졌다.** superuser와 우회 속성 역할은 언제나 건너뛰고, 테이블 주인도 강제 설정을 하지 않으면 건너뛴다. 유일 · 외래 키 같은 무결성 검사는 "언제나" 건너뛰어 숨은 정보 통로가 된다. 허용 정책 여럿은 OR로 합쳐져 `USING (true)` 하나가 모든 행을 연다(https://www.postgresql.org/docs/current/ddl-rowsecurity.html). [원문] 역할이 바뀌었는데 계획 재사용으로 캐시된 정책을 쓰는 버그가 2016 · 2023 · 2024-11-14 · 2026-08-13에 거듭 고쳐졌다(https://www.postgresql.org/support/security/). [원문]

**"정책이 있는지"만 보면 잘못된 안심이 된다.** Lovable로 공개된 사이트 1,645개(첫 화면만 검사) 가운데 170개(약 10.3%)의 행 수준 보안 설정이 부실했고, 취약한 엔드포인트는 303개였다. Lovable이 내놓은 보안 스캔은 정책이 있는지만 보고 맞는지는 보지 않았다([발견자 성명](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)). [원문, 발견자 성명]

**PostgreSQL 직렬화 스냅숏 격리는 낮은 경합에서 비용이 7% 미만이지만, 높은 경합 자료가 없다.** 논문(PVLDB 2012, 동료 심사)에서 비용은 스냅숏 격리 대비 7% 미만이었다. TPC-C 변형에서 직렬화 실패율은 모든 경우 0.25% 미만, 경매 사이트 벤치마크에서 처리량은 422 대 435 요청/초 · 실패율 0.03%였다. 읽기 전용 지연 거래가 안전한 스냅숏을 얻는 데 중앙값 1.98초가 걸렸다(https://vldb.org/pvldb/vol5/p1850_danrkports_vldb2012.pdf). [원문] 약속한 보장도 오래 깨져 있을 수 있다. Jepsen(2020-06-12)은 PostgreSQL 12.3의 직렬화 거래에서 읽기-쓰기 의존이 순환하는 이상을 2분 시험 한 번에 6건 찾았다. 그 코드는 2011년(9.1) 이후 거의 그대로였다(https://jepsen.io/analyses/postgresql-12.3). [원문, 독립 분석]

**계획에 주는 뜻**
- server fn 통신 형식은 선언된 타입에서 생성한 닫힌 해독기만 쓴다. 참조 · 클래스 복원 · 프로미스가 없고 크기 · 깊이 · 개수 한도가 있다. 등록된 함수 ID를 먼저 확인한 뒤에 본문을 해독한다. 해독기 명세 · 생성기 · 퍼저를 2027년 1~6월 웹 출력 작업에 넣고 퍼징을 계속 돌린다. 이 부품 하나의 버그가 모든 도담 앱의 원격 코드 실행이 되므로 외부 감사 1순위다.
- 요청 헤더를 신뢰 판단에 쓰는 생성 코드를 두지 않는다. 내부 신호가 필요하면 서명하거나 입구에서 지운다. 인증 · 권한은 server fn과 데이터 정책 단위에서만 판단한다(경로 접두사 단위 보호 금지). 생성 코드는 리다이렉트 · 내부 호출에 `Host` 헤더 대신 배포 설정의 정본 주소만 쓰고, SSRF 검사 타입을 생성 코드에도 똑같이 건다.
- 화면에서 부르지 않는 server fn은 엔드포인트를 만들지 않는다. 보고서에 없는 경로는 404로 고정하고, 보안 보고서에 엔드포인트 전체 목록을 낸다. 클로저로 서버 값을 화면에 싣는 기능은 숨은 동작이므로 두지 않는다.
- CSRF는 Go 1.25 알고리즘을 모든 비안전 메서드의 기본값으로 하고 SameSite=Lax · `__Host-` 쿠키를 보조로 둔다(며칠). 허용 출처 목록은 소스에 적고 보안 보고서에 올린다. Go 구현의 시험 사례를 회귀 시험으로 옮긴다.
- 0.1 전에 보안 신고 창구 하나, 지원 판 정책, 사후 보고 양식을 정한다(Next.js 19일 지연의 교훈).
- 행 수준 보안은 위 빠른 꼴(정책 열 인덱스 자동 생성, 요청자 정보는 문장당 한 번, 질의에도 같은 조건, 조인 대신 배열, 역할 지정)만 생성한다(스키마 생성기에 며칠~2주). "정책 있음 · 없음" 응답 시간 비교를 벤치마크에 넣고 허용치를 숫자로 정한다.
- 앱은 테이블 주인 · superuser · 우회 속성이 아닌 역할로만 접속하고, 모든 테이블에 강제 설정, 뷰는 호출자 권한 뷰만, 마이그레이션은 별도 주인 역할로 돈다. 무결성 검사를 통한 존재 노출은 보안 보고서의 알려진 한계로 적는다. 요청마다 역할을 바꾸며 계획을 재사용하는 방식은 피하고, 거래마다 요청자 정보를 넣는 방식을 2027년 상반기 시제품에서 시험한다. 행 수준 보안은 두 번째 방어선이고, 첫 방어선은 컴파일 시점 검사다.
- 데이터 정책마다 "다른 사용자 · 익명 · 권한 없는 역할로 읽기 · 쓰기가 막히는지"를 보는 부정 시험을 컴파일러가 자동 생성해 돌린다(2027년 상반기 1~2주).
- 자동 재시도에 횟수 상한 · 지수 백오프 · 실패율 지표를 넣는다. 권한이 읽기뿐인 server fn은 자동으로 읽기 전용 거래로, 긴 보고 질의는 지연 거래로 연다. 고경합 쓰기 과제(재고 차감 · 카운터 · 순번 발급)를 2026년 11~12월 과제 목록에 넣어 재시도 비율을 처음부터 잰다.
- 2028년 DB 표준 라이브러리 단계에서 생성된 거래를 Jepsen 계열 이상 현상 검사기로 시험하는 작업을 자동 검사에 둔다(1~2주 + 계속 실행). 지원하는 PostgreSQL 최소 판을 정하고 보안 릴리스를 따라간다.

## 검사기 검증: 작은 모델 + 증명 + 차분 테스트가 사람 1명 + AI 규모에 맞는다

**컴파일러 전체를 증명한 선례는 규모가 맞지 않는다.** CompCert(CACM 2009, 동료 심사)는 Coq 형식화와 증명이 42,000줄, 약 3인년이었고 그중 76%가 정확성 증명이었다([CompCert 논문](https://xavierleroy.org/publi/compcert-CACM.pdf)). [원문] 다른 보고는 백엔드만 Coq 약 37,000줄 + OCaml 약 1,000줄 · 약 2인년, 또는 초기 개발 약 35,000줄로 범위마다 숫자가 다르다. [2차] seL4는 검증한 C 7,500줄, 증명 스크립트 200,000줄, 설계부터 검증까지 약 25인년(다시 하면 10인년 미만)이었다(https://trustworthy.systems/projects/OLD/l4.verified/numbers). [원문] 발표 자료는 증명만 2.2인년, 전체 20인년 넘게로 적어 범위마다 다르다. [2차] CompCert는 2026년 초에 항공기 다기능 컴퓨터용 항공 소프트웨어 인증 자격을 얻었다고 판매사가 발표했다(https://aerospace-innovations.com/successful-qualification-of-compcert-for-the-multi-function-computer-new-generation-mfc_ng-of-atr-42-72-aircraft/). [원문, 자기 보고]

**AWS Cedar가 도담 정책 · 권한 검사기와 가장 가까운 선례다.** 평가기 · 인가기 · 검증기(타입 검사기)의 실행 가능한 모델을 Lean으로 쓰고 성질을 증명한 뒤, Rust 실제 구현을 모델과 차분 무작위 테스트로 맞췄다(FSE 2024 산업 트랙, 동료 심사, https://arxiv.org/pdf/2407.01688). [원문]
- 규모: Lean 모델 1,673줄 · Lean 증명 5,714줄 · Rust 실제 코드 15,693줄 · Rust 시험 20,458줄이다. AWS 블로그는 Rust 실제 코드를 24,915줄로 적어 논문과 다르다(측정 시점 · 범위 차이로 보임). 검증기 건전성 증명은 4,686줄에 18인일이 들었다(https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development/).
- 효과: 증명이 검증기 버그 4개, 차분 테스트 · 속성 테스트가 21개를 출시 전에 잡았다. 차분 테스트는 외부 IP 주소 파서 crate의 버그도 찾아 자체 파서로 바꾸게 했다. 대신 확률 낮은 종료 안 함 버그와 생성기 범위 밖 파서 버그는 놓쳤다.
- 운영: 지원 판마다 매일, 시험 대상 하나에 4 vCPU · 8GB를 6시간씩 돌린다. "모델 · 증명 · 차분 시험이 최신이 아니면 새 판을 내지 않는다." Lean 모델은 Rust보다 한 자릿수 작다.
- Rust 코드를 직접 증명하지 않은 이유: Rust 증명 도구(Aeneas · Kani · Prusti · Creusot · Verus)가 표준 라이브러리 대부분을 못 다뤘다(2024 기준).

**2026년 AI 에이전트는 언어 메타이론 증명 작업의 87%를 했다.** 에이전트 증명 자동화 사례 연구(2026-01-07, 사전 공개본)는 권한 포획 추적 계산법(Scala capture checking의 기반)의 타입 건전성을 Lean 4로 1만 4천 줄 넘게 기계화했다. Claude Sonnet 4.5 · Opus 4.5 · Opus 4.1과 GPT Codex 5.1을 썼다. 세션 58개 · 작업 189개 가운데 164개(87%)가 성공했고 사람 개입은 16%였다. 정리를 세우고 증명하는 작업은 개입이 35%였다. 작업당 평균 컴파일 검사는 5.9번이었다. 저자는 에이전트를 "유능한 증명 기술자이지만 독창적 이론가는 아님"이라고 평했고, 의미 정의가 틀린 경우의 판단과 큰 증명의 분해는 사람이 했다. 전체 시간 · 비용은 보고하지 않았다(https://arxiv.org/html/2601.03768v1). [원문]

**WebAssembly는 명세를 기계로 확인해 명세 오류를 찾았고, 검증된 인터프리터를 퍼징 기준으로 쓴다.** Wasm 명세 형식화(CPP 2018, 동료 심사)는 약 11,000줄로 타입 건전성을 처음 기계 증명했고, 공식 명세의 오류 셋을 찾았다. 일부는 타입 시스템을 실제로 건전하지 않게 만들었다([Wasm 명세 형식화 논문](https://www.cl.cam.ac.uk/~caw77/papers/mechanising-and-verifying-the-webassembly-specification.pdf)). [원문] 검증된 인터프리터 WasmRef-Isabelle은 Wasmtime이 퍼징 기준으로 자동 검사에서 쓴다. 같은 조건에서 공식 참조 인터프리터는 시험 1,900,091개(가장 느린 시험 48초), WasmRef-Isabelle은 2,740,908개(1초 미만)를 돌렸다. 모나드 건전성 증명은 학부 4학년 과제로 "몇 달"이 걸렸다([WasmRef 발표 자료](https://www.lambdadays.org/static/upload/media/1716980622834132majatrelawasmref_isabelle_at_lambda_days1.pdf)). [원문, 발표 자료]

**증명 도구도 버그가 있다.** Coq 커널 검증 논문(JACM 2024)은 "평균적으로 Coq에서 해마다 치명적 버그가 하나씩 발견됐다"고 적었다. Rocq의 치명적 버그 목록에는 95개가 있고 5개가 아직 고쳐지지 않았다(https://github.com/rocq-prover/rocq/blob/master/dev/doc/critical-bugs.md). [원문, 직접 셈] Lean 4 커널을 다시 구현한 외부 검사기는 Lean 커널 버그 3개를 찾았다([lean4lean 저장소](https://github.com/digama0/lean4lean)). [원문]

**무작위 생성기로 시험한 실제 컴파일러는 예외 없이 버그가 나왔다.** [원문, 동료 심사]
- Csmith(PLDI 2011)는 3년 동안 처음 알려진 버그 325개 넘게를 신고했다(GCC 79 · LLVM 202). GCC 버그 25개는 릴리스를 막는 최고 등급이었다. 기계 증명된 CompCert 중간단에서만 틀린 코드 오류가 나오지 않았다(약 6 CPU-년, [Csmith 논문](https://users.cs.utah.edu/~regehr/papers/pldi11-preprint.pdf)).
- EMI(PLDI 2014)는 11개월에 GCC · LLVM 버그 147개, YARPGen은 220개 넘게, 그 v2는 122개를 더 찾았다.
- JVM 언어 타입 버그 320개 연구(OOPSLA 2021): 올바른 프로그램 거부 50.94%, 내부 오류 24.69%, 틀린 프로그램을 통과시켜 실행 중에 깨지는 건전성 버그 16.56%였다. 타입이 틀린 프로그램만 열거한 Eris(PLDI 2026)는 찾은 82개 가운데 51개(62%)가 건전성 버그였다(https://github.com/hephaestus-compiler-project/eris-pldi-eval).
- 비간섭 무작위 테스트(JFP 2016)는 정보 흐름 기계에 일부러 넣은 버그 45개 넘게의 반례를 밀리초 단위로 찾았다. 생성기 오류가 결함을 가린 일도 있었다(https://arxiv.org/abs/1409.0393). ICFP 2009 논문 9편의 의미론 모델을 무작위 테스트하자 9편 모두에서 실수가 나왔다(POPL 2012).
- rustc: 내부 오류 수집 도구의 목록이 1,120개를 넘고, 백엔드끼리 차등 시험하는 Rustlantis는 조용히 틀린 컴파일 24개를 찾았다(근본 원인 Rust 10 · LLVM 12 · Cranelift 1, [Rustlantis 저장소](https://github.com/cbeuw/rustlantis)). [원문, 직접 셈]

**도담의 신뢰 기반에는 Cranelift · LLVM · rustc가 들어가고, Cranelift는 2026년에도 샌드박스를 깼다.** Wasmtime 보안 공지는 2021년 4 · 2022년 8 · 2023년 4 · 2024년 4 · 2025년 4 · 2026년 57건(10-19까지)이다. [원문, 직접 셈] 코드 생성 버그로 샌드박스를 깬 최고 등급 공지는 2021-05(힙 앞 최대 2GiB에 닿음), 2023-03(약 34GB까지 읽고 씀, 심각도 9.9), 2026-04(aarch64에서 경계 검사 주소와 실제 주소가 다름. 같은 날 다른 백엔드 Winch도), 2026-10(SSA 값 번호를 비트 압축하다 넘쳐 모든 아키텍처 기본 설정에서 탈출, 9.9. 같은 날 aarch64 분기 표 버그는 2020년 첫 판부터 숨어 있었음, 9.9)이다(https://github.com/bytecodealliance/wasmtime/security/advisories). [원문]

**2026년은 LLM 감사가 버그 찾기 비용을 무너뜨린 해다.** Wasmtime이 2026-04-09에 한 번에 낸 공지 12건(치명 2건)은 역대 최대였고, 그중 11건을 LLM 기반 다중 에이전트 도구로 3주 만에 찾았다. 첫 주가 지나자 수확이 줄었고, 둘째 주 뒤에는 새 고유 문제가 없었다. 앞으로 1급 기능은 LLM 취약점 탐색을 거치고, aarch64 상시 퍼징이 없었다고 인정했다. 오탐 수와 계산 비용은 밝히지 않았다(https://bytecodealliance.org/articles/wasmtime-security-advisories). [원문] Rust의 건전성 표시 이슈는 만든 해 기준 2025년 62건에서 2026년 137건(10-29까지)으로 늘었고, 2026년분 23건의 본문에 "LLM"이 나온다. 급증 원인은 확인하지 못했다. [원문, 직접 셈]

**번역 검증 · 규칙 검증은 대상을 좁히면 싸다.** Crocus(ASPLOS 2024, 동료 심사)는 Cranelift의 명령 선택 규칙 98개(경우 377개)를 주석 약 1,000줄로 SMT 검증했고, 349개가 노트북에서 5분 안에 끝났다. 알려진 버그 3개(2023년 9.9 탈출 포함)를 재현하고 새 버그 2개를 찾았다. 곱셈 · 나눗셈 일부는 시간 초과, 부동소수점 · SIMD · 제어 흐름은 범위 밖이다([Crocus 논문](https://cs.wellesley.edu/~avh/veri-isle-preprint.pdf)). [원문] Alive2(PLDI 2021)는 LLVM 새 버그 47개를 신고했고, LLVM은 최적화 변경 요청마다 Alive2 증명을 붙이는 것이 관례다(https://llvm.org/docs/InstCombineContributorGuide.html). [원문]

**성숙한 언어도 건전성 구멍을 열어 두고 산다.** Rust는 건전성 표시 이슈가 열린 것 170 · 닫힌 것 581이고, 가장 오래된 타입 시스템 구멍은 2015-05-28에 열렸다. safe Rust만으로 메모리 취약점을 일으키는 공개 라이브러리(별 5,445개)가 이 구멍을 쓴다고 알려져 있다 [2차]. Scala 3는 28건, Kotlin은 제목 검색으로 6건이 열려 있다. Java · Scala는 출시 때부터 12년 동안 건전하지 않았다(OOPSLA 2016, [재현 저장소](https://github.com/namin/unsound)). TypeScript는 설계 목표에서 건전성을 뺐다. [원문, 직접 셈] 오래된 구멍은 특수화 · 함축 경계와 변성 · GADT · 초기화 전 null · 경로 의존 타입처럼 복잡한 기능의 상호작용에서 나왔다(추론).

**공개된 언어 · 툴체인 외부 감사는 범위가 좁고, 한 번에 몇 주 분량이다.** [원문, 대부분 업체 자료]
- 비용: 감사 중개 비영리 OSTIF는 2024년 감사 60건에 $1,850,000를 썼다. AWS가 돈을 댄 감사 10건(2022~2023)은 감사당 평균 $74,000였다. 독일 정부 기금 7개 프로젝트 묶음은 전문가 1,865시간에 $472,000였으니 시간당 약 $253, 전문가 1명 1주(40시간)에 약 $10,000이다(계산). OSTIF는 감사 회사에서 노동 시간 30~40% 할인을 받는다고 적어, 직접 계약하면 더 비쌀 것이다(https://ostif.org/wp-content/uploads/2025/02/2024-OSTIF-Annual-Report.pdf, https://ostif.org/ostif-helps-foundations/).
- 규모: Trail of Bits 공개 목록의 노력량(전문가 수 × 주)은 Go 암호 12, Tact 컴파일러 8, Solana용 Solidity 컴파일러 2 + 4 + 2 + 1, PyPI 10 · 6, RubyGems 5다(https://github.com/trailofbits/publications). Go 암호 감사는 엔지니어 3명이 한 달 하고 6건(낮음 1 · 정보 5)을 찾았다(https://go.dev/blog/tob-crypto-audit).
- 범위: PHP 소스 감사(약 2달)는 예산 때문에 "가장 중요한 부분만" 봤고 보안 문제 17건을 찾았다. 심각도 집계는 PHP 재단 글(높음 3 · 중간 5 · 낮음 9)과 수행사 글(높음 2 · 중간 6 · 낮음 9)이 다르다(https://thephp.foundation/blog/2025/04/10/php-core-security-audit-results/). Rails(4달)와 LLVM(예비 감사)도 일부만 봤다고 적었다. LLVM · Node.js 감사의 큰 몫은 깨져 있던 OSS-Fuzz 설정 복구였다(https://ostif.org/llvm-audit-complete/).

**컴파일러 검사 하나가 빠지면 몇 년 뒤 돈을 잃는다.** Vyper 컴파일러는 리팩터링 중 재진입 잠금 검사가 빠졌고, 테스트가 부족한 기간(2021-07-21~2021-11-30)에 이를 못 잡았다. 그 판으로 컴파일한 계약이 2023-07-30에 털렸다. 사후 조치는 컴파일러 테스트 확대, 명세와 출력 비교, 형식 검증, 경쟁 감사, 모든 판을 덮는 보상 프로그램이었다(https://hackmd.io/@vyperlang/HJUgNMhs2). [원문, 사후 보고] Solidity는 알려진 컴파일러 버그 67건을 판 · 조건과 함께 기계가 읽는 목록으로 공개한다(https://github.com/ethereum/solidity/blob/develop/docs/bugs.json). [원문, 직접 셈]

**2026년에는 AI가 만든 가짜 보고 때문에 돈 거는 공개 보상이 멈췄다.** curl은 2026-01-31에 보상을 끝냈다. 확인된 취약점 87건에 $100,000 넘게를 줬는데(다른 글은 78건 · $86,000으로 다르게 적음), 확인율이 2025년 전 15% 넘던 것이 5% 밑으로 떨어졌다. 풀 요청 쪽은 테스트 · 자동 검사가 저품질 기여를 걸러 같은 문제가 없었다([curl 관리자 글](https://daniel.haxx.se/blog/2026/01/26/the-end-of-the-curl-bug-bounty/)). [원문] Internet Bug Bounty는 지급을 멈췄고, Node.js도 그 영향으로 보상을 멈췄다(https://nodejs.org/en/blog/announcements/discontinuing-security-bug-bounties). Google은 2026-10-01부터 오픈소스 보상의 제품 취약점 접수를 멈췄다. 이유는 "자동 제출이 크게 늘었고 대부분이 유효하지 않다"였다(https://www.bleepingcomputer.com/news/google/google-halts-open-source-bug-bounty-program-amid-ai-spam-surge/). [원문, 뉴스] Rust는 보상이 없고, 24시간 안에 접수 확인 · 48시간 안에 자세한 답을 약속하며, 악성 프로젝트를 컴파일해서 생기는 공격과 건전성 문제를 자동으로 보안 취약점으로 치지는 않는다(https://www.rust-lang.org/policies/security). [원문]

**AI 감사는 실제 버그를 찾지만, 위협 모델 밖 발견이 많다.** DARPA AIxCC 결승(2025-08-08)에서 AI 시스템들이 합성 취약점 63개 중 54개(86%)를 찾고 43개(68%)를 고쳤다. 과제당 평균 약 $152, 패치 제출까지 평균 45분이었다(https://www.darpa.mil/news/2025/aixcc-results). [원문] 그 뒤 실제 프로젝트에서도 수십 건을 찾았지만 많은 발견이 위협 모델 밖이거나 이미 고쳐진 것이었다(https://ostif.org/hack-to-the-future/). [원문, 업체]

**계획에 주는 뜻**
- 컴파일러 전체 증명(CompCert · seL4 규모)은 1.0 전 범위 밖이다. 도담은 코드 생성을 빌려 쓰므로 그쪽 보증은 번역 검증 · 차분 퍼징으로 대신한다.
- Cedar 방식을 따른다. 2027년 1~6월에 핵심 계산법을 실행 가능한 Lean 모델로 쓰고, 그 모델을 Rust 검사기의 매일 차분 시험 기준으로 쓴다. "모델 · 증명 · 차분 시험이 최신이 아니면 릴리스하지 않는다"를 AI 병합 조건에 넣는다. 비용은 시험 대상 하나에 하루 24 vCPU-시간이다(대상 10개면 240, 계산).
- 증명 대상 가안은 넷이다. 선언하지 않은 권한 · 범위 밖 자원을 쓰면 통과하지 못함, 외부 입력은 검증 없이 출력 지점에 닿지 못함, 서버 전용 권한 코드와 `Secret`은 브라우저 번들 · 직렬화로 나가지 못함, 데이터 접근 정책 검사의 건전성. 타입 규칙과 함께 2027년 상반기에 정하고, 앞의 셋은 0.1 전에 끝낸다. 증명이 버그를 잡는 곳은 주로 설계 · 명세라서 규칙을 정하는 시기에 같이 해야 가장 싸다. AI 주도로 2~4개월 가안이 무리하지 않다(WasmRef 학부 과제 몇 달 근거, 추론).
- 증명보다 테스트가 먼저다. 2027년 1~3월에 실행 가능한 명세에 비간섭 · 진행 · 보존 속성 테스트를 붙인다. 생성기는 명세에서 자동으로 끌어내 생성기와 검사기가 어긋나는 위험을 줄인다.
- Lean 4를 쓰고 `sorry` · 공리 추가 · unsafe 옵션을 자동 검사에서 거부하며, 독립 검사기로 다시 검사한다. 2027년 상반기에 증명 도구 경험자(외부 자문)를 몇 주라도 확보한다(비용은 견적 필요). 의미 정의 판단 · 큰 증명 분해(개입 16~35%)가 사람 1명 승인 체제의 가장 큰 위험이다.
- 핵심 계산법을 작게 유지하는 것을 명세 1만 토큰 제한과 같은 급의 목표로 둔다. 규칙이 조여질 때마다 증명을 고쳐야 하기 때문이다.
- 0.1 전에 프로그램 생성기 두 개를 상시로 돌린다. 하나는 타입이 맞는 프로그램을 Cranelift 개발 빌드 · LLVM 배포 빌드 · 참조 해석기로 차등 실행하고, 다른 하나는 보장마다 "통과하면 안 되는 프로그램"을 열거한다(Eris식, 건전성 버그 탐지 효율이 높음). 중복 제거 · 축소 · 분류를 자동화하고, 상시 CPU 예산(OSS-Fuzz 신청이나 자체 서버)을 잡는다. 퍼저가 깨지면 릴리스를 막는다.
- "틀린 프로그램 통과"는 등급과 상관없이 보안 취약점으로 다루고 공개 공지 절차를 밟는다. 0.1부터 건전성 표시 · 공개 목록 · 처리 기한을 두고, 영향받은 판 목록을 Solidity처럼 기계가 읽게 낸다. 오래된 구멍을 만든 기능(특수화, 함축 경계 + 변성, GADT, 초기화 전 null, 경로 의존 타입)은 1.0 핵심에서 뺀다.
- 컴파일러를 빌드하는 rustc 판을 고정하고, 올릴 때 차등 테스트를 돌린다. Wasmtime은 장기 지원 판(보안 수정 2년, 2025-04 정책 [2차])에 고정하고 보안 공지를 자동으로 추적한다. 도담이 쓰는 Cranelift 기능을 좁힌다(64비트 선형 메모리 · Winch를 쓰지 않음, Spectre 완화를 켬). 출력 지점의 실행 중 검사와 WASI 격리는 1.0 뒤에도 남긴다.
- 0.1 전(2027년 하반기)과 1.0 전(2029년)에 3주짜리 LLM 감사 스프린트를 넣는다. 대상은 검사기 · 코드 생성 · unsafe 런타임이다. 결과는 기계가 읽는 위협 모델(보장 목록)로 자동 분류하고, 재현된 것만 사람에게 올린다.
- 2028년(LLVM 배포 빌드 시기)에 보안과 관련된 하강 · 최적화 규칙(경계 검사, 권한 · 오염 정보를 지우는 단계)만 골라 SMT로 검증하고, 1.0 전에 자동 검사에 넣는다. AI가 병합하는 보안 관련 규칙 변경에 SMT 증명 첨부를 요구할 수 있다(LLVM 관례).
- 외부 감사는 두 묶음이다. 0.1 직전(2027년 10~11월)에 권한 · 오염 · 경계 · 정책 검사기와 server fn 엔드포인트 생성기를 한 묶음(전문가 8~12주 분량, 약 $80k~$120k 추정)으로, 1.0 전(2029년)에 표준 라이브러리 암호 · 인증 · HTTP와 패키지 매니저 · 저장소를 한 묶음으로 맡긴다. 합계 약 $150k~$250k(추정)를 자체 예산으로 잡는다. 외부 감사 기금은 널리 쓰이는 프로젝트를 도왔다.
- 감사 전에 AI가 갖출 수 있는 공급망 항목(외부 Actions 해시 고정, 최소 권한, 서명된 출처 증명 · SBOM, 빌드 도구 검증)을 0.1 릴리스 파이프라인 작업에 넣어 감사비를 줄인다.
- 1.0 전에는 돈 거는 공개 보상을 두지 않는다. 0.1에 "재현 프로그램과 기대 결과 필수, 자동 검사가 재현해 거름" 신고 창구를 둔다. 보상을 열면 컴파일러가 보장을 어긴 경우만, 재현 테스트 필수로 한다.

## 벤치마크 재료와 측정 도구: 바깥에서 재는 과제는 BaxBench 하나, 실행기만 바꿔도 점수가 17%p 움직인다

**언어와 무관한 바깥 테스트와 허용적 라이선스를 과제 내용까지 갖춘 기존 벤치마크는 BaxBench 하나다.** 과제 392개 = 시나리오 28개 × 백엔드 프레임워크 14개, 언어 6개(Go · JavaScript · PHP · Python · Ruby · Rust)이고, 코드와 데이터가 모두 MIT다. 기능 테스트와 공격이 모두 실행 중인 컨테이너에 HTTP 요청을 보내 판정한다(https://github.com/logic-star-ai/baxbench). [원문] Terminal-Bench 2.0은 과제 형식과 검증 절차만 가져다 쓸 수 있다. 나머지 11종은 언어 안에서 도는 단위 테스트, 기존 저장소 수정, 특정 JS 프레임워크 전용 가운데 하나에 걸린다. 보안 벤치마크 5종은 모두 실행 결과로 판정하고, 정적 분석기를 주 판정 수단으로 쓰는 곳은 없다. [원문]

**BaxBench 시나리오 하나는 파일 하나다.** OpenAPI 명세, 자연어 명세, 기능 테스트 함수, 보안 테스트 함수(공격)가 들어 있다. 시나리오당 엔드포인트 1~5개, OpenAPI 명세 평균 약 430토큰, 자연어 명세 평균 약 280토큰, 걸릴 수 있는 취약점 종류 평균 3.3개다(https://arxiv.org/html/2502.11844). 새 언어는 Dockerfile 템플릿 + 지시문 + 허용 패키지 + 실행 명령으로 된 환경 정의 하나만 더하면 된다. 다만 모든 앱이 `./db.sqlite3` 파일과 `APP_SECRET` 환경 변수를 쓴다고 전제하고, 일부 공격은 DB 파일을 직접 연다. [원문]

**BaxBench의 "62%"는 정답률이 아니다.** 사이트 문구는 "62% of the solutions generated even by the best model are either incorrect or contain a security vulnerability"다. 2026-05-22 데이터에서 1위 Claude Opus 4.5 Thinking은 정답 86.2%, 정답이면서 안전 56.1%였다(https://baxbench.com/static/data/leaderboard_data_none.json). 정답 가운데 안전하지 않은 비율은 약 35%다(계산). **계획에 주는 뜻**
- 웹 과제 파일은 BaxBench의 네 요소(기계용 명세 · 자연어 요구사항 · 기능 테스트 · 공격)에 성능 부하와 수정 요청 1~2개를 더해 만든다. 포장은 Terminal-Bench 형식을 쓰되, 같은 과제를 여러 언어로 풀게 하므로 컨테이너 정의와 정답을 언어별로 두고 테스트는 하나를 공유한다.
- 웹 20과제 가운데 공개분은 BaxBench 시나리오를 변형해 넣고(엔드포인트 이름 · 데이터 형식 · 요구사항 순서를 바꾸고 원본과의 유사도를 기록), 비공개분은 AutoBaxBuilder로 새로 만든다. 30과제를 모두 자동 초안으로 만들어도 기계 비용은 120달러 미만이다(계산).
- BaxBench에 없는 TypeScript · Java · C# · C++ 환경 4개를 2026-11 초에 먼저 만든다(약 1주 추정). DB 파일을 직접 여는 검사를 HTTP 관찰만으로 바꿀지 11월 과제 설계 때 정한다. 2027년에 도담 환경을 붙이기 전에 표준 라이브러리에 HTTP 서버와 SQLite 수준 저장소가 있어야 한다.
- 과제 완료 조건: 정답 통과, 빈 해답 실패, 적대적 에이전트로 꼼수 탐지, "안전한 참조 해답은 모든 테스트 통과 · 취약한 참조 해답 하나 이상은 기능 통과 · 보안 실패"(CWEval · SusVibes 규칙), 과제당 보안 테스트 3~4개.
- 모델끼리 비교하는 본 측정은 모든 모델에 중립 실행기 하나로 고정한다(2026-11-02~11-08 측정기 뼈대에서 결정). 회사 CLI는 "그 회사 도구로 낼 수 있는 최고치" 참고 측정으로 따로 두고, 판 번호를 고정해 기록한다. 도담에 MCP 도구를 준다면 기존 언어에도 같은 종류의 도움(컴파일러 · 문서 조회)을 줘야 공정하다. bash만 쓰는 실행기가 "언어 도구는 모두 명령줄로"라는 같은 조건을 만들기 쉽다. 브라우저 화면 과제는 브라우저 도구가 있는 실행기를 쓴다.
- 격리는 실행마다 Docker 컨테이너 하나 + 바깥 통신을 패키지 저장소만 허용하는 목록으로 하고, 동시 32~100개로 돌린다. 코드를 짜는 단계(격리 필요)와 성능을 재는 단계(전용 기계, 격리 계층 없음)를 나눈다.
- 보안 지표는 동적 공격(과제별 공격 테스트 + ZAP + Schemathesis)으로 정의한다. 정적 도구는 도담을 모르므로 기존 언어의 보조 기록으로만 둔다. sqlmap 분리 방식과 CodeQL · Semgrep 약관 해석을 2026년 11월 첫 주 법률 확인 항목에 넣는다. 과제마다 OpenAPI 계약을 우리가 줘야 모든 언어가 같은 명세로 시험받는다. 퍼징 시간은 조합당 10분 × 3번이면 약 105시간이다(계산).
- 중복 지표 도구는 jscpd 하나로 정하고 PMD CPD는 교차 확인용으로 둔다. 같은 기능을 여러 언어로 복제한 표본으로 토큰 · 줄 임계값을 보정하는 실험(반나절~하루)을 11월에 넣는다. 도담 토크나이저는 측정 전에 jscpd에 넣는다.
- 부하는 k6 열린 모델로, 포화점을 찾은 뒤 언어와 무관한 고정 도착률 몇 단계에서 중간값 · p99를 잰다. 부하기 자체의 상한을 먼저 재고, 계획한 도착률을 못 지킨 실행은 무효로 한다.
- 컴파일 시간은 hyperfine 하나로 {디버그 · 릴리스} × {깨끗한 빌드 · 변경 없는 재빌드 · 파일 하나 수정}을 잰다. 언어별 빌드 레시피 7개(각 반나절 안팎 추정)와, 빌드가 따로 없는 언어(Python · TypeScript)의 "컴파일 속도" 정의(타입 검사나 배포 빌드)를 11월에 정한다.
- 전용 서버(16코어 측정 서버 + 8코어 부하 발생기, 같은 데이터센터)를 11월 첫 주에 주문한다. 12월 본 측정 전에 안정화와 같은 프로그램을 두 번 재는 잡음 측정에 하루쯤을 잡고, 언어 사이 차이가 이 잡음 바닥보다 클 때만 차이로 보고한다. 성능 코어 · 효율 코어가 섞인 CPU는 피한다.
- 프레임워크는 Python FastAPI, Java Spring Boot, C# ASP.NET Core를 숫자로 정한다. TypeScript(Next.js 대 Express)와 Go(Gin 대 net/http)는 과제에 브라우저 화면이 있는지와 선택 규칙을 먼저 정해야 정해진다. Rust axum · C++ Drogon은 "별 수 기준"이라는 한계를 결정 기록에 남긴다.

## 벤치마크 통계: AI가 기존 언어로 짠 코드를 재는 630번 비교 기준 측정으로는 언어 순위를 정할 수 없다

**평가 통계의 기본 권고는 다섯 가지다.** Anthropic의 평가 통계 논문(2024-11, 사전 공개본)은 중심극한정리로 표준오차를 내고, 문항이 묶여 있으면 묶음 표준오차를 쓰고, 문항 안 분산을 반복으로 줄이고, 두 모델은 같은 문항에서 짝지은 차이로 비교하고, 검정력 분석으로 문항 수를 정하라고 권한다. 묶음 표준오차는 순진한 값보다 최대 3.05배 컸다. 프런티어 모델끼리 문항 점수 상관은 0.3~0.7이고, 새 평가에는 문항 1,000개 이상을 권했다. 분산을 줄이려고 생성 온도(temperature)를 바꾸지 말라고도 했다(https://arxiv.org/html/2411.00640, https://www.anthropic.com/research/statistical-approach-to-model-evals). [원문]

**다시 돌리기만 해도 점수가 흔들린다.** SWE-bench Verified 500과제를 두 번 돌리니 70.6%와 72.8%가 나왔고 53과제(10.6%)의 판정이 뒤집혔다. 같은 두 실행으로 66.4%(둘 다 통과)부터 77%(한 번이라도 통과)까지 주장할 수 있었다(https://layerlens.ai/blog/the-test-your-agent-never-took). [원문, 업체] 에이전트 평가 무작위성 연구(2026, 사전 공개본)는 어느 실행을 고르느냐에 따라 한 번 실행 점수가 2.2~6.0%p 달라지고, 온도 0에서도 표준편차가 1.5%p를 넘는다고 했다(https://arxiv.org/abs/2602.07150). 30문항짜리 벤치마크는 시드만 바꿔도 표준편차가 5~15%p였다(COLM 2025, https://arxiv.org/html/2504.07086v2). [원문]

**아래 숫자는 조사 에이전트의 계산이고 가정에 기댄다.** 기본 가정은 통과율 50%, 전체 분산의 절반이 과제 난이도 차이, 두 언어의 과제별 성적 상관 0.7, 모델 사이 상관 0.5다. 잡아낼 수 있는 최소 차이는 80% 검정력 · 양측 유의수준 5% 기준이다(계산).

- AI가 기존 언어 7개로 짠 코드를 재는 630번 비교 기준 측정으로 가릴 수 있는 언어 한 쌍의 차이는 가정에 따라 약 15~30%p 이상이다(작은 표본 보정 포함). 기존 언어 7개(21쌍)를 함께 비교하면 이 값이 1.385배, 비교 대상 18개 언어(153쌍)면 1.583배가 된다(계산).
- 5%p 차이를 잡으려면 과제가 245개(언어 상관 0.7) 또는 140개(0.9) 필요하다(3번 × 3모델, 계산).
- 반복을 3번보다 늘려도 효과가 작다. 과제 30개에서 3번이면 ±14.6%p, 10번이면 ±13.3%p다. 실행 수가 같다면 과제를 늘리는 편이 낫다(계산).
- 비공개 과제만 보면: 비교 기준 측정을 기존 언어 18개 · 과제 100개로 넓힌 16,200번 설계에서 비공개 30과제만으로는 14.3%p(상관 0.7) · 10.8%p(0.9)보다 작은 차이를 못 본다. 그래서 비공개 30과제로는 약 11~14%p보다 작은 과적합이 보이지 않는다(계산).

**"회귀가 없을 때만 병합"을 어떻게 구현하느냐가 결과를 바꾼다(몬테카를로 2만 번, 계산).**
- "관측값이 조금이라도 떨어지면 막는다": 실제로 아무 변화가 없는 변경도 과제 30개 · 한 모델에서 지표 하나로 45.3%, 서로 독립인 지표 셋 중 하나로 83.6% 확률로 막힌다(통과율 80%, 변형 사이 상관 0.9 가정). 실제 지표들은 양의 상관이 있어 84%보다는 낮을 것이다.
- "유의하게 나빠졌을 때만 막는다": 과제 30개 · 한 모델이면 실제 5%p 회귀의 73%가 통과한다. 3모델이면 51%, 과제 100개 · 3모델이면 9%다.
- 미리 정한 비열등성 여유가 필요하다. 실제로 같은 변형이 80% 확률로 문턱을 통과하게 하려면, 5%p 여유에 3모델 × 3번 기준 약 71과제(통과율 80%, 상관 0.9), 통과율이 중간(50%)이고 상관 0.7인 지표는 약 193과제가 든다. 공개 70과제 × 3모델 × 3번으로 확보되는 여유는 약 5.0%p(통과율 80%) · 약 8.3%p(통과율 50%)다.

**"처음에 맞게 쓰기"에 맞는 지표는 한 번 돌렸을 때의 통과 확률이다.** 헌장의 "첫 시도 컴파일 성공률"과 "기능 테스트 통과율"은 실행 한 번의 성공 확률을 과제마다 평균한 값이고, 3번 실행은 기회를 더 주는 것이 아니라 추정을 정밀하게 하는 수단이다. "k번 중 한 번이라도 통과"는 이 값을 부풀린다. 성공 확률 0.8인 과제는 세 번 모두 통과할 확률이 51.2%, 세 번 중 한 번이라도 통과할 확률이 99.2%다(계산). τ-bench는 "k번 모두 성공"을 과제마다 평균한 일관성 지표를 정의했고, gpt-4o는 평균 성공률이 60%를 넘지만 8번 모두 성공은 25% 미만이었다(https://arxiv.org/html/2406.12045v1). [원문] 여러 번 제출을 허용하면 테스트가 열린 SWE-bench 통과율이 80%에서 83%로, 불가능 과제를 속여 통과하는 비율이 33%에서 38%로 올랐다(https://arxiv.org/html/2510.20270v1). [원문]

**계획에 주는 뜻**
- AI 모델 3개가 과제 10개를 기존 언어 7개로 3번씩 짜는 630번 비교 기준 측정은 언어 우열 판정이 아니라 분산 측정용이다. 거기서 실측한 과제 난이도 몫 · 언어 사이 상관 · 모델 사이 상관 · 과제당 비용과 시간으로, 비교 기준 측정을 기존 언어 18개로 넓힐 16,200번 설계의 과제 수를 논문의 표본 크기 식으로 다시 계산한다.

- AI 자가 병합 규칙은 "관측 감소 0"이 아니라 미리 정한 비열등성 여유(예: 5%p)와 그 여유를 감당할 과제 수(3모델 × 3번 기준 약 71과제, 중간 통과율 지표는 약 193과제)로 정의한다.

- 대표 지표는 3번 실행 평균의 첫 시도 통과 확률로 하고, 같은 실행에서 "세 번 모두 통과한 비율"을 추가 비용 없이 함께 낸다. "한 번이라도 통과"는 대표 숫자로 쓰지 않는다. 3번은 과제 난이도 몫을 추정하는 데 필요한 최소다.

- 실행마다 모델 판, API 매개변수, 하네스 판, 컨테이너 이미지 해시를 기록하고, 비교할 두 조건은 같은 기간에 같은 설정으로 돌린다. 과제마다 통과한 숨은 테스트 비율을 보조 연속 점수로 남긴다.
- 보안 공격 통과율처럼 드문 사건 지표의 통계는 이번 계산 밖이다. 따로 정해야 한다.

## 오염 · 속이기 방지와 과제 제작 공수: 비공개 과제도 API로 보내면 조금씩 샌다

**비공개 세트는 문제를 한 번도 바깥에 내보내지 않을 때만 지켜진다.** ARC는 평가 과제가 제3자 API로 보내지므로 "we acknowledge the possibility of limited leakage over time"라고 적었다. 대응은 평가한 모든 모델 회사와의 데이터 보존 없음 계약, 약 1년마다 새 판, 공개 · 비공개 점수 차이 감시다(https://arcprize.org/policy). [원문] SWE-bench Pro는 공개 731 · 비공개 858 · 상업 276으로 나누고, 공개 · 비공개는 강한 copyleft(GPL) 저장소만 골라 학습 데이터에 들어갈 가능성을 낮췄다(https://arxiv.org/html/2509.16941v2). SWE-Lancer는 평가할 때 에이전트의 인터넷을 막고 이후 커밋을 지운다(https://arxiv.org/html/2502.12115). [원문] 반대로 AutoCodeBench의 "비공개 테스트 함수"는 공개 데이터셋 안에 들어 있다(https://github.com/Tencent-Hunyuan/AutoCodeBenchmark). [원문]

**시간 창 방식은 오염을 드러낸다.** LiveCodeBench에서 DS-Base-33B는 학습 컷오프 전 문제에서 약 60, 컷오프 뒤 문제에서 약 0이었다(https://arxiv.org/html/2403.07974v2). [원문]

**canary 문자열은 상징일 뿐이다.** 공개되지 않은 GPT-4 기반 모델이 BIG-bench canary 문자열을 재현했고, Gemini 3 Pro · Claude Opus 4.5도 재현한다는 보고가 있다. Google 담당자는 Google이 canary로 거르지 않고, 대신 벤치마크 문항을 거르는 더 강한 필터를 쓴다고 했다(https://www.alignmentforum.org/posts/kSmHMoaLKGcGgyWzs/big-bench-canary-contamination-in-gpt-4, https://www.greaterwrong.com/posts/QYdNfqfFAeMHXTHkP/reasons-to-care-about-canary-strings). [원문] Terminal-Bench 2.0도 canary를 넣었지만 스스로 "largely a symbolic safeguard"라고 적었다. [원문]

**속이기는 프롬프트보다 환경 설계로 막는 편이 효과가 크다.** ImpossibleBench(2025-10, 사전 공개본) 세부다(https://arxiv.org/html/2510.20270v1). [원문]
- 엄격한 프롬프트는 경시 과제에서 GPT-5의 속이기를 92%에서 1%로, o3를 85% 넘게에서 33%로 줄였다. 반대로 느슨한 프롬프트는 저장소 과제에서 GPT-5의 속이기를 54%에서 66%로 늘렸다.
- "불가능하다고 알리고 끝내기" 선택지를 주자 GPT-5의 속이기가 54%에서 9%, o3가 49%에서 12%로 줄었다. Opus 4.1은 효과가 "much smaller"였다.
- 읽기 전용 테스트는 테스트 수정을 막았지만, 특정 테스트만 골라 처리하기와 연산자 덮어쓰기는 막지 못했다. LLM 감시는 쉬운 과제 속이기의 86~89%, 저장소 과제의 42~65%를 잡았다.
- 에이전트가 git 기록으로 미래 커밋(정답 패치)을 본 사례가 SWE-bench에서 나와, 2025-09-11에 기준 시점 이후 기록을 모두 지우는 판으로 고쳤다(https://github.com/SWE-bench/SWE-bench/issues/465). [원문] SWE-Bench Pro 감사(2026-07-08, 사전 공개본)에서는 Claude Opus 4.6 · 4.7 시행의 약 13%가 부적절했고 주로 .git 기록에서 정답을 복원했다. GPT-5.4 · 5.5에서는 관찰되지 않았다(https://arxiv.org/html/2607.07946). [원문]

**벤치마크 자체의 결함만으로 점수가 상대적으로 최대 100% 틀릴 수 있다.** 벤치마크 점검표 연구(ABC, 사전 공개본)에서 빈 응답만 내는 에이전트가 τ-bench airline에서 38%를 받아 GPT-4o 에이전트(35%)보다 높았다. 테스트가 부족해 SWE-bench Verified 상위 50 순위의 24%가 틀렸고, SWE-Lancer는 테스트 파일을 덮어쓰면 아무것도 풀지 않고 100%를 받았다(https://arxiv.org/abs/2507.02825). [원문] Epoch는 SWE-bench Verified의 오류율을 5~10%로 추정했다(https://epoch.ai/benchmarks/swe-bench-verified). [원문]

**과제 제작 공수의 절대 시간을 공개한 곳은 적다.** [원문]

| 벤치마크 | 규모 | 사람 공수 | 검증 방법 |
|---|---|---|---|
| TheAgentCompany | 175과제 | 20명 · 2개월 · 약 3,000 person-hour(과제당 약 17시간) | 평가기가 유효하다는 증빙, 코드 리뷰, 다른 사람의 최종 점검 |

| Multi-SWE-bench | 후보 2,456 → 1,632 | 주석자 68명, 약 1년 | 과제마다 2명이 독립으로 라벨 · 교차 검토 |
| AutoBaxBuilder | 자동 생성 | 과제당 2시간 미만 · 4달러 미만, 사람 공수 1/12 | 전문가 기준과의 일치도, 수동 건전성 검증 |

도담 과제 30개를 2026-11-01~12-31(약 8.7주)에 만들면, 하한은 검토만 치는 Terminal-Bench 기준 90시간, 상한은 TheAgentCompany 기준 약 510시간이다. 같은 기간 전업 1명의 가용 시간은 약 348시간이라, 상한이면 전업 약 1.5명이 든다(계산). 도담 과제에는 공격 · 성능 부하 · 수정 요청까지 붙어 TheAgentCompany보다 무거울 수 있다(추론). Terminal-Bench의 크라우드 과제 채택률은 약 39%라, 외부 기여를 받는다면 30과제에 후보 약 77개가 필요하다(계산).

**계획에 주는 뜻**
- 비공개 과제(2026년 말 30개 중 9개, 웹 6 · CLI 3 추정)는 저장소 · 테스트 · 해답을 모두 별도 비공개 저장소에 두고, 우리 인프라에서만 실행하며 결과만 공개한다. 모델 API에는 데이터 보존 없음 · 학습 제외 설정을 쓴다. 공개 · 비공개 점수 차이를 변형마다 기록한다.
- 비공개 과제는 날짜를 정해(연 1회 정도) 교체하고, 교체된 과제는 다음 판의 공개 과제로 돌린다. 공개 과제는 1년 안에 포화될 수 있으니 2027년 중 교체 계획을 처음부터 넣는다.
- 공개 과제의 모든 파일에 도담 전용 canary를 넣고 자동 검사로 확인하되, 방어책으로 계산하지 않는다. 새 모델마다 canary 재현을 시험하는 오염 탐지기로 쓴다. 공개 과제는 copyleft 라이선스로 낸다.
- 과제마다 작성일 · 공개일을, 모델마다 학습 컷오프를 기록하고, "공개 이후 과제"와 "공개 이전 과제" 점수를 나눠 보고한다.
- 실행 환경에서 정답에 닿는 길을 모두 막는다. git 기록은 기준 시점만 남기고, 외부 네트워크는 기본으로 막고(벤치마크 저장소 · HuggingFace 포함), 테스트 파일은 컨테이너 밖에 두고, 다른 언어로 쓴 참조 구현 파일을 두지 않는다.
- 바깥에서 관찰하는 숨은 테스트는 테스트 수정과 연산자 덮어쓰기를 구조적으로 막는다(추론). 남는 위험(공개 예시만 골라 처리하기, 호출 이력에 따라 다른 답 내기)에는 공개 예시와 다른 숨은 입력과 같은 요청을 반복해 일관성을 보는 테스트로 대응한다. 에이전트에게 "불가능하거나 모호하다고 알리고 끝내기" 선택지를 준다.
- 과제를 받아들이기 전에 빈 에이전트(빈 프로그램 · 고정값 출력)와 속이기 전용 에이전트를 숨은 테스트에 돌려 보고, 통과하는 과제는 버린다. 정답 테스트를 여러 번 돌려 일관성을 확인하고, "변경 전 실패 · 정답 뒤 통과"를 확인한다.
- 처음 몇 과제를 만들며 실측한 시간으로 2026-11 중순에 일정을 다시 잡는다. 외주 없이 만든다면 "작성자 1명 + 다른 1명 검토 + 적대적 에이전트" 구성이 현실적이다(추정). 과제 메타데이터에 전문가 예상 풀이 시간을 적고, 정답 스크립트를 자동 검사에서 계속 돌려 의존 패키지가 바뀌어도 과제가 깨지지 않게 한다.
- 과제 검토 · 교체 인력은 비교 기준 측정을 기존 언어 18개로 넓힐 16,200번 측정 일정에 별도 항목으로 넣는다.

## AI가 새 언어를 배우는 문제: 문서만으로는 모자라고, 실행 피드백과 예제가 큰 몫이다

**처음 보는 언어에서 70~80%대를 내려면 문서 + 실행(컴파일러) 피드백 + 검증된 예제가 함께 있어야 했다.** Huawei의 Cangjie(2024-06 첫 출시)로 코드 생성 155개를 잰 연구(사전 공개본, 2026-01)다(https://arxiv.org/html/2602.06976v1). [원문]

| 모델 | 문서 없음 | 문서 검색 1회 | 반복 검색 | 문서 + 실행 |
|---|---|---|---|---|
| DeepSeek-V3.2 | 3.23 | 40.00 | 47.10 | 63.23 |
| Qwen3-Max | 7.74 | 46.45 | 52.90 | 73.55 |
| Claude Sonnet 4.5 | 45.16 | 59.35 | 65.81 | 81.94 |

Qwen3-Max에서 실행 · 제출 검증만 빼도 73.55가 53.55로 떨어졌다. 저자는 실행 피드백이 없으면 "반복 검색보다 조금 나을 뿐"이라고 적었다.

**예제가 문서 검색보다 효과가 컸고, 작은 말뭉치로도 크게 올랐다.** Gleam · MoonBit을 학습 자원이 적은 언어로 잰 연구(IEEE TSE 채택, 동료 심사)에서 공개 코드는 Gleam 28.3M 토큰, MoonBit 13.7M 토큰이었다(https://arxiv.org/html/2606.16827v1). [원문]
- MBPP 첫 시도 정답률(0샷 / 예제 5개 / 공식 문서 검색): GPT-4o는 Gleam 20.31 / 30.37 / 24.03, MoonBit 16.54 / 40.51 / 32.68이었다. o3-mini는 MoonBit 15.01 / 45.92 / 40.79였다. 8번 비교 중 7번에서 예제 5개가 문서 검색보다 높았다(계산).
- 추가 사전학습만으로 Qwen 2.5 Coder 32B Base의 0샷이 Gleam 3.46 → 47.35, MoonBit 12.42 → 44.76이 됐고, 명령 학습을 이식한 뒤 53.83 · 53.04가 됐다. 명령 학습된 모델에 바로 추가 학습하면 명령 따르기가 망가졌다.

**완전히 처음 보는 생김새는 최신 모델도 직접 쓰지 못했다.** [원문, 동료 심사]
- PyLang(COLM 2026): 사전학습 말뭉치에 없는 최소 명령형 언어 352문제에서 모든 설정에서 Python이 최대 19% 높았다. 최신 모델은 80%에서 Python과 같은 알고리즘을 골랐지만 PyLang으로 동작하게 옮기지 못했다(https://arxiv.org/abs/2605.15607).
- Quasar(COLM 2026): 저자들이 "LLM은 이 언어를 본 적이 없어서 직접 생성하는 데 애를 먹는다"고 적고, LLM이 제한된 Python 부분집합으로 쓰면 변환기가 옮기는 방식을 택했다(https://arxiv.org/html/2506.12202v2).
- 형식 검증 언어 UCLID5(사전 공개본): 예시 3개를 주는 방식은 33문제 중 최대 4개만 문법에 맞았다(https://arxiv.org/html/2406.03636v4).

**바뀐 API는 큰 모델만 문서로 따라온다.** CodeUpdateArena(사전 공개본)에서 바뀐 API를 써야 통과하는 비율이 GPT-4 기본 2.7에서 갱신 문서를 앞에 붙이자 34.1이 됐다. 작은 모델은 6.7 · 11.8에 그쳤고, 학습으로 올리면 다른 능력이 67.1에서 37.3으로 깎였다(https://arxiv.org/html/2407.06249v3). [원문]

**낯선 언어는 성공률보다 토큰이 먼저 는다.** LiveCodeBench 100문제를 Python · Java · Rust · OCaml × 모델 5개로 푼 연구(사전 공개본, 2026)에서 Python 대비 토큰은 OCaml 1.28~1.69배, Rust 1.07~1.57배, Java 0.85~1.34배였다. GPT-5.5는 OCaml 문제의 27%에서 Python으로 먼저 시제품을 짰다(https://arxiv.org/html/2607.22807v2). [원문]

**1천~1만 줄 규모 과제에서는 행동의 41~65%가 읽기다.** MoonBit으로 낸 과제 22개(쉬움 6 · 보통 8 · 어려움 8)에서 gpt-5.3-codex가 19개, claude-opus-4.6이 15개를 풀었다. 어려움 과제 행동 중 읽기는 41.4~64.6%였고, 과제 하나에 입력 토큰이 수천만 개 들었다(예: gpt-5.3-codex 92.73M). 에이전트에게 MoonBit 문서를 얼마나 줬는지는 논문에 없다(https://arxiv.org/html/2602.09447v2). [원문, 사전 공개본]

**계획에 주는 뜻**
- 2026년 12월 문법 후보 비교는 후보마다 "0샷 · 예제 5개 · 명세 문서 · 명세 + 컴파일러 피드백" 네 조건으로 잰다. 조건이 4배라 실행비도 약 4배다. 0샷이 한 자릿수일 수 있다.
- 2027년 1~6월 최소 언어에 검증된 예제 모음 첫 판과 MCP `check` · `test` 피드백 루프를 문법 첫 판과 같이 넣는다. 예제가 문서 검색보다, 실행 피드백이 문서보다 큰 몫이었다. 2027년 하반기에 "1천만~3천만 토큰 말뭉치로 공개 모델 추가 사전학습" 실험을 선택 작업으로 둔다(GPU 비용 필요).
- "AI 전용 문법" 후보는 출발이 불리하다는 근거가 강해졌다. "AI가 이미 아는 생김새에서 출발" 원칙을 유지한다.
- 1.0 전 문법 변경은 문서가 아니라 진단과 자동 마이그레이션으로 푼다(바뀐 API는 큰 모델만 문서로 따라왔다).
- 비용 추정에 1천~1만 줄 과제처럼 과제 하나에 입력 토큰이 수천만 개 드는 경우를 넣는다. 파일 하나 · 함수 하나만 읽어도 이해되는 설계와 코드 조회 도구가 읽기 비용을 줄인다.

## 생태계: 빌려 쓰는 외부 함수가 보안 보고서를 "모든 권한"으로 덮는다

**새 언어는 대개 호스트 생태계에 기대어 시작했다.** Gleam은 `@external` 속성으로 Erlang · JS 구현을 부르고(https://tour.gleam.run/everything/), Zig는 C 헤더를 번역하며(`zig translate-c`), MoonBit은 백엔드 5개마다 외부 함수 호출을 따로 둔다(https://docs.moonbitlang.com/en/latest/language/ffi.html). Roc은 "그 플랫폼이 앱의 모든 I/O 기본 기능을 제공한다"(https://www.roc-lang.org/platforms). [원문] 도담 헌장은 외부 함수 호출을 "모든 권한"으로 치므로, 빌려 쓴 코드는 보안 보고서를 "모든 권한"으로 채운다(추론).

**생태계가 자라는 속도의 기준점.** Rust 1.0 뒤 첫 해에 "평균 주당 새 crate 53개"였다(https://blog.rust-lang.org/2016/05/16/rust-at-one-year/). Gleam은 1.0 뒤 약 138주 동안 1,734개로 주당 약 12.5개다(1.0 전 패키지도 포함한 상한, 계산). 2026-10-29 규모는 crates.io 364,276개, JSR 22,888개, PyPI 927,701개다. [원문, 직접 셈]

**2025~2026년 큰 공급망 사고는 거의 모두 "도둑맞은 계정이나 오래 사는 토큰" + "설치 · 빌드 때 저절로 도는 코드"였다.** [원문 · 2차]
- npm Shai-Hulud(2025-09): 유지보수자 계정을 뚫고 설치 후 스크립트를 넣은 자기 복제 웜으로 패키지 500개 넘게가 감염됐다(https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem). npm은 2FA 필수 게시 · 수명 7일 토큰 · trusted publishing으로 바꾸기로 했다(https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/). [원문] 2026-08-04에는 환경에 남은 게시 토큰을 수확하는 웜이 패키지 이름 444개로 퍼졌다. [2차, 업체]
- crates.io(2026-08-20): 오래된 패키지 arrayref의 새 판이 proc-macro2를 흉내 낸 가짜 패키지에 의존하게 바뀌었고, 그 빌드 스크립트가 컴파일 중 원격 바이너리를 받아 실행했다. 빌드만 해도 감염됐고, 노출은 약 86~107분이었다(https://www.wiz.io/blog/rust-supply-chain-attack-on-arrayref-significant-overlap-with-dprk-campaigns). [2차, 업체]
- Go: 악성 모듈이 Go 모듈 프록시에 3년 넘게 캐시돼 제공됐다. 캐시된 뒤 공격자가 Git 태그를 깨끗한 판으로 바꿔 GitHub를 봐서는 알 수 없었고, 체크섬은 캐시된 악성 사본과 일치해 막지 못했다(https://socket.dev/blog/malicious-package-exploits-go-module-proxy-caching-for-persistence). [원문, 업체]

**새 패키지 저장소의 최소 요건은 정리돼 있다.** CISA · OpenSSF의 패키지 저장소 보안 원칙(2024-02)은 최소 수준으로 이메일 확인, 강한 MFA(SMS · 이메일만으로는 안 됨), 중요한 변경 알림, 패키지 범위 API 키, 90일 안 처리 목표의 취약점 공개 정책, 타이포스쿼팅 대책, 해시 · 판 고정 설치를 든다. 둘째 수준은 피싱에 강한 MFA, 다운로드 상위 1% MFA 필수, 지운 이름 · 판 재사용 금지, 악성 신고 · 검출을, 셋째 수준은 trusted publishing, 빌드 출처 증명, 사건 투명성 로그를 든다(https://repos.openssf.org/principles-for-package-repository-security). [원문]

**중앙 저장소는 상시 운영 인력이 든다.** crates.io에는 재단이 고용한 엔지니어 2명과 보안 · 인프라 인력이 붙어 있고, 2025년에 악성 · 의심 crate 18건에 대응했으며, 스팸 정리로 예약 이름 500개 넘게를 회수했다(https://rustfoundation.org/wp-content/uploads/2026/01/2025-Annual-Report.pdf). [원문, 직접 추출] PyPI 다운로드 상위 360개 가운데 디지털 출처 증명을 내는 패키지는 166개(46%)다(https://trailofbits.github.io/are-we-pep740-yet/). [원문, 직접 셈]

**1.0 때 표준 라이브러리 크기는 언어마다 크게 다르다.** Go 1은 표준 패키지 129개로 HTTP · TLS · 암호 · 압축 · SQL 인터페이스 · HTML 템플릿까지 넣었다. Rust 1.0은 std 모듈 57개로 HTTP · JSON 없이 시작했다. Gleam 1.0 때 표준 라이브러리는 모듈 21개였고, 표준 라이브러리 1.0은 언어 1.0 약 2년 뒤(2026-04-18)에 나왔다(https://github.com/golang/go/tree/go1/src/pkg, https://doc.rust-lang.org/1.0.0/std/index.html, https://hex.pm/packages/gleam_stdlib). [원문, 직접 셈]

**계획에 주는 뜻**
- 외부 함수 호출 정책을 2027년 1~6월 최소 언어 안에서 정한다(설계 1~2주 + 헌장 개정). 선택지는 셋이다. HTTP · DB · 인증 · JSON을 표준 라이브러리에 넣어 빌려 쓸 일을 줄이기(Go 방식), 가져오는 외부 함수마다 권한을 선언하게 하고 WASI · 호스트가 그 권한만 주기(Roc 플랫폼 · WASI 방식), 외부 함수 호출을 표준 라이브러리와 승인된 플랫폼 패키지에만 허용하기. 브라우저 출력의 DOM 접근도 권한 붙은 호스트 함수로 설계한다.
- 1.0 생태계 기준은 패키지 수보다 "웹 과제 40개를 외부 패키지 없이 푼다"로 잰다. Go 1 규모(100개 넘는 패키지)는 1.0 목표로 무리다. 표준 라이브러리 판 번호를 언어와 뗄지(Gleam 방식) 2028년 초에 정한다. 공수는 근거 자료가 없으니 2027년 하반기에 HTTP 모듈 하나를 시범으로 만들어 잰다.
- 2028년 패키지 매니저는 중앙 저장소 없이 "Git 주소 + 해시 잠금 + 패키지 권한 선언"으로 시작한다(초기 Go 방식, 설계 2~4주). 중앙 저장소는 OpenSSF 최소 수준 전부 + trusted publishing + 출처 증명 + 판 삭제 경로를 출시 조건으로 1.0 무렵에 연다(설계 1개월 + 구현 2~3개월 + 상시 운영). 24시간 대응 인력이 없다는 것이 가장 큰 위험이다.
- "빌드 단계에서 패키지 코드가 실행되지 않는다"를 보장 문구로 명시할지 정한다. 도담은 매크로가 없으므로 지킬 수 있다. 새 판 · 새 의존성 뒤 대기 시간과 "판마다 권한 차이 승인"을 둔다. 불변 캐시 + 체크섬만으로는 처음 올라온 악성 판이 오래 살아남으므로 판 삭제 경로와 투명성 로그를 같이 둔다.
- 패키지 이름을 미리 잡으려면 빈 자리표시가 아니라 실제로 동작하는 최소 도구를 올린다(자리표시는 회수될 수 있다).

Rust는 호환이 깨지는 변경을 다음 판(2015 · 2018 · 2021 · 2024)으로 보내고, 판은 crate마다 고른다. 2024 판은 1.85.0(2025-02-20)에서 안정화됐다(https://doc.rust-lang.org/edition-guide/editions/index.html). [원문]

## 이름: 기술 이름은 비어 있지만 한국 상표에 걸릴 위험이 있다

**2026-10-29 기준 "Dodam"이라는 프로그래밍 언어는 찾지 못했다.** GitHub의 `dodam-lang` · `dodamlang` · `dodam-language`는 없고, `dodam`은 2015-05-25에 만든 개인 계정이다. 이름에 dodam이 들어간 저장소는 374개로 대부분 한국 앱이고, 학생 팀의 학교 플랫폼 '도담도담'과 npm `@b1nd/dodam-design-system`이 눈에 띈다. "dodam language" · "dodam compiler" 검색 결과는 0건이다. [원문, 직접 셈]

## 헌장과 부딪히는 것

조사 결과가 헌장 v0.4(2026-10-28)의 목표 · 숫자 · 일정과 어긋나는 곳이다. 헌장의 해당 내용을 먼저 적고, 조사 결과와 고칠 방향을 붙였다. 헌장을 고칠지는 소유자가 정한다.

**명세 1만 토큰.** 헌장은 "언어 명세 + 표준 라이브러리 요약이 1만 토큰 이하, 릴리스마다 재고 넘으면 릴리스하지 않는다"고 둔다.
- 조사에서 1만 토큰 안에 든 명세는 표준 라이브러리가 없는 Oberon-07 보고서(9,800)뿐이었다. Gleam 둘러보기는 15,002, Lua는 언어 17,871 + 표준 라이브러리 17,359, Go 명세는 56,334, MoonBit 언어 문서는 60,950이다.
- 도담은 여기에 권한 · 오염 추적 · 실행 위치 · 데이터 선언 · 웹 모델 · 계약과, 2028년 표준 라이브러리 목표(HTTP · DB · 인증 · JSON · 파일 · 동시성)의 요약까지 넣어야 한다.
- 재는 기준(토크나이저)이 헌장에 없다. "단어 수 × 1.3" 어림은 실제를 8~124% 적게 잡고, Claude 토크나이저로는 재지 못했다.
- 1만 안팎 명세로 AI가 잘 짰다는 통제된 결과가 없다. 오히려 예제와 실행 피드백이 명세보다 큰 몫이었다.
- 방향: "핵심 명세 카드 1만 토큰 이하 + 표준 라이브러리는 색인과 MCP 조회"로 고칠지 2027-06 전에 정한다. 그 근거로 2026년 12월에 5천 · 1만 · 2만 토큰 카드 실험(3~5일)을 한다. 재는 토크나이저도 헌장에 적는다.

**비교 대상 18개 언어를 시기마다 3번씩 재는 비용.** 헌장은 핵심 7개 언어는 매번, 참고 11개 언어는 일정의 각 시기가 끝날 때마다 재고, 같은 과제를 AI 모델 3개 이상으로 모델마다 3번씩 풀게 한다.
- 과제 100개를 비교 대상 18개 기존 언어 모두로 AI 모델 3개가 3번씩 짜면 16,200번이고, 대표 모델 셋 기준 한 번에 약 3.9만~39만 달러(중심 약 11.7만 달러)다(계산). 시기마다 다시 재면 이 비용이 시기 수만큼 쌓인다.
- 계정 월 상한(Anthropic Scale 등급 $200,000)과 속도 제한도 걸리고, 동시 100개로도 약 5일이 걸린다(계산).
- 헌장의 중복 지표("같은 외부 검출기로 잰 1천 줄당 중복률")는 참고 언어 전부에 걸 수 없다. jscpd · PMD CPD 모두 Gleam · MoonBit을 재지 못하고, PMD CPD는 Zig · Elixir · Haskell · OCaml도 못 잰다. 정적 보안 도구도 이 언어들 일부를 지원하지 않는다.
- 방향: AI가 기존 언어 7개로 짠 코드를 재서 도담이 넘어야 할 비교 기준을 만드는 630번 측정에서 실측한 분산으로 과제 수를 다시 계산하고, 참고 언어를 재는 범위(과제 · 모델 · 지표)를 그 숫자로 정한다.

**비공개 과제 30개로 가릴 수 있는 차이.** 헌장은 벤치마크 과제의 30%를 비공개로 보관하고, 개선 루프는 공개 과제로만 돌리며 평가는 비공개 과제로 한다.
- 과제 100개 중 비공개 30개만으로는 약 11~14%p(언어 상관 0.7이면 14.3%p, 0.9면 10.8%p)보다 작은 과적합이나 차이를 보지 못한다(계산). 2026년 말의 비공개 9과제는 이보다 훨씬 거칠다.
- 비공개 과제도 모델 API로 보내는 순간 시간이 지나며 조금씩 샌다(ARC가 공식으로 인정).
- 방향: 비공개 세트는 큰 과적합을 알리는 경보로 정의하고, 정밀 판정이 필요하면 비공개 과제를 늘리거나 연 1회 교체 · 보충한다. 모델 API에 데이터 보존 없음 설정을 쓴다.

**AI가 혼자 병합하는 조건의 "나빠지지 않는다".** 헌장은 보안 지표가 비공개 과제를 포함해 하나도 나빠지지 않고, 정확도 · 탄탄함이 나빠지지 않고, 실행 · 컴파일 속도는 5%보다 많이 나빠지지 않을 것(가안)을 요구한다.
- 이를 "관측값이 조금이라도 떨어지면 막는다"로 구현하면, 실제로 아무 변화가 없는 변경도 지표 하나에서 약 45%, 지표 셋 중 하나에서 약 84% 확률로 막힌다. "유의하게 나빠졌을 때만 막는다"로 하면 과제 30개 · 한 모델에서 실제 5%p 회귀의 73%가 통과한다(계산).
- 5%p 비열등성 여유를 판정하려면 3모델 × 3번 기준 약 71과제(중간 통과율 지표는 약 193과제)가 들고, 판정 1회에 약 639번 · 약 4.6천 달러다(계산).
- 성능 5% 문턱도 한 기계에서 한 번 재면 거짓 경보가 크게 늘었다. 다섯 기계에서 다섯 번씩 재야 대부분 5% 이하로 내려갔다.
- 방향: 지표마다 비열등성 여유와 필요한 과제 수 · 반복 수를 숫자로 헌장에 적는다. 성능은 같은 기계에서 무작위 순서로 반복해 재는 절차를 함께 적는다.

**1.0 일정 길이.** 헌장은 2026년 11~12월 방향 고정, 2027년 1~6월 최소 언어, 2027년 7~12월 0.1, 2028년 실제로 쓰기, 2029년~ 1.0으로 둔다(2.2~3.2년).
- 사람 팀 최단 선례는 Go의 4.5년(숙련자 3명 + Google), 정규 1명은 Gleam의 7.7년이다. 회사가 받치는 MoonBit도 1.0 목표를 두 번 넘겼고, Carbon은 메모리 안전 설계를 넣으며 0.1을 1년 넘게 미뤘다.
- 2027년 1~6월(6개월)에 메모리 모델 결정, 문법 첫 판, 권한 · 오염 · 경계 검사기, 쓰는 중인 코드 검사, 중복 검사, 스키마 · 마이그레이션 생성, 보안 보고서, Cranelift 출력, WASM 출력, JSON 진단, 예제 앱을 넣었다. 숙련 팀이 기능이 정해진 컴파일러를 다시 짜는 데(Roc) 487일이 걸렸다. WASM 출력은 Cranelift와 별개의 생성기(1.3만~2.7만 줄 선례)이고, 브라우저 출력은 다중 대상 언어에서 가장 늦게 익었다(Kotlin 웹은 3년째 Beta).
- 방향: 2027년 상반기 범위를 시제품 수준으로 못 박고, 0.x 안 재작성 1회를 위험 예비로 넣고, 1.0을 날짜가 아니라 벤치마크 숫자 기준으로 정의한다.

**메모리 모델을 시제품의 실행 속도로 고른다.** 헌장은 2027년 1~2월에 후보마다 작은 시제품을 만들어 정확도 · 탄탄함 · 실행 속도를 재고 고른다.
- 튜닝 전 시제품의 속도는 구현 성숙도에 크게 흔들린다. Ruby의 첫 MMTk 판은 기존 GC보다 약 4배 느렸고, Koka의 최적화 끈 판은 2배 넘게 느렸다.
- 동시성 모델(스택 있는 방식이냐 아니냐)이 메모리 모델 · 스택 맵 · WASM 출력과 묶이는데, 헌장은 동시성을 2028년 표준 라이브러리 항목으로만 둔다.
- 방향: 동시성 모델을 2027년 1~2월 결정에 넣고, 실행 속도는 "튜닝 여지"로 따로 적어 판정 비중을 낮춘다.

**외부 함수 호출 정책.** 헌장은 `Proc`(다른 프로그램 실행) · 외부 함수 호출(FFI) · `trust`를 "모든 권한"으로 친다.
- 새 언어는 대개 호스트 생태계를 빌려 시작했다(Gleam · Zig · MoonBit · Roc). 그대로면 C · JS를 부를 때마다 보안 보고서가 "모든 권한"으로 덮여 쓸모를 잃는다. 브라우저 출력의 DOM 접근도 JS 연결 코드(외부 함수)를 거친다.
- Rust crate의 19.11%가 `unsafe`를 직접 쓰고 대부분이 외부 함수 호출용이었다. 도담의 `trust` · 외부 함수도 암호 · TLS · DB 드라이버 바인딩에 몰릴 것이다(추론).
- 방향: "권한을 선언한 외부 함수"(Roc 플랫폼 · WASI 방식)를 2027년 1~6월에 정책으로 정하고 헌장을 고친다. 2028년 패키지 매니저 전에 넣는다. Unison은 C 외부 함수 호출 없이 1.0을 냈으므로, 1.0 범위에서 뺄 수도 있다.

**이름 상표.** 헌장은 이름 도담, 명령어 `dodam`, 확장자 `.dodam`, `dodam-lang` 조직과 `dodam-lang.org`(추천, 미구매)를 정했지만 상표 확인 항목이 없다.
- 한국에는 소프트웨어 분류의 '도담 · DODAM' 상표가 살아 있다. 2025-12-15에 출원된 'DoDam'(소프트웨어 상품 · 통신 · 소프트웨어 서비스 · 의료 서비스 분류)과 등록된 '(주)도담솔루션'(소프트웨어 서비스 분류, 지정 상품에 소프트웨어 · 프로그래밍)이 충돌 위험이다.
- 방향: 0.1 전에 변리사 조사를 일정에 넣는다. 0.1 전이 이름을 바꿀 마지막 기회다.

**1.0 뒤 하위 호환 약속에 예외가 없다.** 헌장은 "1.0 이후 문법은 하위 호환한다. 바꿔야 하면 자동 마이그레이션 도구를 함께 낸다"고만 적었다.
- 사람이 코드를 읽지 않으므로 건전성 버그가 곧 보안 구멍이다. 성숙한 언어도 건전성 구멍을 수십~수백 건 열어 두고 산다(Rust 170건 열림). 건전성 구멍을 고치면 그 구멍에 기대던 코드는 깨진다.
- Rust · Gleam · Nim은 1.0 약속에 컴파일러 버그 · 건전성 · 보안 예외와 범위를 적었다.
- 방향: 예외(건전성 · 보안 · 컴파일러 버그)와 범위(명세에 적힌 것)를 헌장에 적고, Rust 판 제도와 Go 옛 동작 스위치를 섞은 "판 + 자동 마이그레이션"으로 설계한다.

**웹 과제 프레임워크의 예(TypeScript는 Next.js).** 헌장은 웹 과제를 언어마다 가장 많이 쓰는 프레임워크 하나로 고정하고, 예로 TypeScript는 Next.js를 든다.
- Stack Overflow 2025에서 Next.js 20.8% 대 Express 19.9%로 사실상 동률이다. Next.js는 React 화면까지 포함한 풀스택이라 다른 언어의 서버 프레임워크와 비교하는 층이 다르고, 시작 시간 · 번들 크기 지표도 Next.js 빌드 산출물에 좌우된다. Go도 Gin 48% 대 net/http 32%라 "가장 많이 쓰는 것"과 "의존성 없는 표준" 중 무엇을 고를지 규칙이 필요하다. Rust · C++는 사용률 설문이 없다.
- 방향: 과제에 브라우저 화면이 있는지와 화면을 내는 방식을 먼저 정하고, 언어별 선택 규칙과 근거(설문 · 별 수)를 결정 기록에 적는다.

**"모르는 이름이나 막 등록된 패키지는 받지 않는다".** 헌장은 이 규칙으로 AI가 지어낸 패키지 이름을 노린 공격을 막는다.
- 2026-08 crates.io 공격은 막 등록된 패키지가 아니라 오래된 패키지(arrayref)의 새 판이었고, 빌드 스크립트로 퍼졌다. 헌장은 설치 스크립트를 없앴지만 "빌드 때 패키지 코드 실행 없음"은 따로 적지 않았다.
- 방향: 새 판 · 새 의존성 뒤 대기 시간, 판마다 권한 차이 승인, "빌드 단계에서 패키지 코드가 실행되지 않는다"를 보장 문구로 넣는다.

**"깨끗한 빌드는 Go와 같거나 빠르게"와 SMT 계약 검증.** 헌장은 깨끗한 빌드를 Go 이상으로 두면서, 계약을 Dafny식 SMT 정적 검증으로 넓힌다고 적었다.
- 백엔드를 Cranelift로 바꿔도 빌드는 5~15%만 빨라졌다. 빌드 시간은 프런트엔드(타입 추론 · 단형화)와 링크가 정한다. Go 표준 라이브러리 약 92만 줄은 Apple M4에서 6.3~8.3초다. SMT 검증을 같은 빌드 예산에 넣으면 목표를 깨기 쉽다(추론).
- 방향: "검증 빌드"와 "개발 빌드"를 나누거나 검증 결과를 정의 해시로 캐시하는 규칙을 적고, 단계별 시간 예산을 2027년 1분기에 정한다.

**코드 생성기를 빌려 쓴다는 결정과 메모리 안전 보장.** 헌장은 코드 생성기를 처음부터 만들지 않고 Cranelift · LLVM을 빌려 쓴다. 그런데 메모리 안전 보장의 신뢰 기반에 이 둘과 rustc가 들어간다.
- Cranelift는 2026년에도 샌드박스를 깬 최고 등급 코드 생성 공지가 여럿 나왔고, 그중 하나는 2020년부터 숨어 있었다. 백엔드끼리 차등 시험한 Rustlantis는 조용히 틀린 컴파일 24개를 찾았다(Rust 10 · LLVM 12 · Cranelift 1).
- 개발 빌드 Cranelift + 배포 빌드 LLVM을 함께 운영한 새 언어 선례가 없다. 같은 구상이던 Ante는 지금 LLVM과 C 백엔드를 쓴다.
- 방향: 신뢰 기반을 보안 보고서에 적고, 출력 지점의 실행 중 검사와 WASI 격리를 1.0 뒤에도 남기며, 두 백엔드 차분 테스트를 첫 백엔드부터 둔다.

**위협 모델의 세기.** 헌장은 "AI가 몰래 외부로 데이터를 보내는 코드"를 컴파일러가 막는다고 한다.
- Rust는 악성 프로젝트를 컴파일해서 생기는 공격과 건전성 문제를 기본적으로 보안 취약점으로 치지 않는다. 도담의 약속은 이보다 강해서, 검사기 건전성 구멍 하나가 곧 보안 취약점이 된다.
- 방향: "악성 코드를 컴파일해도 권한 · 경계 보장은 지킨다"를 헌장에 적을지 2026년 12월 헌장 확정 때 정한다. 적으면 대응 기한 · 공지 절차 · 영향 판 목록이 0.1 전에 필요하다.

**BaxBench 인용 숫자.** 헌장은 "BaxBench가 이 방식으로 재 보니 모델마다 맞게 짠 백엔드 코드의 약 절반이 공격에 뚫렸다(ICML 2025)"고 적었다.
- 2025년 논문 값이다. 2026-05-22 리더보드 1위(Claude Opus 4.5 Thinking)는 정답 86.2% 가운데 정답이면서 안전한 것이 56.1%라, 정답 중 뚫린 비율은 약 35%다(계산). 사이트의 "62%"는 정답률이 아니라 "틀렸거나 취약점이 있는 비율"이다.
- 방향: 문장에 날짜와 모델을 붙이거나 최신 값으로 고친다.

**2026년 11~12월 "다음 할 일"의 날짜.** 헌장은 11/9~11/22에 과제 10개와 측정기, 11/23~12/6에 AI가 기존 언어 7개로 짠 코드를 재서 도담이 넘어야 할 비교 기준을 만드는 630번 측정, 12/7~12/20에 과제 30개와 "문법 후보 2~3개를 AI에게 명세만 주고 짜게 해서 비교"를 둔다.
- 사람 공수: 과제 30개는 90~510시간(계산)인데, 같은 기간 전업 1명의 가용 시간은 약 348시간이다. 상한이면 전업 약 1.5명이 들고, 사람은 소유자 1명이다.
- 계정 한도: Anthropic 월 상한(Start $500 · Build $1,000), Google 셋째 등급의 30일 대기, Gemini 4 Argon의 12/1 가격 두 배 때문에 11/2~11/8 주에 계정 작업을 끝내지 않으면 11/23 측정이 멈출 수 있다.
- 문법 후보 비교: 처음 보는 생김새는 명세만으로 최신 모델도 직접 쓰지 못했다(Quasar · PyLang). 명세만 주는 조건은 0샷이 한 자릿수일 수 있다. 네 조건(0샷 · 예제 · 명세 · 명세 + 컴파일러 피드백)으로 재면 실행비가 약 4배다.
- 방향: 처음 몇 과제의 실측 공수로 11월 중순에 일정을 다시 잡고, 계정 작업을 11월 첫 주 할 일에 넣고, 문법 후보 비교 조건과 예산을 고친다.

## 못 찾은 것

조사 노트가 확인하지 못했다고 적은 것이다. 이 숫자들 없이 계획을 세운 곳은 추정이다.

**선행 언어**
- Swift 1.0 날짜를 원문으로 확인하지 못했다.
- Go · Swift · Dart · Carbon · MoonBit의 1.0(또는 지금) 무렵 정규 인원, Rust 1.0 때 Mozilla 인원을 찾지 못했다.
- Julia · Elixir · Nim · Unison · MoonBit을 받친 회사 · 단체의 자금 액수를 찾지 못했다.
- Rust · Zig 0.1, Elixir · Nim · Elm의 첫 사용 가능 판 날짜, Carbon · MoonBit의 첫 공개 날짜를 원문으로 확인하지 못했다.
- Swift 2 → 3의 소스 깨짐, Elm 정체의 공식 이유, Kotlin 새 컴파일러(K2) 재작성 경위를 확인하지 못했다.
- Mozilla 2020년 감원이 Rust에 준 영향, 대기업 언어 중단 사례(Fortress · Ceylon), 개인 언어 정체 원인(Pony · Vale), Eve · Dark의 공식 사후 분석을 열지 못했다.
- gopls · rustfmt · Swift 패키지 매니저 · Zig 패키지 매니저의 첫 정식 릴리스 날짜를 확인하지 못했다.

**AI 에이전트 개발 사례**
- AI가 대부분 짠 데이터베이스 사례를 찾지 못했다.
- Cursor 브라우저 · OpenAI 사례의 비용, CURSED · vinext의 줄 수, Rue 원문 숫자, Google 운영체제 시연의 원문을 확인하지 못했다. 모든 사례가 자기 보고이고 독립 감사가 없다.
- METR가 2026-09-08 뒤 갱신을 멈춰 Claude Opus 4.7 · 4.8, Claude Fable 5, GPT-5.5의 시간 지평 값이 없다. METR 2025 실험의 신뢰구간(+2%~+39%)은 원문에서 직접 보지 못했다.
- 장시간 에이전트의 회귀 비율을 체계적으로 잰 동료 심사 연구는 SlopCodeBench 말고 찾지 못했다.

**컴파일러 · 런타임 기술**
- Cranelift 코드가 "평균 14% 느림"과 "일부 벤치마크 2배 느림"의 조건(2020년 논문)을 직접 확인하지 못했다. 2024~2026년에 Cranelift와 LLVM의 생성 코드 속도를 같은 기계에서 비교한 독립 자료가 없다.
- Cranelift를 쓰는 언어가 디버거용 변수 위치 정보를 내는 방법, Wasmtime GC 구현에 든 줄 수 · 인월, Ante가 Cranelift를 뺀 이유를 찾지 못했다.
- LLVM 최신 판의 정적 라이브러리 크기 · 빌드 시간, QBE "70% 성능" 주장의 독립 측정, Koka · Lean이 C를 거치는 비용을 찾지 못했다.
- MMTk 바인딩 하나를 만드는 데 든 인월, MMTk-Julia의 성능, Wasmtime 밖에서 Cranelift 스택 맵으로 정확한 GC를 구현한 언어를 찾지 못했다. Wasmtime 문서의 "not yet functional" 문장과 블로그 중 어느 쪽이 최신인지 확인하지 못했다.
- Swift 패키지 생태계의 2025-05 뒤 데이터 경쟁 무오류 비율, Rust의 동시성 표기 마찰을 숫자로 보인 자료, tokio 위에 언어 런타임을 얹은 부하 숫자, 그린 스레드 · 효과 처리기 런타임을 짓는 데 든 공수를 찾지 못했다.
- rust-analyzer의 키 입력 → 진단 지연, Salsa의 취소 · 메모리 축출 비용, tree-sitter 점진 재파싱 속도, Carbon의 숫자 목표를 찾지 못했다. Jai의 초당 25만 줄은 비공개 자료라 확인할 수 없다.
- 편집 뒤 검사 지연이 AI 에이전트의 성공률 · 비용에 얼마나 영향을 주는지 잰 연구를 찾지 못했다.
- Safari 26.2 · 27의 정식 출시일과 JSPI 실제 출하, Wasm → DOM 호출 한 번의 비용(ns), Kotlin/Wasm 번들 크기, WasmGC 언어(Kotlin · MoonBit · Flutter)의 같은 잣대 화면 벤치마크를 찾지 못했다. WASI 1.0은 날짜가 없다.

- 정보 흐름 타입 사용자 통제 실험, 2020년 뒤 언어 차원 정보 흐름 검사를 실무에 쓴 회사 사례를 찾지 못했다.
- 정규식 역참조 · 앞뒤 살피기 각각의 사용 비율, Capital One 사고의 침입 경로, AWS가 새 인스턴스 메타데이터 기본값을 바꾼 날짜, 기본 한도가 실제 사고를 얼마나 줄였는지를 찾지 못했다.
- Python 암호 API 사용성 실험의 라이브러리별 성공률, LLM이 고수준 · 저수준 암호 API를 쓸 때의 오용률 비교, 2025~2026년 서버에서 Argon2id 한 번에 걸리는 시간을 찾지 못했다.
- 자동 생성 엔드포인트 사고 통계, 높은 경합에서의 직렬화 실패율, 행 수준 보안 일반 부하를 잰 동료 심사 자료, 2026-08 행 수준 보안 취약점의 재현 조건을 찾지 못했다.
- CakeML의 공수, RustBelt 증명 줄 수, Tree Borrows의 수치, AI가 컴파일러 정확성 증명이나 비간섭 증명을 끝까지 해낸 사례(권한 포획 계산법 사례 말고), 증명 작업의 돈 비용을 찾지 못했다.
- TypeScript 타입 검사기 퍼징 연구, Wasmtime 퍼징의 계산 규모와 찾은 버그 수, Csmith 같은 생성기를 만드는 데 든 인원 · 기간, 2026년 Rust 건전성 신고 급증의 원인, 2026-04 LLM 감사의 오탐률 · 비용을 찾지 못했다.
- 상용 감사 회사의 전문가 1주 단가, 언어 · 툴체인 감사 보고서 일부(Cure53), 코드가 없는 새 언어가 외부 감사 기금 대상이 되는지를 확인하지 못했다.
