# Pilot measurement record — 17 November 2026

Dodam is a programming language built so that AI writes it correctly and safely, and it is still in its design phase. Before the design is fixed, we first measure how well AI writes in existing languages. Those numbers become the bar Dodam must beat. This document records the pilot: the first time that measurement was run from start to end. It says what was run and how, what came out, what one run used, and how those numbers were used to judge the next measurement and the December schedule.

Every number in this document comes from two data files kept in the repository with it. One holds only the measured values copied from the run records; the other holds the estimates computed from them, with their assumptions. If a number in the document differs from the data, an automatic check fails.

## At a glance

- One sign-up task was run once in each of 7 existing languages, 7 runs in all. All 7 ran to the end.
- 6 languages got the full score (1.0) on both steps. C++ passed every functional check but failed one security check, so it scored 0.0 on both steps.
- In one run the AI worked for 79.2 seconds on average, and the run took 223.9 seconds from start to end on average.
- This pilot could not settle what percent of the subscription limits one run uses. The weekly utilization did not move by its display step (1 percentage point) over 6 runs, and the tool did not report the 5-hour limit. Only an upper bound is known.
- The login token was never seen on a command line (the process table was read 2,820 times), it was not found in any file the runs left, and no container was left.
- The first baseline measurement of 630 runs takes 14 nights on this machine, running at night only, if every run is like the ones measured here. Larger models and other tasks have not been measured.
- The pilot finished earlier than planned. The dates of the December schedule are not changed, because the number that would justify moving them earlier or later (how long a larger model works) has not been measured yet.

## What was run and how

- **Date**: 17 November 2026 (UTC).
- **AI**: Claude Code 2.1.326, Anthropic's official command-line tool. It was pinned to that version unmodified, and the run records show the same version. No model was chosen, so the tool's default, claude-sonnet-5-5, was used. It ran on a subscription login.
- **Task**: a sign-up and login service (web-signup). An HTTP API where people sign up, log in and read their own account. It has 2 steps: the first builds it from nothing, the second adds a changed requirement (logging out and editing the name).
- **Languages**: Python, TypeScript, Java, C#, Go, Rust and C++, once each.
- **Isolation**: the AI wrote its code inside a container for each language, not on this machine. The result was judged with hidden tests the AI cannot see, in another container with no network and no credentials.
- **Nothing was emulated**: a real model wrote the code on a real subscription account, and the real judge judged it.
- **Order**: the runs came in 3 batches. Python ran first, TypeScript about 3.5 hours later, and the other languages right after it. The runner was changed in between.
- **When the runner stops by itself**: it starts no new run once the weekly utilization reaches 50%, or once the agents it ran have worked 30 minutes within 5 hours. One run may take at most 3 hours. Nothing was stopped this time.

### The C++ result

The C++ program built and passed every functional and boundary check in both steps: 6 of 6 functional and 25 of 25 boundary checks in the first step, 8 of 8 and 31 of 31 in the second.

What failed was one security check. The program the AI wrote served the files of its own folder. When the judge asked for `GET /CMakeLists.txt`, the build file that says how this program is built came back as it is. A server written this way can hand out its source code or its settings the same way, so it counts as a vulnerability. The program passed 7 of 8 security checks in the first step and 8 of 9 in the second. Each step counted 1 vulnerability, and in the second step the same check still failed, which also counted as 1 check of the earlier step still broken after the change.

This is the AI's result, not a fault of the judge. At the start the C++ folder held only that one build file, so serving files came from the code the AI wrote. In the other 6 languages, 0 checks failed.

With one run per language, this does not show that code written in C++ is less safe. It does show that the security checks catch a problem the functional checks alone do not see.

## What one run used

### Measured: time and tokens

- **AI working time**: 79.2 seconds per run on average (shortest 63.4, longest 109.0). The 7 runs add up to 9.2 minutes.
- **Whole run** (preparing the containers, the AI's work, the build and the judging together): 223.9 seconds per run on average (between 160.2 and 314.1). The 7 runs add up to 26.1 minutes.
- **Judging time**: 64.5 seconds per run on average (both steps together).
- **Tokens** (the 7 runs together): input 116, cache read 1,068,528, cache write 151,078, output 68,106. There were 60 turns in all.
- **The amount the tool writes down**: 1.39 dollars for the 7 runs together. The tool computes this figure by itself; the runs were on a subscription, so it is not money that was charged. Of the limit notices, 0 said that extra paid usage was in use.

### The weekly limit: only an upper bound

While it runs, the tool reports the weekly utilization in whole percent.

- Over the 6 runs from TypeScript to C++, the first reading was 35% and the last reading was 35%. It moved by 0 percentage points.
- Of the 7 runs, 0 had a first reading that differed from its last.
- The earlier rise of 8 percentage points, from 27% to 35%, is not what runs used. The 27% is the value stored when the Python run ended, and the 35% is the first reading of the TypeScript run about 3.5 hours later. No measurement ran in between; the same account was used for development work. The same holds for the 25% and 27% of the Python run: the first value had been stored earlier.

**What this bounds.** The figure is shown in whole percent, so the 6 runs used less than 1 percentage point together. Divided by the runs, that is less than 0.17 percentage point per run on average (1 ÷ 6).

**What it cannot tell.** There is no lower bound. It cannot tell whether one run uses close to that upper bound or a hundredth of it. The upper bound times 630 runs is 107.1 percentage points, so this number cannot even tell whether the whole baseline measurement fits inside one week's limit. The runner stops at 50% weekly and the figure stood at 35% at the end, which leaves 15 percentage points. In the worst case (0.17 percentage point per run) that room is used up after 88 runs (15 ÷ 0.17). In fact far more runs may fit.

**What further measurement would settle it.** Run the same run 21 times in a row at a time when nothing else uses the account, and read the weekly utilization at the start and at the end. That resolves one run down to 0.05 percentage point (1 ÷ 21).

### The 5-hour limit: the tool does not report it

Of the 7 runs, 0 reported the utilization of the 5-hour limit. So this limit was kept only by the runner's own guard. The guard adds up the working time of the agents the runner ran and starts no new run once it reaches 30 minutes within 5 hours. After the 6 runs from TypeScript to C++ the guard had counted 8.0 minutes. After the Python run it had counted 1.2 minutes; the runner was then changed and the guard keeps its record in a new place, so the TypeScript run started from 0.0 minutes.

**What this bounds.** Only that 8.0 of the 30 minutes the runner set for itself were used.

**What it cannot tell.** How much of the account's real 5-hour limit was used. The guard's 30 minutes are not a measured value; they were chosen to be careful. The guard does not count other work done on the same account.

**What further measurement would settle it.** As long as the tool does not report this value, run records alone cannot tell. The cheapest way is to read it from the account's usage screen before and after a row of runs and write it down. Only the account's owner can see that screen.

## Safety

- **Was the token seen on a command line?** While the runs went on, the process table of this machine was read every 0.5 seconds: 2,820 readings in all, and 0 of them showed the token. Of the 2,820 readings, 2,439 belong to the 6 runs made after the runner was changed, and 984 were taken while the AI worked.
- **Was the token left in the results?** Every file the runs left was searched for the token. 7 of the 7 scans were clean: 0 places found, 0 files that could not be read and so could not be checked.
- **What was left**: 0 containers. The watch stopped a run midway 0 times. Problems found in the judging environment: 0. Errors of the AI tool: 0.
- **The limit of this check**: the watch of the process table sees command lines only. The environment variables of running processes were not looked at. With readings 0.5 seconds apart, a process that came and went faster can be missed.

## The limits of this pilot

- **One run per language.** We do not know how far the score and the time spread when the same run is repeated.
- **One task.** Other tasks may take longer or shorter.
- **One model, and one that was not chosen.** The tool is what was pinned; the tool picked the model (claude-sonnet-5-5). Larger models were not measured.
- **One company's model.** Numbers measured on one company's models alone do not fix the core design of the language.
- **The limits.** Only an upper bound is known for the weekly limit, and nothing for the 5-hour limit.
- **Nothing was emulated.** The numbers come from real runs. Their weakness is the small sample.

## How long the first baseline measurement takes

The charter plans the first baseline measurement as 630 runs: 3 AI models write 10 tasks in the 7 existing languages 3 times each (3 × 10 × 7 × 3 = 630). The table that comes out of it is the bar Dodam must beat.

Assumptions:

- One machine, this one, one run at a time.
- Runs at night only. A night is 8 hours, and every night is used.
- The runner's guard stays as it is (30 minutes within 5 hours). A new run starts only while the counted time is below the limit.
- The AI working time and the whole time of a run are the averages measured here (79.2 and 223.9 seconds). Where the AI working time is taken as a multiple, only the added working time is added to the whole time; judging and preparing the containers are taken to stay the same.
- The subscription's weekly limit and its real 5-hour limit are taken not to stop anything. As said above, this has not been confirmed.

As measured:

- At 1.32 minutes per run the guard lets 23 runs start in one 5-hour window. The last of them starts because the time counted until then is just below 30 minutes. These 23 runs are over in 85.8 minutes.
- Once the first runs leave the 5-hour window, the same number can run again, and this second row also ends inside the 8 hours. That makes 46 runs a night.
- 630 runs divided by 46 a night, rounded up, is 14 nights.
- The AI works 13.9 hours in all. In the unit of the schedule simulation, the AI working day (what one agent does in 16 hours), that is 0.87 working days. The plan had taken 0.5 hours per run and set aside 20 working days.

| AI working time of one run | Minutes | Starts in one window | Runs a night | Nights | AI working time in all (hours) |
|---|---|---|---|---|---|
| As measured | 1.32 | 23 | 46 | 14 | 13.9 |
| If 2 times the measured value (an assumption) | 2.64 | 12 | 24 | 27 | 27.7 |
| If 4 times the measured value (an assumption) | 5.28 | 6 | 12 | 53 | 55.4 |

The charter gives this measurement the 21 nights from 12 December 2026 to 1 January 2027. To end inside them it needs 30 runs a night, and for that the AI working time of a run must not exceed 2.14 minutes on average (1.62 times the measured value).

**Not measured.** One of the 3 models has been measured, and one of the 10 tasks. How much longer a larger model works is known only once it is measured. The 2 times and 4 times in the table are assumptions, not measurements.

**A cheap next measurement.** One night is enough. Run the same task with the same model 21 times (the 7 languages 3 times each). That is about 27.7 minutes of AI working time, which fits in one window of the guard (30 minutes), and it is over in about 78.4 minutes. It gives the spread of a repeated run and how many percentage points the weekly utilization moves per run. When the guard's window opens again the same night, run the largest model 7 times (once per language) to measure how many times the measured value its working time is.

No new run was made while this document was written.

### The verdict

- **The pilot**: finished on 17 November 2026. Its mark of being done, "we know what percent of the subscription limit one run uses", is half met. Time and tokens are measured; for the limits only an upper bound is known. The other half is met by the one-night measurement described above.
- **The baseline measurement (12 December 2026 to 1 January 2027)**: the dates stay. At the plan's capacity the chance of ending by 1 January 2027 was 37% with the inputs before the pilot. After the pilot it is 53% if every run is like the measured ones, 18% if the AI working time is 2 times, and 0% if it is 4 times. The middle dates are 2026-12-30, 2027-01-13 and 2027-02-10 in that order. The end of the row as it stands lies between "as measured" and "2 times". Which of them holds is known only once a larger model is measured, so for now there is no ground to move the dates earlier and none to move them later. The day it starts depends on the 10 tasks and on the measuring tool being complete, and the pilot did not change the amount of that work.
- **The direction-fixing gate (24 February 2027)**: the date stays. The chance of reaching it by that day was 49% with the inputs before the pilot, and after the pilot it is 61%, 46% and 0% in the same order.
- **The time freed by finishing early**: 19 days remain until the day the pilot was to end. They go to the two pieces of work that decide when the baseline measurement starts (the 10 tasks and completing the measuring tool) and to the one-night measurement described above. Once its numbers are in, they say which row of the table holds, and the dates are judged again then.
- **About the table for one Claude account**: under that assumption the chance that the baseline measurement ends by 1 January 2027 was 2% before the pilot and is 5% after it as measured, and the middle date moves earlier from 2027-04-28 to 2027-03-10. The gap to the plan's capacity does not come from the pilot; it comes from the capacity assumption. The pilot itself, on the other hand, was finished with one Claude account 12 days earlier than planned. This pilot could not confirm whether about 5 working days a week is right, so this table is not used as a ground for changing dates; it is written down to show how far the schedule slips if that assumption holds.
