# Pilot measurement record — 17 November 2026

Dodam is a programming language built so that AI writes it correctly and safely, and it is still in its design phase. Before the design is fixed, we first measure how well AI writes in existing languages. Those numbers become the bar Dodam must beat. This document records the pilot: the first time that measurement was run from start to end. It says what was run and how, what came out, what one run used, and how those numbers were used to judge the next measurement and the December schedule.

Every number in this document comes from two data files kept in the repository with it. One holds only the measured values copied from the run records; the other holds the estimates computed from them, with their assumptions. If a number in the document differs from the data, an automatic check fails.

## At a glance

- One sign-up task was run once in each of 7 existing languages, and these 7 runs are the ones counted. All 7 ran to the end. The same task had been started 2 more times in Python earlier that day; they are told below, with why they are not counted.
- Of the 7 counted runs, 6 languages got the full score (1.0) on both steps. C++ passed every functional check but failed one security check, so it scored 0.0 on both steps.
- In one run the AI worked for 79.2 seconds on average, and the run took 223.9 seconds from start to end on average.
- This pilot could not settle what percent of the subscription limits one run uses. The weekly utilization did not move by its display step (1 percentage point) between two readings. All that gives is an upper bound (less than 0.21 percentage point per run). The tool did not report the 5-hour limit.
- In the 7 runs whose process table was watched, the login token was never seen on a command line (2,820 readings). The 2 starts before them were not watched, and the run tool they used was the version that passes the token on a command line. In the files the runs left, the token was found in none of the 9 scans.
- The first baseline measurement of 630 runs takes 14 nights on this machine, running at night only, if every run is like the ones measured here. Larger models and other tasks have not been measured.
- The pilot finished earlier than planned. The dates of the schedule stay as the plan's dates at the plan's capacity (one account per AI company, about 15 working days a week), and the figures for today's conditions are given beside them. Under today's conditions (one Claude account shared with the owner's other work, counted as about 4 working days a week) the chance that the baseline measurement ends by 1 January 2027 is 2%. What one account gives in a week is an assumption, not a measured value.

## What was run and how

- **Date**: 17 November 2026 (UTC).
- **AI**: Claude Code 2.1.326, Anthropic's official command-line tool. It was pinned to that version unmodified, and the run records show the same version. No model was chosen, so the tool's default, claude-sonnet-5-5, was used. It ran on a subscription login.
- **Task**: a sign-up and login service (web-signup). An HTTP API where people sign up, log in and read their own account. It has 2 steps: the first builds it from nothing, the second adds a changed requirement (logging out and editing the name).
- **Languages**: Python, TypeScript, Java, C#, Go, Rust and C++, once each.
- **Isolation**: the AI wrote its code inside a container for each language, not on this machine. The result was judged with hidden tests the AI cannot see, in another container with no network and no credentials.
- **Nothing was emulated**: a real model wrote the code on a real subscription account, and the real judge judged it.
- **Order**: the 7 counted runs came in 3 batches. Python ran first, TypeScript about 3.5 hours later, and the other languages right after it. The runner was changed in between.
- **When the runner stops by itself**: it starts no new run once the weekly utilization reaches 50%, or once the agents it ran have worked 30 minutes within 5 hours. One run may take at most 3 hours. Nothing was stopped this time.

### The C++ result

The C++ program built and passed every functional and boundary check in both steps: 6 of 6 functional and 25 of 25 boundary checks in the first step, 8 of 8 and 31 of 31 in the second.

What failed was one security check. The program the AI wrote served the files of its own folder. When the judge asked for `GET /CMakeLists.txt`, the build file that says how this program is built came back as it is. A server written this way can hand out its source code or its settings the same way, so it counts as a vulnerability. The program passed 7 of 8 security checks in the first step and 8 of 9 in the second. Each step counted 1 vulnerability, and in the second step the same check still failed, which also counted as 1 check of the earlier step still broken after the change.

This is the AI's result, not a fault of the judge. At the start the C++ folder held only that one build file, so serving files came from the code the AI wrote. In the other 6 languages, 0 checks failed.

With one run per language, this does not show that code written in C++ is less safe. It does show that the security checks catch a problem the functional checks alone do not see.

### The 5-hour limit: the tool does not report it

Of the 7 runs, 0 reported the utilization of the 5-hour limit. So this limit was kept only by the runner's own guard. After the 6 runs from TypeScript to C++ the guard had counted 8.0 minutes. After the Python run it had counted 1.2 minutes; the runner was then changed and the guard keeps its record in a new place, so the TypeScript run started from 0.0 minutes.

**What it cannot tell.** How much of the account's real 5-hour limit was used. The guard's 30 minutes are not a measured value; they were chosen to be careful. The guard does not count other work done on the same account.

**What further measurement would settle it.** As long as the tool does not report this value, run records alone cannot tell. The cheapest way is to read it from the account's usage screen before and after a row of runs and write it down. Only the account's owner can see that screen.

## How long the first baseline measurement takes

Assumptions:

- One machine, this one, one run at a time.
- Runs at night only. A night is 8 hours, and every night is used.
- The runner's guard stays as it is (30 minutes within 5 hours). A new run starts only while the counted time is below the limit.
- The AI working time and the whole time of a run are the averages measured here (79.2 and 223.9 seconds). Where the AI working time is taken as a multiple, only the added working time is added to the whole time; judging and preparing the containers are taken to stay the same.
- The subscription's weekly limit and its real 5-hour limit are taken not to stop anything. As said above, this has not been confirmed.

### What the next measurements can and cannot settle

All of this is worked out with the runner's guard as it is now.

**First night: the same task with the same model, as many runs as the guard lets one night hold.** That is 46 runs (6 rounds of the 7 languages and 4 more). The AI works about 60.7 minutes.

- The weekly limit. A step reports once, early, so 45 runs lie wholly between the first and the last reading of the night. If the figure does not move between them, one run uses less than 0.022 percentage point (1 ÷ 45) and 630 runs use less than 14 percentage points. That is inside the 15 percentage points of room that were left on the day of the pilot. If the figure moves by one step, 630 runs may use up to 28 percentage points, and whether they fit that room stays open. Unless the week of the weekly limit starts anew between the two readings, other work on the same account can only raise the figure. Then "it did not move" can be trusted, while "it moved" may be that other work. When the week starts anew the figure drops, and "it did not move" cannot be trusted. So the measurement is made on a night that does not hold the time at which the weekly limit starts anew, which the usage screen of the account shows, and a night whose last reading is lower than its first is not used.
- The spread. 4 languages are run 7 times and the other 3 are run 6 times, which shows how far the score and the time of a repeated run spread.
- What stays open. 2 models and 9 tasks are still unmeasured. How much room there is on that day depends on how much the account was used that week.

**Second night: the largest model, once per language, 7 runs.**

- Does it fit the guard? If that model's AI working time is up to 3.78 times the measured value (5 minutes per run), all 7 runs start in one window. If it is longer, the remaining runs wait until the window opens again, and up to 7.57 times (10 minutes per run) they still end within one night. At 4 times, for example, 6 runs start in the first window and 7 end within the night. Beyond that, one more night is used.
- What it settles. How many times the measured value that model works on this task. Every run that ends gives one value.
- What stays open. 1 model, 9 tasks, and the share of the weekly limit a larger model takes: with 7 runs an unmoved figure only says less than 0.17 percentage point per run.

So these two nights do not settle which row of the table above holds. A row of the table is an average over 3 models and 10 tasks; the two nights measure 2 models and 1 task. What they give is a number for one part of that average.

**A way to measure without any new run (a separate piece of work; it is not built here).** The Claude Code session records on this machine hold the tokens used, the model and the time. Adding up from those records the tokens used between two readings of the weekly utilization gives what one percentage point costs in tokens, and from that what a week gives. The day of the pilot already has two such readings, 27% and 35%.

- What it settles. What one account gives in a week, which is the capacity assumption of the schedule simulation.
- What stays open. What was used on that account outside this machine is not in the records. Tokens of different models may weigh differently. The 5-hour limit cannot be found this way either.

### The verdict

- **The pilot**: finished on 17 November 2026. Its mark of being done, "we know what percent of the subscription limit one run uses", is half met. Time and tokens are measured; for the limits only an upper bound is known.
- **What happens to the dates (the decision)**: the dates of the schedule stay as the plan's dates at the plan's capacity, and are labelled so.
