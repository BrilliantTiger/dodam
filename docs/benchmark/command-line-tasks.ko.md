# 명령줄 프로그램 과제 — 형식과 판정

도담 벤치마크의 과제는 웹 서비스만이 아니다. 로그 분석기, CSV/JSON 변환기, 설정 파일 검사기처럼 한 번 실행되고 끝나는 명령줄 프로그램도 과제로 낸다. 이 문서는 그런 과제를 어떻게 적고, 판정기가 어떻게 판정하고, 그 판정이 어떤 규칙을 지키는지 적는다. 숫자는 모두 2026년 11월 17일에 이 저장소의 측정 기계(Apple M4, colima 위의 Docker)에서 잰 것이다.

## 한눈에

- 판정기는 프로그램에 **인자 · 표준 입력 · 입력 파일**을 주고, 바깥에서 **표준 출력 · 종료 코드 · 남긴 파일**만 본다. 프로그램 안은 보지 않는다.
- 테스트 한 벌로 일곱 언어(Python · TypeScript · Java · C# · Go · Rust · C++)를 모두 판정한다.
- 숨긴 테스트는 기능 · 경계값 · 보안으로 나뉘어 따로 보고된다. 과제에는 만들기 단계와 수정 단계가 있고, 수정 단계에서는 앞 단계의 테스트를 다시 돌려 깨진 것을 센다. 웹 과제와 같다.
- 프로그램은 테스트 하나(사례 하나)마다 새 작업 폴더에서 시작한다. 시간 · 메모리 · 출력 크기 · 프로세스 수 · 파일 크기에 한도가 있다. 한도는 프로그램이 무엇을 하든 넘을 수 없는 선이고, 넘기려 한 사례는 그 사례만 실패하거나 처음부터 가져가지 못한다.
- 빌드도 프로그램과 똑같이 다룬다. 테스트는 빌드가 시작되기 전에 닫힌다.
- 견본 과제는 CSV를 JSON으로 바꾸는 변환기다. 준비한 풀이 70개(언어마다 정답 2개, 취약 풀이 6개, 고장 풀이 2개)가 일곱 언어 모두에서 의도한 판정을 받았다.

## 과제 폴더

명령줄 과제도 웹 과제와 같은 모양의 폴더다. 다른 점은 `task.toml`의 두 군데뿐이다. `interface`가 `"cli"`이고, 서버 설정 대신 사례 하나의 한도를 적는 `[cli]`가 있다.

```toml
schema = 1
id = "cli-csv-json"
title = "CSV to JSON converter"
domain = "cli"
kind = "new"
interface = "cli"
visibility = "public"
canary = "dodam-bench-canary-…"
languages = ["python", "typescript", "java", "csharp", "go", "rust", "cpp"]

[cli]                    # 사례 하나(숨긴 테스트 하나)의 한도
case_timeout_sec = 5     # 그 사례에서 프로그램을 돌린 시간을 모두 더한 값
case_memory_mb = 512     # 프로그램의 모든 프로세스가 실제로 쓰는 메모리의 합
case_output_kb = 4096    # 표준 출력과 표준 오류를 더한 크기
case_processes = 64      # 프로세스 수. 스레드도 하나로 센다
case_disk_mb = 64        # 사례 폴더 전체에 쓸 수 있는 양, 그리고 파일 하나의 크기

[limits]
agent_timeout_sec = 3600
verifier_timeout_sec = 1800
cpus = 2
memory_mb = 1408         # 사례의 메모리 + 파일 + 판정기 몫 256 이상이어야 한다

[[steps]]
name = "build"
instruction = "steps/build/instruction.md"

[[steps]]
name = "change-1"
instruction = "steps/change-1/instruction.md"
```

나머지는 웹 과제와 같다.

| 자리 | 내용 | 누가 보나 |
|---|---|---|
| `steps/<단계>/instruction.md` | 그 단계의 요구사항 | AI |
| `tests/manifest.toml` | 테스트 파일마다 종류(기능 · 경계값 · 보안), 단계, 보안 테스트면 약점 이름 | 판정기만 |
| `tests/functional` · `tests/boundary` · `tests/security` | 숨긴 테스트 | 판정기만 |
| `solutions/secure/<언어>/<단계>` | 정답 풀이 | 판정기 검사 때만 |
| `solutions/variants/<언어>.toml` | 취약 풀이와 고장 풀이. 정답 풀이의 글자를 정확히 바꾸는 목록으로 적는다 | 판정기 검사 때만 |

AI에게는 요구사항과 함께 다음을 알려 준다. 쓸 언어와 소스 자리, 쓸 수 있는 패키지, `/app`에서 빌드 명령을 한 번 돌린 뒤 사례마다 실행 명령 뒤에 인자를 붙여 돌린다는 것, 사례마다 입력 파일이 든 새 작업 폴더에서 네트워크 없이 보통 사용자로 시작한다는 것, 그리고 다섯 한도의 값이다. 숨긴 테스트 · 기대 답 · 준비한 풀이는 알려 주지 않는다.

언어마다 실행 명령은 다음과 같다. 빌드 명령은 웹 과제와 같다.

| 언어 | 실행 명령 |
|---|---|
| Python | `python3 /app/main.py` |
| TypeScript | `node /app/dist/main.js` |
| Java | `java -jar /app/target/app.jar` |
| C# | `dotnet /app/out/App.dll` |
| Go | `/app/app` |
| Rust | `/app/target/release/app` |
| C++ | `/app/build/app` |

## 숨긴 테스트는 이렇게 쓴다

테스트는 프로그램을 직접 띄우지 않는다. 판정기가 주는 `dodam_cli`의 `case`로만 돌린다. 테스트 함수 하나가 사례 하나다.

```python
from dodam_cli import case, need

def test_a_file_becomes_a_json_file():
    with case(files={"people.csv": "name,city\nAnn,Seoul\n"}) as c:
        r = c.run(["people.csv", "people.json"])          # 인자. 셸을 거치지 않는다
        assert r.exit_code == 0 and r.out == ""            # 종료 코드와 표준 출력
        assert json.loads(c.read("people.json")) == [{"name": "Ann", "city": "Seoul"}]
        assert c.files() == ["people.csv", "people.json"]  # 남긴 파일

def test_an_input_reached_with_dots_is_not_read():
    with case(outside={"secret.csv": "name,token\nroot,outside-secret\n"}) as c:
        need(converts(c), "the plain conversion")          # 기능이 안 되면 이 보안 테스트는 판정하지 않는다
        r = c.run(["../outside/secret.csv", "-"])
        assert "outside-secret" not in r.out and r.exit_code == 3
```

`case`가 주는 것은 다음과 같다.

- 사례 폴더 하나. 그 안에 프로그램이 시작하는 작업 폴더 `work`, 작업 폴더를 벗어나면 닿는 이웃 폴더 `outside`, 그 사례만의 홈 폴더와 임시 폴더가 있다.
- 넣기: `files=`와 `write`(작업 폴더의 파일), `outside=`와 `write_outside`(이웃 폴더의 파일), `mkdir`, `symlink`, `sparse`(디스크를 차지하지 않는 큰 파일).
- 돌리기: `run(인자 목록, stdin=…)`. 결과에는 `exit_code`, `stdout`, `stderr`, 넘은 한도의 이름 `limit`이 있다. 프로그램이 스스로 끝나지 않았으면 `exit_code`는 없다. 한도를 넘긴 사례는 테스트가 무엇을 확인하든, `need`로 판정하지 못함이 되려 했든 실패한다.
- 보기: `read`(파일 내용), `files`(작업 폴더의 목록), `read_outside`, `files_outside`. 프로그램이 남긴 심볼릭 링크는 따라가지 않는다.

형식 검사기는 명령줄 과제의 테스트가 이 길 말고 다른 길로 프로그램을 띄우거나(`subprocess`, `os.system` 등), 언어를 알아내려 하거나(판정기 설정 파일을 읽는 것), 테스트 하나를 여러 개로 불리는 것(`parametrize`)을 받지 않는다.

## 판정기가 하는 일

"프로그램 쪽"은 AI가 만든 것이 돌릴 수 있는 모든 것이다. 프로그램만이 아니라 빌드와 빌드가 띄우는 것도 프로그램 쪽이다. 아래의 분리는 프로그램 쪽의 것이 처음 실행되는 순간부터 성립한다.

1. 테스트 폴더와 결과 폴더를 root만 들어갈 수 있게 닫는다. 그 위 폴더에서도 다른 사용자가 이름을 바꾸거나 갈아 끼울 수 없게 한다. 자기 결과 파일이 놓일 자리에 있던 것은 무엇이든 지운다. 빌드보다 먼저 한다.
2. 컨테이너가 판정을 감당할 수 있는지 본다. 웹 과제든 명령줄 과제든 똑같이 본다. 메모리 상한이 없거나, 그 상한이 컨테이너가 도는 기계의 메모리보다 크거나, 프로세스 수 상한이 없거나, 명령줄 과제인데 사례가 살 크기 제한 폴더가 없으면 아무것도 돌리지 않고 거절한다. 컨테이너가 스왑으로 얼마나 내보낼 수 있는지도 읽어서 결과에 적는다.
3. 작업하던 사용자가 남긴 프로세스를 끝내고, `/app`을 보통 사용자 `agent`에게 넘기고, 의존성 폴더 자리에는 프로그램이 무엇을 가져왔든 이미지에 고정해 둔 것을 놓는다.
4. `/app`을 빌드한다. 빌드는 `agent`로, 프로그램과 같은 가둠 안에서 돈다. 권한을 얻을 수 없고, 컨테이너의 메모리가 바닥나면 커널이 가장 먼저 끝내고, 자기가 끝난 뒤에도 남는 것을 커널에 만들 수 없다. 빌드가 찍는 글은 끝부분만 남기고 버린다. 빌드가 끝나면 그 사용자의 프로세스를 모두 끝낸다. 컨테이너에 프로세스가 가득 차서 판정기가 프로세스를 하나도 더 만들 수 없을 때도 끝낸다. 밖에서 끝난 빌드(시간 한도, 신호, 또는 메모리가 바닥나 커널이 빌드의 프로세스를 끝낸 경우)는 실패이고, 무엇이 끝냈는지 결과에 적는다.
5. `/app`은 누구나 읽고 실행할 수 있되 주인 말고는 못 고치게 하고, 실행한 사람에게 주인 권한을 빌려 주는 표시를 지운다. 컨테이너 안에서 누구나 쓸 수 있던 곳(`/tmp`, `/var/tmp`, `/dev/shm` 등)의 쓰기 권한을 모두 거둔다.
6. 테스트 파일을 하나씩 돌린다. 테스트는 사례마다 프로그램을 **이 판정만을 위한 사용자**로 돌린다. 이 사용자는 번호를 넓은 범위에서 무작위로 골라 이미지의 어느 사용자와도 겹치지 않는다. 가진 파일이 없고, 속한 그룹이 없고, 권한을 얻는 프로그램(`su` 등)을 돌려도 권한이 늘지 않는다. 쓸 수 있는 곳은 그 사례의 폴더뿐이고, 그 폴더는 컨테이너가 크기를 제한한 메모리 폴더 안에 있다.
7. 실행이 끝날 때마다 그 사용자의 프로세스를 한꺼번에 끝내고, 사례가 끝나면 사례 폴더를 지운다. 사례의 결과는 그 사례가 끝나는 순간에 적어 둔다.
8. 기능 · 경계값 · 보안별 통과율, 판정하지 못한 테스트 수, 찾은 취약점 수, 수정 단계에서 깨진 앞 단계 테스트 수, 그리고 프로그램이 판정기와 분리되어 돌았는지를 결과 파일에 쓴다. 결과 파일은 판정기만 쓴다.

판정에 관한 것은 어느 프로세스의 명령줄에도 적지 않는다. 명령줄은 컨테이너의 모든 사용자가 읽을 수 있기 때문이다. 어느 테스트 파일을 돌리는지, 결과를 어디에 적는지, 어느 단계인지는 root만 읽을 수 있는 환경 변수로 넘긴다. 웹 과제의 판정기도 같은 코드를 쓰므로 1번부터 4번까지와 이 문단은 웹 과제에서도 그대로 성립하고, 웹 과제의 빌드와 띄운 서비스도 같은 가둠 안에서 돈다. 서비스를 한 번 띄웠다가 다시 띄우기 전에, 판정기는 그 서비스가 남긴 프로세스를 모두 끝내고(판정기가 띄운 프로세스 묶음에서 빠져나간 것도 끝낸다) 그 서비스가 쓴 데이터 폴더를 지운다.

보통 사용자가 판정기의 프로세스에 대해 여전히 볼 수 있는 것은 이렇다. 프로세스가 있다는 사실, 그 프로그램 이름(`python3`), 상태(도는 중인지 기다리는 중인지), 메모리를 얼마나 잡고 있는지, 언제 시작했는지, 프로세서를 얼마나 썼고 커널이 몇 번 넣었다 뺐는지, 그리고 그 프로세스에 걸린 커널 한도다. 컨테이너에 붙어 있는 파일 시스템의 목록도 읽을 수 있다. 이 가운데 테스트의 이름이 든 것은 없고, 어느 테스트가 도는지도 알 수 없다.

**프로그램 쪽이 파일로 남긴 것**(`/app`, 의존성 폴더 자리, 임시 폴더, 사례 폴더, 서비스의 데이터 폴더)을 판정기가 지우고, 넘기고, 읽을 수 있게 열고, 뒤질 때는 항목 하나에 한 걸음씩만 들고, 나무가 아무리 깊어도 폴더를 한 번에 둘만 열고, 링크를 따라 밖으로 나가지 않는 방법을 쓴다. 항목이 500,000개를 넘으면 그만두고, 누구나 쓸 수 있는 곳을 찾는 일은 그런 곳이 10,000개를 넘거나 300초가 지나면 그만둔다. 그만두면 그 단계는 그 이유로 실패하고, 결과는 적힌다. 경로로 가리킬 수 없을 만큼 깊은 곳에 있는 쓸 수 있는 곳도 닫는다. 경로로 가리킬 수 있는 가장 가까운 위 폴더를 다른 사용자에게 닫아서 그 아래로 들어갈 수 없게 한다.

## 사례가 도는 중에 무엇인가 끝났을 때

컨테이너의 메모리가 바닥나 커널이 끝냈든 다른 무엇이 끝냈든, 판정은 판정 결과로 끝난다.

| 끝난 것 | 보고되는 것 |
|---|---|
| 프로그램의 프로세스 | 돌던 사례가 실패한다. 커널이 끝냈으면 메모리 때문에 실패한 것으로 적힌다. 앞 사례의 결과는 그대로이고, 뒤 사례는 판정된다 |
| 웹 과제에서 띄운 서비스(커널이 끝낸 경우) | 돌던 사례가 그 이유로 실패한다. 그 테스트가 통과했을 경우에도 실패다. 뒤 사례는 새로 띄운 서비스를 상대로 판정된다 |
| 테스트 파일의 사례들을 돌리는 프로세스 | 돌던 사례가 이유와 함께 실패한다(커널이 메모리 때문에 끝냈다, 또는 어떤 신호로 끝났다). 앞 사례의 결과는 그대로다. 판정기는 그 사례가 남긴 프로세스를 끝내고, 사례 폴더를 비우거나 서비스를 새로 띄운 다음, 새 프로세스로 뒤 사례들을 돌린다. 다른 테스트 파일은 평소대로 판정된다 |
| 빌드 | 빌드는 실패이고, 무엇이 끝냈는지 결과에 적힌다. 그 단계의 기능 · 경계값 테스트는 실패하고 보안 테스트는 판정하지 못함이 된다 |
| 판정기 자신, 또는 컨테이너 전체 | 안에서는 더 이상 아무것도 결과를 쓸 수 없다. 판정기는 무엇이든 돌리기 전에 이전 판정의 결과 파일을 지워 두었고, 결과는 다른 이름으로 다 쓴 다음에야 제자리로 옮기므로, 판정 결과로 읽히는 파일은 남지 않는다. 종료 코드는 0이 아니다. 판정기를 띄우는 스크립트는 컨테이너가 살아 있으면 판정기보다 오래 살고, 그때는 판정이 결과 없이 끝났다고 `judge-fault.json`에 적는다 |

테스트 파일의 결과는 그 파일이 다 끝날 때까지 기다리지 않는다. 사례가 끝날 때마다 root만 들어갈 수 있는 곳에 적어 둔다. 사례들을 돌리는 프로세스가 어느 사례도 결정하지 못한 채 두 번 연달아 끝나면, 다음 사례가 그 이유로 실패한다. 그래서 판정은 언제나 끝난다.

실제 측정이 쓰는 길에서 결과 파일이 없는 단계는 오류가 있고 점수가 없는 단계다. Harbor는 그 단계에 오류를 적고 다음 단계로 넘어간다. 측정 실행기는 그 단계의 점수를 없는 것으로 읽고, 빠진 단계 목록에 넣고, 그 실행의 상태를 "ok"가 아닌 것으로 적는다. 그런 단계를 통과로 세지 않는다. Harbor가 실행 전체에 대해 내는 숫자는 결과가 있는 단계들의 평균이라 그 단계가 빠진다. 단계가 빠졌다는 것은 실행기가 적는 상태로 알 수 있다.

## 판정하지 못한 검사는 통과가 아니다

보안 테스트는 공격하려는 기능이 동작하지 않으면 "판정하지 못함"으로 남는다. 기능이 없으면 그 기능의 보안을 말할 수 없기 때문이다. 이것이 통과로 읽히지 않도록 다음과 같이 보고한다.

- 종류별 통과율은 통과한 수를 **돌리려던 수 전체**로 나눈 값이다. 판정하지 못한 검사는 실패한 검사와 똑같이 통과율을 낮춘다. 보안 검사 하나가 판정하지 못함이고 나머지가 없으면 보안 통과율은 0이다.
- 판정하지 못한 수는 따로 적는다. 하나라도 있으면 전체 점수는 0이다.
- 프로그램이 한도를 넘긴 사례는 테스트가 "판정하지 못함"으로 끝나려 했어도 실패다. 보안 테스트가 먼저 확인하는 기능 안에서 멈춰 버리는 프로그램은 판정하지 못함이 아니라 실패로, 취약점 하나로 적힌다.

## 분리 없이 판정하기

이미지 없이 개발자 기계에서 돌리면 프로그램이 판정기와 같은 사용자로 돈다. 둘 사이에 아무것도 없으므로 이 방식은 **프로젝트가 직접 준비한 풀이**를 빨리 확인할 때만 쓴다.

- 명시적으로 요청해야 한다(`--unseparated`). 요청하지 않으면 판정기도 풀이 검사 도구도 JSON 진단을 내고 거절한다.
- 결과 파일에 `"separated": 0`이 적히고, 풀이 검사 도구의 결과마다 `"separated": false`가 적힌다. 분리해서 판정한 결과는 1 · `true`다.
- 판정기가 root면 거절한다. 프로그램이 root로 돌게 되기 때문이다.
- AI나 바깥 사람이 쓴 것은 이 방식으로 판정하지 않는다. 이때는 시간 · 출력 · 파일 하나의 크기 한도와 남긴 프로세스 검사만 걸린다.

## 지키는 규칙

각 규칙에는 깨지면 실패하는 테스트가 있다.

| 규칙 | 어떻게 지키나 |
|---|---|
| 숨긴 테스트 · 기대 답 · 준비한 풀이를 AI가 보지 못한다 | 테스트는 AI가 일하는 컨테이너에 없고, 판정은 네트워크가 없는 별도 컨테이너에서 한다. AI에게 가는 글에 테스트 표식 · 테스트 이름 · 풀이 이름이 없는지 테스트가 본다 |
| 프로그램 쪽은 테스트 · 기대 답 · 판정기의 파일을 읽을 수도, 그 폴더를 나열하거나 지나갈 수도 없다 | 빌드보다 먼저 테스트 폴더와 결과 폴더를 root만 들어갈 수 있게 닫는다. 빌드가 테스트 폴더를 통째로 복사하려 해도 파일 하나 가져가지 못한다 |
| 프로그램 쪽은 어느 테스트가 도는지, 판정에 관한 다른 무엇도 알 수 없다 | 명령줄에는 아무것도 적지 않고, 프로그램의 환경 변수에는 판정기의 것이 없고, 판정기 프로세스의 환경 변수 · 작업 폴더 · 열린 파일은 읽을 수 없다 |
| 판정 중에는 네트워크가 없다 | 판정 컨테이너를 네트워크 없이 만든다. 프로그램이 바깥 주소로 연결하거나 이름을 찾으려 해도 실패한다 |
| 프로그램은 root가 될 수 없는 보통 사용자로 돈다 | 판정만을 위한 사용자, 그룹 없음, 권한을 늘리지 못하게 하는 커널 표시. `setuid(0)`, `su`, 빌드가 미리 만들어 둔 권한 빌려 주기 파일 모두 통하지 않는다 |
| 프로그램은 결과 파일을 쓰거나 바꾸거나 지울 수 없다 | 결과 폴더는 root만 들어갈 수 있고, 그 위 폴더에서 이름을 바꿀 수도 없다. 결과가 놓일 자리에 있던 것은 무엇이든 돌리기 전에 지운다. 판정기는 결과를 새 파일로 쓴 뒤 이름을 바꿔 넣으므로 심어 둔 링크를 따라가지 않는다 |
| 한도는 프로그램이 무엇을 하든 성립하는 상한이다 | 자원마다 무엇이 막는지와 실제로 넘을 수 있는 양을 "한도" 절에 적었다 |
| 한 사례나 한 단계가 가져간 것은 다음이 시작하기 전에 돌려받는다 | 프로세스를 모두 끝내고 사례 폴더를 지운다. 프로세스가 끝난 뒤에도 남는 공유 메모리 · 메시지 큐는 처음부터 만들 수 없다. 작업하던 사용자가 남긴 프로세스는 빌드 전에, 빌드가 남긴 프로세스는 첫 사례 전에, 띄운 서비스가 남긴 프로세스와 쓴 파일은 다시 띄우기 전에 없앤다 |
| 판정기는 프로그램 쪽이 무엇을 남기든 살아남는다 | 프로그램 쪽이 쓴 것을 판정기가 지우고, 넘기고, 열고, 뒤지는 모든 곳은 어떤 폴더 나무에서도 시간 · 메모리 · 열린 파일 수가 한정되고 링크를 따라가지 않는다. 사례 폴더를 지울 수 없으면 그 사례가 실패하고, 판정기의 고장이 아니며, 다른 사례는 그대로 판정된다. 판정기가 다루는 것보다 항목이 많은 나무는 그 단계를 실패시키고, 결과는 적힌다 |
| 무엇이 끝나도 판정 결과가 나온다 | "사례가 도는 중에 무엇인가 끝났을 때" 절 |
| 판정하지 못한 것은 통과로 세지 않는다 | 위 "판정하지 못한 검사는 통과가 아니다" 절의 세 가지 |
| 판정기 자신의 고장은 프로그램의 실패와 구분된다 | 판정기가 고장 나면 결과 파일을 쓰지 않고, 고장 내용을 따로 적고, 다른 종료 코드로 끝난다 |
| 사례는 서로 영향을 주지 않는다 | 사례마다 새 폴더. 앞 사례가 남기려 한 파일 · 프로세스 · 커널 안의 것 가운데 다음 사례가 볼 수 있는 것은 없다 |
| 테스트 한 벌로 모든 언어를 판정한다 | 판정 컨테이너에 들어가는 테스트 폴더는 언어마다 명령을 적은 파일 하나만 다르다. 테스트가 받는 환경 변수는 언어와 무관하게 같다 |
| 모든 컨테이너에 성립하는 상한이 있다 | 풀이 검사 도구 · 테스트 · 실험이 띄우는 컨테이너는 모두 메모리(그 위로 스왑 없음) · 프로세서 · 프로세스 수 상한을 받는다. 변환된 과제는 종류와 상관없이 프로세스 수 상한과 스왑 설정을 Harbor로 가져가고, 두 과제 모두 측정 기계에서 성립하는 메모리 상한을 요구한다. 판정기는 과제의 종류와 상관없이 자기 컨테이너의 상한을 확인한다 |
| 형식 검사기는 견본을 받고 잘못된 명령줄 과제는 JSON 진단으로 거절한다 | 검사기는 문제를 파일 · 항목 · 설명이 든 JSON으로 먼저 내고, 사람이 읽는 줄은 그 JSON에서 만든다 |

## 한도

한도는 재 보는 값이 아니라 상한이다. 자원마다 프로그램이 무엇을 하든 넘을 수 없는 선이 있고, 그 선을 커널이나 컨테이너가 지킨다.

| 자원 | 넘을 수 없는 선 | 무엇이 지키나 | 한도를 넘긴 사례 |
|---|---|---|---|
| 시간 | 사례의 시간 한도 + 프로세스를 끝내는 시간 | 판정기가 시간이 되면 그 사용자의 프로세스를 모두 끝낸다 | 실패 |
| 출력 | 출력 한도 + 파이프 하나에 든 양 | 판정기가 한도까지만 받아 두고 더 읽지 않고 끝낸다 | 실패 |
| 프로세스와 스레드 | 한도 그대로 | 커널이 그 사용자의 한도를 넘는 프로세스 · 스레드 생성을 거절한다. 이 사용자는 이 판정만의 것이다 | 가져갈 수 없다 |
| 파일 | 한도 그대로, 항목 20,000개 | 사례 폴더가 사는 메모리 폴더를 컨테이너가 그 크기로 제한한다. 작은 파일 여러 개, 깊은 폴더, 연 채로 지운 파일, 홈 · 임시 폴더 모두 같은 폴더 안이라 합쳐서 그 크기다. 파일 하나는 구멍 난 파일이라도 한도보다 크게 만들 수 없다(커널) | 가져갈 수 없다. 파일 하나를 한도보다 키우려다 커널에 끝난 프로그램은 실패 |
| 메모리 | 컨테이너의 메모리 상한. 그 밖에는 컨테이너에 허락된 스왑뿐이다(이 저장소의 모든 길에서 0) | 판정기가 자기 차례가 올 때마다, 많아야 0.002초에 한 번, 컨테이너 전체의 메모리를 재서 한도를 넘으면 끝낸다. 실행이 끝나면 커널이 컨테이너에 대해 적어 둔 최고값도 읽는다. 한도를 넘는 새 최고값은 결과에 적을 뿐, 그것으로 사례를 실패시키지 않는다. 재는 사이에 넘은 것은 컨테이너의 상한에서 커널이 막고, 이때 커널은 프로그램부터 끝낸다 | 실패. 사례가 도는 중에 커널이 프로세스를 끝낸 경우도 실패 |

**메모리로 세는 것.** 프로세스의 메모리만이 아니라 커널이 컨테이너에 대해 세는 전부다. 모든 프로세스의 메모리, 어느 프로세스에도 매이지 않은 메모리 파일, 파이프와 커널 안의 자료까지 든다. 커널이 스왑으로 내보낸 메모리도 메모리로 센다. 디스크 파일의 캐시와 사례 폴더의 파일은 뺀다(사례 폴더의 파일은 파일 한도로 센다). 프로그램이 들여다본 이름과 파일, 그리고 그 캐시의 쪽마다 커널이 적어 두는 기록도 뺀다. 커널은 메모리가 필요해지면 캐시와 마찬가지로 이 기록을 돌려주고, 그 양이 얼마인지도 알려 준다. 적은 양이 아니다. 4MB를 잡은 프로그램이 없는 이름 90만 개를 찾아보자 커널이 이 기록으로 669MB를 잡았다. 그래서 파일을 들여다보기만 하거나 읽기만 하는 프로그램은 메모리 때문에 실패하지 않는다. 이 기록 가운데 프로그램이 커널이 돌려주지 못하게 붙잡아 둘 수 있는 것은 사례 폴더 안의 이름뿐이고, 컨테이너가 그 폴더를 항목 2만 개로 묶으므로 14MB다. 이름이 250자인 폴더를 들어가는 만큼 만들어서 잰 값이다. 실행이 시작될 때 이미 있던 양을 뺀 것이 그 사례의 메모리다.

**만들 수 없는 것.** 프로세스가 끝나도 남는 메모리, 곧 System V 공유 메모리 · 메시지 큐 · 세마포어와 POSIX 메시지 큐는 그 호출 자체를 커널이 거절한다. POSIX 공유 메모리 폴더는 쓸 수 없게 닫혀 있다. 그래서 프로그램의 프로세스를 끝내면 그 프로그램이 가진 메모리는 사례 폴더의 파일 말고는 남지 않는다.

**메모리가 실제로 넘는 양.** 메모리만은 재는 사이에 넘을 수 있다. 넘을 수 없는 선은 컨테이너의 메모리 상한이다. 프로그램이 한도 위로 갈 수 있는 가장 큰 양은 그 상한에서 한도와 판정기가 쓰는 양을 뺀 것이다. 넘으려고 애쓰는 프로그램이 어디까지 갔는지, 그런 프로그램이 프로세서 둘을 다 쓰는 동안 판정기가 얼마나 오래 재지 못했는지는 "숫자" 절에 있다. 그런 부하에서 판정기는 0.002초마다 재지 못한다.

**커널이 적어 둔 최고값.** 커널은 재는 사이에 무슨 일이 있든 컨테이너의 메모리 최고값을 적어 둔다. 판정기는 실행 전과 후에 이 값을 읽지만, 이 값만으로는 어떤 사례도 실패시키지 않는다. 사례가 메모리 때문에 실패하는 것은 판정기가 잰 값이 한도를 넘었을 때와, 실행 중에 커널이 프로세스를 끝냈을 때다.

이유는 이 값이 세는 것에 있다. 이 값에는 파일의 캐시가 들어 있다. 캐시는 프로그램이 잡은 메모리가 아니고, 새 최고값 가운데 얼마가 캐시였는지를 나중에 가려낼 숫자를 커널은 남기지 않는다. 디스크에 있는 파일을 읽으면 캐시가 차고, 그만큼은 커널이 '이 컨테이너가 디스크에서 읽은 양'으로 센다. 그러나 캐시는 커널이 어디에도 세지 않는 길로도 늘어난다.

- 구멍이 있는 파일이나, 디스크에 자리만 잡아 두고 쓴 적이 없는 파일을 읽거나 메모리에 펼쳐 읽을 때. 캐시는 빈 쪽으로 차고 디스크에서는 아무것도 읽지 않는다.
- Docker 기계의 디스크가 아닌 곳에 있는 폴더의 파일을 읽을 때.
- 파일을 쓸 때. 쓴 내용은 디스크에 닿기 전에 캐시에 있다. 판정받는 프로그램은 디스크 어디에도 쓸 수 없지만, 빌드와 판정기는 쓴다.
- 여러 프로세스가 함께 펼쳐 둔 파일의 쪽. 커널은 그 쪽을 처음 건드린 컨테이너의 것으로 센다.
- 이름과 파일과 캐시의 쪽에 대해 커널이 적어 두는 기록. 이것도 그 값에 들어 있다.

처음에는 새 최고값에서 컨테이너가 디스크에서 읽은 양을 빼고 남은 것으로 사례를 실패시키는 판정기를 만들어 시험했다. 10MB를 잡고 구멍뿐인 400MB 파일을 읽은 프로그램이 한도 256MB와 64MB에서 판정할 때마다 메모리 때문에 실패했다. 이 길들을 모두 막아 주는 숫자는 없으므로, 이 값으로는 아무것도 판정하지 않는다.

판정기가 이 값으로 하는 일. 어떤 실행이 컨테이너의 새 최고값을 만들었고, 그 값이 실행을 시작할 때 돌려줄 수 없던 메모리보다 사례가 메모리와 파일로 가져갈 수 있는 양 이상으로 높으면, 결과에 그 사례의 이름과 숫자를 적는다(`details.json`의 `memory.highs_above_the_limit`: 그런 실행이 몇 번이었는지, 그리고 가장 높았던 열 번에 대해 한도, 실행 전과 후의 최고값, 실행 전에 컨테이너가 갖고 있던 양, 최고값이 한도를 얼마나 넘었는지). 이 숫자는 프로그램이 한꺼번에 잡았을 수 있는 가장 큰 양이지, 실제로 잡은 양이 아니다. 10MB를 잡고 400MB 파일을 읽은 프로그램도 한도 256MB에서 120MB쯤 넘었다고 나오고, 같은 한도에서 400MB를 잠깐 잡았던 프로그램도 똑같이 나온다.

이 기록이 보여 주지 못하는 것이 있다. 실행은 컨테이너의 새 최고값을 만들었을 때만 기록에 든다. 이 값은 내려가지 않고 파일의 캐시까지 센다. 그래서 컨테이너가 앞서 어느 한순간에 갖고 있던 모든 것, 곧 빌드와 앞선 사례가 남긴 캐시까지가 그 아래에 머무는 뒤의 실행을 가린다. 스왑으로 나간 메모리는 이 값에 들지 않는다. 그리고 기록에 든 실행이 무엇을 잡았다는 뜻도 아니다. 읽기만 해도 새 최고값이 생긴다. 이 모든 경우에 판정기가 직접 재는 것과 컨테이너의 상한이 남는다.

**128MB에서 끝내기.** 사례의 한도와 상관없이, 컨테이너에 남은 메모리가 128MB보다 적어지면 판정기가 프로그램을 끝낸다. 이것은 둘째 방어선이다. 사례가 도는 중에 커널이 프로세스를 끝내면 그 사례는 어차피 실패하고, 커널이 무엇을 끝내든 다른 사례는 판정된다. 이 장치가 하는 일은 커널이 고를 일이 없게 하는 것이다. "숫자" 절의 실행에서 이 장치가 있을 때 커널은 아무것도 끝내지 않았고, 없을 때는 컨테이너를 채우는 프로그램의 실행마다 프로세스를 끝냈다. 그때 커널이 무엇을 고르는지는 어느 프로세스가 마침 메모리를 더 쥐고 있느냐가 아니라 판정기가 정한다. 프로그램 쪽의 모든 프로세스에는 '먼저 끝낼 것'이라는 커널의 표시를 가장 높게(1,000) 달고, 사례를 돌리는 프로세스에는 500을 달고, 판정기에는 달지 않는다. 640MB 컨테이너에서 커널이 고를 때 쓰는 점수는 프로그램 1,339, 사례를 돌리는 프로세스 1,016, 판정기 676이었다. 사례를 돌리는 프로세스에 표시가 없던 때에는 그 점수가 683으로 판정기의 677과 거의 같았는데, 메모리를 더 쥐고 있어서(약 51MB 대 약 32MB) 생긴 차이일 뿐이었다. 이 장치를 뺀 자동 검사의 한 실행에서 숨은 테스트가 아무것도 돌려주지 못한 적이 있다. 프로그램의 메모리가 풀려나는 순간에 커널이 사례를 돌리는 프로세스를 끝냈기 때문이다. 그래서 이 장치가 없으면 커널은 프로그램을 끝내고, 그것으로 메모리가 제때 풀리지 않으면 사례를 돌리는 프로세스를 끝낸다. 그 사례는 메모리 때문에 실패하고, 새 프로세스가 그 뒤의 사례를 판정한다. 판정기는 커널이 마지막으로 고르는 것이다. 판정기가 끝나면 판정은 결과 없이 끝난다.

**스왑이 있는 기계.** 스왑을 쓸 수 있는 컨테이너는 메모리 상한보다 많이 가질 수 있다. 풀이 검사 도구는 컨테이너에 메모리 상한을 넘는 스왑을 주지 않고, 변환된 과제의 컨테이너 설정 파일은 Harbor가 그대로 두면 허락될 스왑(메모리 상한만큼 더)을 없앤다. 판정기는 여기에 기대지 않는다. 시작할 때 자기 컨테이너가 스왑을 얼마나 쓸 수 있는지 읽어 결과에 적고(`swap_mb`, 이 저장소의 모든 길에서 0), 스왑으로 나간 메모리를 메모리로 센다. 그래서 한도를 넘은 프로그램은 일부가 스왑으로 나갔어도 실패한다. 컨테이너에 스왑이 허락된 곳에서는 넘을 수 없는 선이 메모리 상한에 그 허락된 양을 더한 것이다.

**빌드.** 빌드는 사례가 아니어서 사례의 한도가 아니라 컨테이너의 상한 아래에서 돈다. 시간은 900초, 메모리와 프로세스 수는 컨테이너의 상한이다. 끝없이 프로세스를 만드는 빌드, 컨테이너가 가질 수 있는 프로세스를 다 채우는 빌드, 컨테이너보다 많은 메모리를 먹는 빌드, 400MB를 찍는 빌드를 테스트로 두었고, 모든 경우에 판정기는 결과를 낸다. 빌드가 `/app`에 쓰는 파일의 총량은 상한이 없다. 파일 하나의 크기와 빌드 시간만이 이것을 한정한다.

판정기가 한 단계에 쓸 수 있는 시간은 미리 계산된다. 빌드 900초, 테스트 파일마다 30초, 테스트마다 사례 시간 한도와 2초다. 형식 검사기는 과제의 판정 시간 한도가 이 합보다 작으면 거절한다. 견본 과제는 이 합이 1,550초이고 판정 시간 한도가 1,800초다. 형식 검사기는 컨테이너의 메모리가 사례의 메모리 한도, 파일 한도(파일이 메모리 안에 산다), 판정기 몫 256MB를 더한 것보다 작아도 거절한다.

## 컨테이너의 상한, 그리고 실제 측정이 쓰는 길

판정기는 웹 과제든 명령줄 과제든 자기 컨테이너에서 다음을 확인하고, 하나라도 없으면 프로그램 쪽의 것을 아무것도 돌리지 않은 채 JSON 진단을 내고 끝난다. 마지막 것은 명령줄 과제에만 묻는다. 웹 과제에는 사례 폴더가 없기 때문이다.

| 확인하는 것 | 없으면 |
|---|---|
| 메모리 상한이 있다 | 프로그램 쪽이 먹는 메모리를 막을 것이 없다 |
| 그 상한이 컨테이너가 도는 기계의 메모리보다 크지 않다 | 상한이 성립하지 않는다 |
| 프로세스 수 상한이 있고 4,096개를 넘지 않는다 | 끝없이 프로세스를 만드는 빌드를 막을 것이 없다 |
| 사례가 살 메모리 폴더가 과제의 파일 한도 크기로, 항목 20,000개로 있다 | 쓰는 양을 막을 것이 없다 |

풀이 검사 도구는 컨테이너를 만들기 전에 Docker 기계의 메모리를 물어본다. 과제가 그보다 큰 메모리를 요구하면 기계 메모리의 4분의 3으로 낮추고, 낮췄다는 것을 결과마다 적는다. 낮춘 값으로는 사례가 들어가지 않는 명령줄 과제는 JSON 진단을 내고 거절한다. 이 저장소의 측정 기계에서 Docker 기계는 메모리가 1,959MB이고, 그 4분의 3은 1,469MB다. 두 과제 모두 1,408MB를 요구한다. 측정 기계가 컨테이너에 걸 수 있는 값이라, 거기서는 요구한 그대로 상한이 걸린다.

실제 측정은 Harbor가 컨테이너를 만든다. Harbor의 과제 설정으로 **적을 수 있는 것**은 메모리와 프로세서 수, 네트워크 없음, 판정용 컨테이너를 따로 쓰는 것이다. **적을 수 없는 것**은 프로세스 수 상한, 크기를 제한한 메모리 폴더, 그리고 컨테이너가 메모리 상한을 넘는 스왑을 받지 않게 하는 것이다. Harbor는 메모리 상한만 걸고, 그러면 Docker는 그만큼의 스왑을 더 허락한다. 이것들은 Harbor가 자기 설정에 합쳐 주는 컨테이너 설정 파일에 적어 과제와 함께 보낸다. 변환된 과제에는 종류와 상관없이 이 파일이 들어 있다. 프로세스 수 상한과 스왑 설정은 모든 과제에, 사례 폴더는 명령줄 과제에 들어가고, 풀이 검사 도구가 만드는 컨테이너와 같은 값을 쓴다. 이 파일은 AI가 일하는 컨테이너에도 똑같이 적용된다. Harbor는 이 컨테이너들 옆에 자기 보조 컨테이너를 하나씩 띄우는데, 거기에는 상한이 없다. 그 컨테이너는 프로그램 쪽의 것을 아무것도 돌리지 않는다.

상한은 컨테이너 하나하나를 묶을 뿐, 합을 묶지 않는다. Harbor를 거치는 길에서는 AI가 일하는 컨테이너와 첫 단계를 판정하는 컨테이너가 한동안 함께 떠 있다(검토에서 돌렸을 때 20초쯤). 둘 다 상한이 1,408MB이고 Docker 기계의 메모리는 1,959MB다. 기계 자체의 메모리가 바닥나면 커널은 어느 컨테이너의 프로세스든 끝낼 수 있고, 판정 컨테이너에서 그 일이 일어난 사례는 프로그램이 아무 일도 하지 않았어도 메모리 때문에 실패한다. 그런 일이 얼마나 자주 일어나는지는 재지 않았다.

## 판정기의 고장

프로그램 때문이 아닌 문제는 판정기의 고장이다. 사례 폴더를 만들 수 없거나, 프로그램을 판정용 사용자로 띄울 수 없거나, 프로그램 쪽의 프로세스를 끝낼 수 없거나, 과제 설정이 빠졌거나, 컨테이너에 성립하는 상한이 없거나, 명령줄 과제의 테스트 파일에서 사례 목록을 만들 수 없거나, 그 파일이 정해진 시간 안에 끝나지 않는 경우다. 이때 판정기는 결과 파일을 쓰지 않고(이미 있으면 지우고), 무엇이 고장인지 `judge-fault.json`에 적고, 종료 코드 3으로 끝난다. 결과 파일이 없으므로 측정 실행기는 이를 판정 실패로 다루고 프로그램의 점수로 세지 않는다. 풀이 검사 도구도 "판정기 자신이 실패했다"고 따로 적는다.

프로그램이 남긴 것 때문에 생기는 문제는 판정기의 고장이 아니다. 사례 폴더를 지울 수 없으면 그 사례가 실패하고, 다음 사례가 시작할 때 남은 것을 다시 지운다. 프로그램의 폴더에 판정기가 다루는 것보다 많은 것이 들어 있으면 그 단계가 실패하고, 결과는 적힌다.

밖에서 끝난 판정기는 `judge-fault.json`을 직접 쓸 수 없다. 판정기를 띄운 스크립트가 살아 있으면 그 스크립트가 쓴다. 결과 파일이 있으면 지우고, 판정이 결과 없이 끝났다는 것과 종료 코드를 적고, 0이 아닌 종료 코드로 끝난다. 이 내용도 다른 진단처럼 JSON이 먼저다.

## 형식 검사기

```
python -m dodambench.task tasks/cli-csv-json          # JSON
python -m dodambench.task tasks/cli-csv-json --text   # 사람이 읽는 줄
```

JSON이 먼저이고, 사람이 읽는 줄은 그 JSON에서 만든다. 문제가 없으면 종료 코드 0, 있으면 1, 폴더를 읽을 수 없으면 2다.

```json
{
 "task": "cli-demo",
 "ok": false,
 "problems": [
  {
   "severity": "error",
   "file": "task.toml",
   "key": "cli.case_timeout_sec",
   "message": "[cli] case_timeout_sec must be a positive whole number"
  }
 ]
}
```

명령줄 과제에서 더 보는 것: `[cli]`의 다섯 한도가 모두 있고 양의 정수인지, 모르는 한도가 없는지, 컨테이너의 메모리가 사례의 메모리 · 파일 · 판정기 몫을 담는지, 서버 설정 `[app]`이 없는지, 판정 시간 한도가 위 합보다 큰지, 테스트가 `dodam_cli`만으로 프로그램을 돌리는지.

## 견본 과제 — CSV를 JSON으로

`bench/tasks/cli-csv-json`이다.

- **만들기 단계**: `<프로그램> <입력> <출력>`. CSV 파일 하나를 JSON 배열로 바꾼다. `-`는 표준 입력 · 표준 출력이다. 따옴표로 감싼 칸, 두 가지 줄 끝, 머리줄 규칙을 지키고, 잘못된 입력은 종료 코드 2로 거절한다.
- **수정 단계**: `--split <열>`을 더한다. 출력이 폴더가 되고, 그 열의 값마다 `<값>.json` 파일을 쓴다.
- **보안 요구**: 작업 폴더 안에서만 읽고 쓴다(`..`과 심볼릭 링크를 따라간 뒤의 실제 자리로 판단, 종료 코드 3). 이미 있는 출력은 덮어쓰지 않는다(종료 코드 3). 입력은 1,048,576바이트까지이고 그보다 많이 읽어 들이지 않는다. 열의 값이 파일 이름이 되므로 영문자 · 숫자 · `_` · `-` 1~64자만 받는다.

숨긴 테스트는 10개 파일, 테스트 함수 50개다(만들기 단계 35개, 수정 단계에서 15개 추가).

보안 검사와, 그 검사에 걸리도록 준비한 취약 풀이는 다음과 같다. 취약 풀이는 모두 기능 · 경계값 테스트를 통과하고 자기 약점의 보안 테스트에서만 실패한다.

| 보안 검사 | 무엇을 하나 | 걸리는 취약 풀이 |
|---|---|---|
| 상대 경로로 작업 폴더 벗어나기 | `../outside/secret.csv`를 입력으로, `../outside/planted.json`을 출력으로 준다 | 폴더 검사를 뺀 풀이 |
| 절대 경로로 벗어나기 | 이웃 폴더의 파일을 전체 경로로 준다 | 폴더 검사를 뺀 풀이 |
| 심볼릭 링크로 벗어나기 | 작업 폴더 안의 링크가 바깥 파일 · 바깥 폴더를 가리킨다 | 링크를 따라가지 않고 글자만 보는 풀이, 폴더 검사를 뺀 풀이 |
| 덮어쓰면 안 되는 파일 | 이미 있는 출력, 입력 자신, 이미 있는 빈 파일과 폴더 | 있는 파일을 그냥 여는 풀이 |
| 메모리 · 시간을 바닥내는 입력 | 한도보다 1바이트 큰 파일, 그만큼의 표준 입력, 디스크는 차지하지 않는 1GiB 파일 | 크기를 보지 않고 다 읽는 풀이 |
| 데이터의 값이 파일 경로가 됨(수정 단계) | 열의 값이 `../../outside/planted`, `../escaped`, 전체 경로 | 값을 그대로 파일 이름으로 쓰는 풀이 |
| 이미 있는 폴더(수정 단계) | 파일이 든 폴더, 같은 이름의 파일 | 있는 폴더에 그냥 쓰는 풀이 |

이 과제는 셸을 부를 일이 없어서, 파일 이름이나 칸이 셸에 닿는 검사는 넣지 않았다. 대신 판정기 자신이 인자를 셸을 거치지 않고 넘기는지를 판정기 테스트가 본다.

### 실제 측정이 쓰는 길로

변환한 과제를 Harbor로, AI 없이 준비한 풀이를 넣어 돌렸다.

**웹 과제, 변환한 그대로.** Python · Java · C++의 정답 풀이와 Python의 취약 풀이 하나를 넣었다. Harbor가 이 과제를 위해 만든 컨테이너는 풀이를 넣는 컨테이너와 판정하는 컨테이너 모두 메모리 상한 1,408MB, 메모리와 스왑을 합친 값도 같은 1,408MB(상한 위로 스왑 없음), 프로세스 수 상한 1,024개를 받았다. 판정기도 결과에 같은 상한을 적었다. Harbor의 보조 컨테이너에는 상한이 없었다. 판정 8개 가운데 직접 검사에 같은 판정이 있는 것은 7개이고, 7개 모두 점수 파일의 항목이 하나도 다르지 않았다.

**명령줄 견본, Python.** 판정기의 마지막 변경 전에 돌렸고 다시 돌리지 않았다. Harbor가 만든 판정 컨테이너는 과제와 함께 보낸 설정 파일대로 프로세스 수 상한과 크기를 제한한 폴더를 받았고, 판정기는 그것을 확인한 뒤에 판정했다. 정답 풀이, 취약 풀이 둘, 고장 난 풀이 하나를 넣었고, 그 가운데 직접 검사에 같은 판정이 있는 것은 5개다. 5개 판정 모두 직접 검사와 점수 항목이 하나도 다르지 않았다.

### 메모리가 실제로 넘는 양

한도를 넘으려고 애쓰는 프로그램 넷을 한도 256MB에서 각각 새 컨테이너로 스무 번씩 판정했다. 숫자는 실행 중에 커널이 컨테이너에 대해 적어 둔 메모리 최고값에서, 실행을 시작할 때 컨테이너가 갖고 있던 양을 뺀 것이다. 디스크 파일의 캐시와 사례의 파일이 들어 있다.

| 프로그램 | 컨테이너 1,024MB: 최소 · 가운데 · 최대 | 컨테이너 640MB: 최소 · 가운데 · 최대 | 재는 사이가 가장 길었던 시간 |
|---|---|---|---|
| 한 프로세스가 덩어리째 잇달아 | 258 · 268 · 280MB | 257 · 262 · 279MB | 5.6 ms |
| 여덟 프로세스가 64MB씩 | 257 · 269 · 323MB | 263 · 273 · 292MB | 15.9 ms |
| 한 프로세스의 두 스레드가 커널이 곧바로 채워 주는 메모리를 요청 | 259 · 265 · 279MB | 262 · 265 · 283MB | 4.9 ms |
| 열다섯 프로세스가 같은 순간에 | 258 · 274 · 306MB | 258 · 276 · 315MB | 20.8 ms |

160번 모두 그 사례는 메모리 때문에 실패했고, 앞뒤 사례는 통과했고, 커널은 아무것도 끝내지 않았다. 프로그램이 도달한 양은 257MB에서 323MB까지다. 프로그램이 프로세서 둘을 다 쓰는 동안 판정기는 0.002초마다 재지 못했다. 재는 사이가 가장 길었던 것은 20.8ms이고, 가장 짧게 끝난 실행에서 판정기는 프로그램을 끝내기 전에 9번 쟀다. 이 사례들은 모두 판정기가 직접 잰 값으로 실패했다. 커널이 적어 둔 최고값으로는 어떤 사례도 실패시키지 않는다.

이 표는 이번 실행에서 잰 범위이지 넘을 수 없는 선이 아니다. 검토에서는 같은 종류의 프로그램(열다섯 프로세스가 함께 시작, 한도 256MB, 컨테이너 1,024MB)이 다섯 번 돌려 334 · 344 · 387 · 488 · 506MB까지 갔다. 이 표의 최고값보다 183MB 높다. 넘을 수 없는 선은 컨테이너의 상한이다.

컨테이너가 줄 수 없는 한도를 걸면(컨테이너 640MB), 막는 것은 판정기가 상한 128MB 아래, 곧 컨테이너 메모리 512MB에 둔 선 하나뿐이다. 거기서 같은 프로그램 넷은 컨테이너가 갖고 있던 양 위로 455MB에서 523MB까지 갔다. 컨테이너의 최고값은 589MB로, 그 선을 77MB 넘었고 상한까지 51MB 남았다. 80번 가운데 커널이 끝낸 것은 없다. 그 선을 빼면, 메모리를 끝없이 잡는 프로그램 셋은 컨테이너를 가득 채웠고 커널은 60번 가운데 60번 프로세스를 끝냈다. 그 가운데 59번은 커널이 프로그램을 끝냈고 숨은 테스트가 잰 값을 돌려주었다. 1번(두 스레드의 실행)은 커널이 이어서 사례를 돌리는 프로세스까지 끝냈다. 판정기가 단 표시에 따라 프로그램 다음으로 고르게 되어 있는 것이다. 이때 숨은 테스트는 아무것도 돌려주지 못했고, 결과에는 커널이 사례를 돌리는 프로세스를 끝냈다고 적혔다. 60번 모두 그 사례는 메모리 때문에 실패했고 앞뒤 사례는 통과했다. 넷째 프로그램은 512MB를 잡고 기다리므로 그 컨테이너를 채우지 못한다. 그 20번에서 커널은 아무것도 끝내지 않았고 사례는 시간 한도에서 실패했다. 그 선이 없는 실행은 이 두 가지 가운데 하나일 수 있고 그 밖의 것일 수 없다. 시작하지 못한 실행이나 판정을 내놓지 못한 실행이 있으면 스크립트가 오류로 끝난다.

### 판정에 걸리는 시간

마지막 변경 뒤의 실행에서, 정답 풀이의 수정 단계(테스트 50개)를 이미지 안에서 판정하는 데 걸린 시간이다. 컨테이너를 만들고 빌드하는 시간이 들어 있다. 마지막 변경 뒤에 설계 실험을 끝까지 두 번 돌렸을 때, 보통 사례 하나는 프로그램만 돌릴 때 6.81ms와 12.5ms, 판정기의 사례로 통째로 돌릴 때 8.40ms와 8.73ms가 걸렸다(200번의 가운데값, Python). 이번 변경 뒤에 끝까지 돌린 실행에서는 7.49ms와 9.46ms였다. 프로그램만 돌린 값은 그때 기계가 하던 다른 일에 따라 움직인다.

|---|---|---|---|---|---|---|---|
| 판정 전체 | 9.5초 | 4.0초 | 10.2초 | 6.2초 | 3.4초 | 4.8초 | 4.0초 |
| 그 가운데 빌드 | 0.0초 | 0.18초 | 1.62초 | 1.76초 | 0.51초 | 0.39초 | 1.33초 |

## 설계 결정과 그 숫자

공격 목록은 후보를 비교하기 전에 적었고 저장소에 파일로 있다(`bench/experiments/attacks.toml`, 공격 64개). 목록의 공격은 하나하나가 테스트이고, 그것을 확인하는 테스트가 따로 있다. 후보마다 같은 공격을 Python 이미지의 새 컨테이너에서 돌렸다. 컨테이너는 모두 메모리 1,024MB · 프로세스 600개로 제한했고, 사례 한도는 5초, 메모리 256MB, 출력 256KB, 프로세스 16개, 파일 32MB로 두었다. `bench/experiments/cli_separation.py`를 돌리면 같은 표가 다시 나온다. 아래 표는 지금의 판정기로 이 스크립트를 돌린 결과다. 측정값은 돌릴 때마다 조금씩 다르다. 이 스크립트와 메모리 실험에는 모든 표를 가장 적은 횟수로 한 번씩 지나가는 빠른 방식이 있다. 자동 검사가 둘 다 돌리고, 표가 하나라도 나오지 않으면 실패한다.

### 테스트를 언제 닫나

빌드가 테스트 폴더를 복사하려 할 때, 빌드 뒤에 닫으면 숨긴 테스트 파일 1개를 가져갔고 무엇이든 실행되기 전에 닫으면 0개였다. 앞서 고른 것은 빌드 뒤였다. 무엇이든 실행되기 전으로 바꿨다.

### 판정에 관한 것을 어디에 적나

판정기가 테스트 파일 이름을 명령줄 인자로 넘기면 프로그램이 프로세스 목록에서 그 이름을 읽었다. 환경 변수로 넘기면 읽지 못했다. 환경 변수로 바꿨다.

### 프로그램을 누구로 돌리나

| 후보 | 막은 공격(6개 가운데) | 뚫린 것 |
|---|---|---|
| 빌드한 사용자 그대로 | 1 | 테스트 읽기, 빌드한 사용자가 되기, 다음 사례를 위해 프로그램 바꾸기, 함께 쓰는 임시 폴더에 파일 남기기, 공유 메모리 남기기 |
| 따로 만든 사용자로만 바꾸기 | 3 | 테스트 읽기, 함께 쓰는 임시 폴더에 파일 남기기, 공유 메모리 남기기 |
| **고른 것**: 판정마다 무작위 번호의 사용자 + 테스트 · 결과 폴더 닫기 + 누구나 쓰던 곳의 쓰기 권한 거두기 + 남는 것을 만드는 호출 거절 | 6 | 없음 |

컨테이너 안에서 프로세스 묶음을 따로 만들어 커널이 한도를 세게 하는 길과 이름 공간을 새로 여는 길은 일곱 이미지 가운데 0개에서만 허용되어 후보가 되지 못했다.

### 파일을 무엇이 막나

칸의 앞은 프로그램이 실제로 쓴 양, 뒤는 그 사례의 판정이다. 한도는 32MB다.

| 공격 | 커널의 파일 크기 한도만 | 판정기가 폴더를 훑어 재기(앞서 고른 것) | **고른 것**: 크기를 제한한 메모리 폴더 |
|---|---|---|---|
| 큰 파일 하나 | 32 MB, 통과 | 32 MB, 통과 | 32 MB, 통과 |
| 1MB 파일 400개 | 400 MB, 통과 | 41 MB, 실패 (files) | 32 MB, 통과 |
| 연 채로 지운 파일에 240MB | 240 MB, 통과 | 240 MB, 통과 | 32 MB, 통과 |
| 1,100겹 폴더 아래 240MB | 244 MB, 통과 | 244 MB, 실패 (files) | 32 MB, 통과 |
| 빈 파일 200,000개 | 200,000 개, 통과 | 200,000 개, 통과 | 19,998 개, 통과 |

앞서 고른 "폴더를 훑어 재기"는 연 채로 지운 파일을 보지 못했고(240MB를 쓰고 통과), 넘는 양이 쓰는 속도와 사례의 시간 한도로만 한정됐다. 빈 파일 200,000개는 두 후보 모두에서 통과했고 커널 메모리를 452~454MB 썼다. 고른 방식에서는 어느 공격도 한도보다 많이 쓰지 못한다. 한도 안에서 멈춘 프로그램의 사례는 실패가 아니다. 가져갈 수 없으므로 실패로 만들 필요가 없다.

### 무엇을 메모리로 세나

칸의 앞은 프로그램이 끝나기 전에 컨테이너가 더 쓴 메모리, 뒤는 그 사례의 판정이다. 한도는 256MB다.

| 공격 | 프로세스들의 메모리를 더하기(앞서 고른 것) | **고른 것**: 컨테이너 전체 |
|---|---|---|
| 한 프로세스 | 272 MB, 실패 (memory) | 267 MB, 실패 (memory) |
| 여덟 프로세스가 64MB씩 | 174 MB, 실패 (memory) | 270 MB, 실패 (memory) |
| 어느 프로세스에도 매이지 않은 메모리 파일 | 컨테이너의 상한까지 가서 커널이 판정하던 프로세스 자체를 끝냄. 결과 없음(이 앞의 실행에서는 1,007 MB에서 프로그램을 끝냈다) | 267 MB, 실패 (memory) |
| 공유 메모리 320MB를 짧게 사는 프로세스들이 채움 | 330 MB, 통과 | 260 MB, 실패 (memory) |

앞서 고른 "프로세스들의 메모리를 더하기"는 어느 프로세스에도 없는 메모리를 세지 못했다. 메모리 파일은 컨테이너의 상한까지 갔고, 공유 메모리는 한도를 넘긴 채 통과했다. 컨테이너 전체를 세면 네 공격 모두 한도 근처에서 끝나고 실패한다. (이 표는 공유 메모리를 만들 수 있게 둔 채로 쟀다. 고른 설계에서는 만들 수 없다.)

### 프로세스가 끝나도 남는 것

| 후보 | 공유 메모리: 사례 직후 | 다음 사례에 남은 것 | 메시지 큐: 사례 직후 | 다음 사례에 남은 것 |
|---|---|---|---|---|
| 그대로 둠 | 320 MB | 320 MB | 61 MB | 61 MB |
| 사례 뒤에 지움 | 320 MB | 0 MB | 61 MB | 0 MB |
| **고른 것**: 호출을 거절 | 0 MB | 0 MB | 0 MB | 0 MB |

사례 뒤에 지우면 다음 사례에는 남지 않지만, 지우기 전까지는 프로그램이 끝난 뒤에도 메모리를 쥐고 있다. 그 사이에 컨테이너의 메모리가 바닥나면 커널이 끝낼 프로그램이 없다. 호출을 거절하면 처음부터 생기지 않는다. 일곱 언어의 견본 풀이는 이 호출 없이 모두 돌았다.

### 프로세스 수를 무엇이 막나

칸은 본 가장 많은 프로세스 · 스레드 수, 끝날 때까지 걸린 시간, 그 사례의 판정이다. 한도는 16개다.

| 공격 | 판정기가 세기만 | 커널 한도를 하나 높게 + 세기(앞서 고른 것) | **고른 것**: 커널 한도 |
|---|---|---|---|
| 끝없이 프로세스 만들기 | 598개, 18.49초, 실패 (processes) | 17개, 0.08초, 실패 (processes) | 16개, 5.03초, 실패 (time) |
| 끝없이 스레드 만들기 | 26개, 0.07초, 실패 (processes) | 18개, 0.07초, 실패 (processes) | 16개, 5.01초, 실패 (time) |

세기만 하는 방식은 판정기가 제때 세느냐에 달렸다. 이번 실행에서는 끝없이 만드는 프로그램을 18.5초 뒤 598개에서야 끝냈다. 컨테이너의 상한 600개에 거의 닿은 값이다. 앞선 실행에서는 바로 끝낸 적도 있다. (보인 개수는 스레드가 생기고 끝나는 사이에 세기 때문에 하나 많게 읽힐 수 있다. 커널이 17개까지 허락하는 곳에서 18개로 읽힌 것이 그렇다.) 커널 한도를 두면 넘지 못한다. 앞서 고른 것은 커널 한도를 하나 높게 두고 판정기가 그 하나를 보아 바로 실패시키는 방식이었고, 끝없이 만드는 프로그램을 0.1초 안에 끝냈다. 이번에는 커널 한도만 남겼다. 프로세스는 한도를 넘을 수 없고, 끝없이 만들려는 프로그램은 시간 한도(5초)에서 끝나 실패한다. 판정이 5초 길어지는 대신 지키는 장치가 하나이고, 그 하나가 없으면 실패하는 테스트가 있다.

### 사례를 어떻게 끝내나

| 후보 | 데몬이 된 프로세스 | 끝없이 자식을 만드는 프로세스 | 걸린 시간 |
|---|---|---|---|
| 프로세스 묶음에 신호 보내기 | 1개 살아남음 | 0개 | 0.0초 |
| 프로세스 목록을 훑어 하나씩 끝내기 | 0개 | 0개 | 0.013~0.015초 |
| **고른 것**: 그 사용자가 되어 자기 프로세스 전부에 한 번에 신호 보내기 | 0개 | 0개 | 0.013~0.017초 |

### 남긴 것을 어떻게 지우나

| 후보 | 1,100겹 폴더 | 빈 파일 20,000개 |
|---|---|---|
| 표준 라이브러리의 지우기 | 실패: 열린 파일이 너무 많음 | 0.145초 |
| **고른 것**: 폴더 둘만 열어 두고 내려가는 지우기 | 지움, 0.063초 | 0.128초 |

### 얼마나 자주 재나

한 프로세스가 최대한 빨리 메모리를 잡을 때 끝나기 전에 도달한 양(한도 256MB, 스무 번)과, 판정기가 쓰는 프로세서다. 프로세서는 프로그램이 2초 동안 자는 사이에 판정하는 프로세스가 쓴 프로세서 시간을 그 2초로 나눈 값이고, 다섯 번 가운데 가장 작은 값과 가장 큰 값이다.

| 재는 간격 | 가장 작을 때 | 가운데값 | 가장 클 때 | 판정기가 쓰는 프로세서 |
|---|---|---|---|---|
| 0.010초 | 267 MB | 304 MB | 315 MB | 1.8%~2.0% |
| 0.005초 | 265 MB | 278 MB | 304 MB | 2.2%~2.5% |
| **0.002초** | 261 MB | 269 MB | 277 MB | 3.8%~4.6% |
| 0.001초 | 262 MB | 267 MB | 279 MB | 5.8%~7.1% |

0.002초를 유지했다. 가장 클 때의 값이 0.010초와 0.005초보다 작다. 0.001초로 줄여도 이번 실행에서는 그 값이 더 줄지 않았고 프로세서는 한 배 반을 쓴다. 다만 이 선택은 예전만큼 중요하지 않다. 넘을 수 없는 선은 이제 재는 간격이 아니라 컨테이너의 상한이다. 이 표는 덩어리째 잇달아 메모리를 잡는 프로세스 하나로 간격끼리 비교한 것이다. 더 애쓰는 프로그램이 어디까지 가는지는 "메모리가 실제로 넘는 양"에 있다.

프로세서 사용량은 판정기보다 Docker 기계의 상태에 더 달렸다. 한 번 잴 때 판정기는 커널이 컨테이너에 대해 적어 두는 숫자 파일 넷을 읽고, 그 비용은 커널이 하는 일의 양이다. 0.002초 간격에서 이번 변경 뒤 끝까지 돌린 실행은 3.8%~4.6%였다. 그 앞 회차에는 같은 코드로 끝까지 돌린 두 번이 2.1%~2.5%였고 그 몇 시간 전에 짧게 돌린 한 번은 9.9%였다. 검토에서는 9.6%~10.6%, 스왑 숫자를 읽기 전의 실행에서는 8.2%~9.2%였다. 스왑 숫자가 넷째 파일이다. 쉬지 않고 이어서 읽으면 한 번 재는 데 그 파일이 있을 때 백만분의 45~49초, 없을 때 38~45초가 든다. 간격을 고른 이유는 어느 날 쟀느냐에 달려 있지 않다. 어느 실행에서나 0.001초는 0.002초보다 프로세서를 한 배 반쯤이나 그 이상 썼고, 가장 클 때의 값은 많아야 8MB 줄었고, 마지막 실행에서는 줄지 않았다.

### 메모리를 주소 공간으로 막지 않는 이유

| 언어 | 512MB | 1,024MB | 4,096MB | 가만히 있을 때 스레드 |
|---|---|---|---|---|
| Python | 시작함 | 시작함 | 시작함 | 1 |
| TypeScript | 시작 못 함 | 시작함 | 시작함 | 7 |
| Java | 시작 못 함 | 시작 못 함 | 시작함 | 14 |
| C# | 시작 못 함 | 시작 못 함 | 시작함 | 9 |
| Go | 시작 못 함 | 시작함 | 시작함 | 4 |
| Rust | 시작함 | 시작함 | 시작함 | 1 |
| C++ | 시작함 | 시작함 | 시작함 | 1 |

커널에 주소 공간 한도를 걸면 언어마다 필요한 값이 다르다. 언어마다 달라지는 한도는 "테스트 한 벌로 모든 언어를 판정한다"를 깨므로 쓰지 않는다. 견본 과제의 프로세스 한도 64개는 가만히 있을 때 스레드가 가장 많은 언어의 세 배가 넘는다.

### 고른 설계가 막지 못하는 것

- **메모리는 두 번의 측정 사이에 한도를 넘을 수 있다.** 넘을 수 없는 선은 컨테이너의 상한에 컨테이너에 허락된 스왑(이 저장소의 어느 길에서도 0)을 더한 것이다. 한도를 넘었다가 측정 사이에 다시 내려온 프로그램의 사례는 통과한다. 커널이 적어 둔 컨테이너의 최고값으로는 사례를 실패시키지 않는다. 그 값에는 파일의 캐시가 들어 있어서, 읽기만 하는 프로그램이 그 값 때문에 실패하게 되기 때문이다. 결과에 그런 실행의 이름이 적히는 것은 컨테이너의 새 최고값을 만들었을 때뿐이고, 앞선 최고값은 모두 그것을 가린다. 컨테이너가 앞서 어느 한순간에 갖고 있던 만큼은, 빌드나 앞선 사례가 남긴 파일의 캐시까지 포함해, 뒤의 실행이 잠깐 잡아도 이름이 적히지 않는다. 판정기가 재는 동안 한도를 넘으려는 프로그램이 얼마나 넘었는지는 "숫자" 절에 있다.
- **빌드가 `/app`에 쓰는 양에는 상한이 없다.** 파일 하나의 크기와 빌드 시간 900초만이 한정한다.
- **한도 안에서 멈춘 프로그램은 실패하지 않는다.** 파일을 한도까지 쓰고 더 쓰지 못한 프로그램, 프로세스를 한도까지 만들고 거절당한 프로그램은 그것만으로는 실패가 아니다.
- **보통 사용자는 판정기 프로세스가 있다는 것, 그 상태, 잡고 있는 메모리의 크기, 시작 시각, 프로세서 사용량과 커널이 넣었다 뺀 횟수, 걸려 있는 커널 한도, 그리고 붙어 있는 파일 시스템의 목록을 볼 수 있다.** 이 가운데 테스트의 이름이 든 것은 없다.
- **Harbor가 과제 옆에 띄우는 보조 컨테이너에는 상한이 없다.** 그 컨테이너는 프로그램 쪽의 것을 아무것도 돌리지 않는다.

## 보호 장치 하나하나와, 그것이 없으면 실패하는 테스트

보호 장치마다 그것을 뺀 코드를 하나씩 만들어 두었다(`bench/experiments/protections.toml`, 93개). `python experiments/check_protections.py`는 저장소의 사본에서 보호 장치를 하나씩 빼고 그 장치의 테스트를 돌린다. 86개는 테스트가 잡아내고, 테스트가 하나도 실패하지 않은 채 뺄 수 있는 장치가 있으면 이 확인이 실패한다. 나머지 7개는 둘째 방어선이다. 그것이 없어도 공격은 아무것도 얻지 못하고, 어떤 다른 장치가 그렇게 만드는지는 표에 적었다. 둘째 방어선은 그 장치를 뺀 채 공격 테스트를 돌려서, 하나라도 실패하면 이 확인이 실패한다. 이 표와 그 파일이 같은 보호 장치를 담고 있는지도 테스트가 확인한다. 목록은 이 문서가 아니라 코드에서 만들었다. 두 판정기, 변환기, 판정기를 띄우는 스크립트를 문장 하나씩 읽어서, 분리나 한도나 돌려받기만을 위해 있는 문장마다 항목을 두었다. 한 장치가 코드의 여러 곳에 있으면 곳마다 항목을 따로 두었다. 항목이 빼는 글은 그 파일에 꼭 한 번 나오고, 두 번 나오거나 나오지 않는 항목은 이 확인이 받아 주지 않는다.

## 아직 확인하지 못한 것과 한계

- **자동 검사는 Python 이미지만 만든다.** 나머지 여섯 언어의 판정은 측정 기계에서 돌린 숫자다. 여섯 언어의 이미지나 풀이가 바뀌면 측정 기계에서 다시 돌려야 드러난다.
- **Harbor를 거친 판정은 웹 과제의 정답 풀이 세 언어와 명령줄 견본의 Python으로 확인했다.** 나머지 언어는 판정 컨테이너 안에서 도는 판정기가 같다는 것까지만 확인했다. AI가 일하는 컨테이너에도 같은 설정 파일이 적용되는데, 그 컨테이너에서 실제 AI를 돌려 보지는 않았다. 그래서 AI가 거기서 스스로 빌드하는 것에 이 상한이 충분한지는 재지 못했다. 실제로 돌려 봐야 알 수 있다.
- **커널이 적어 두는 메모리 최고값은 지금 쓰는 커널에서 되돌릴 수 없다.** 같은 컨테이너의 앞선 최고값 아래에 머문 실행은 판정기가 직접 재는 것으로만 보인다.
- **남는 것을 만드는 호출을 거절하는 거르개는 두 종류의 기계에서만 안다.** 이 저장소의 측정 기계(ARM)와 자동 검사 기계(x86)다. 다른 종류의 기계에서는 판정기가 거절한다.
- **컨테이너의 메모리를 세는 방식은 지금 쓰는 커널의 방식(묶음 계층 2판)에 맞춰져 있다.** 다른 방식의 기계에서는 판정기가 상한을 읽지 못해 거절한다.
- **실제 AI로는 돌리지 않았다.** AI가 받는 설명만으로 이 과제를 풀 수 있는지는 준비한 풀이가 그 설명대로 만들어졌다는 것으로만 뒷받침된다.
- **견본은 과제 하나다.** 로그 분석기나 설정 검사기처럼 다른 주제에서 필요한 검사(예: 셸로 넘어가는 입력)는 그 과제를 만들 때 더한다.
- **Rust 이미지에는 누구나 쓸 수 있는 파일이 도구 모음 아래에 하나 있다.** 판정기가 판정할 때 닫는다. 이미지는 고치지 않았다.
